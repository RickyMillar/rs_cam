## Tooling and setup

### Tool families

- Flat end mill
- Ball nose
- Bull nose

### Tool metadata exposed in the GUI

- geometry: diameter, cutting length, corner radius, included angle, taper angle

- cutting metadata: flute count, tool material, cut direction

### Machine and material models

- stock material library in `rs_cam_core::material`
- machine profiles in `rs_cam_core::machine`
- feeds/speeds calculator in `rs_cam_core::feeds`
- **every feeds cell declares its basis** (feeds matrix, 2026-09-23) — `FeedsResult::support` reads `VendorBacked` when a printed vendor row answered, `FormulaOnly { source }` when the calculator's formula answered (the source string names the fit and the uncited k0), or `Refuse`. Suggest refuses the tool the operation's own registry row refuses (`tool_constraints`), the same rule the generator applies, and the refusal names the operation and the allowed kinds in words: non-V tools on VCarve, Inlay and Chamfer; a bull nose on Scallop and UnifiedFinish; a flat end mill, bull nose or V-bit on Pencil and SpiralFinish. For those two operations the generator and the MCP operation schema (`required_tool_type`) moved with Suggest: a Pencil or Spiral Finish toolpath with a non-ball tool no longer generates. **A formula-only wood cell ships only where a published chart backs the formula** (ruling R1, evidence half, 2026-09-23): `feeds::support::formula_backing` encodes `planning/feeds_matrix_2026-09-23/FORMULA_BACKING_v2.md` for softwood, hardwood, MDF and hardwood plywood; a cell with no vendor row that the judgement calls CLUELESS refuses with `FeedsError::Unbacked` and a reason that names the missing chart (every drill cell except the G6 flat end mill plunge claim below, ball nose in MDF and plywood, bull nose finishes in plywood, V-bit adaptive and parallel, tapered ball roughing, ...). The refusal is about the recipe, not the operation: the GUI and MCP add doors still create the operation with its registry and stock defaults and no recipe, and say so ("Added without a feeds recipe: ..."). Other materials keep the formula, except a drill. **A flat end mill plunge ships from the Amana Spektra Ramp Down rule** (ruling B5, G6, 2026-09-24): a 2- or 3-flute flat end mill at 3.175-6.0 mm in wood, plywood or MDF reads its own printed side chip / Z, held per tooth at the drill RPM cap (14 000), so the feed is about 0.78x the printed Ramp Down, and the card says so; every other drill cell refuses in every material, and the unsourced 2.5 drill multiplier is gone. Matrix on 15b98aaa: 498 of 960 cells ship (416 vendor-backed, 82 formula-only), 462 refuse (192 tool rule, 270 CLUELESS). The vendor table holds the printed chart rows with stored chart text and hashes; rows that no chart prints are labelled `derived`, grade C. Where a chart prints one value per size (Amana Spektra spiral plunge: flat-end pocket and adaptive at 1/8 in, 6 mm, 1/4 in) the row carries a maximum only, so Suggest shows no band and the post-simulation burn gate is silent on those cells. One published depth de-rate (Onsrud, Freud, Amana: 1.00 / 0.75 / 0.50 at 1 / 2 / 3 x D, linear between, 0.50 held above with a Caution) scales the feed, the shown band and the gate alike; the unsourced 1.5 x D depth hint is gone. **A finishing or semi-finishing pass has no axial depth ceiling** (ruling R2, 2026-09-23): Suggest ships its depth, the load report shows the measured peak with no bound (`load.depth.reported`), and the deflection gate is the limit; roughing keeps the depth ladder and the rigidity clamp. On a tapered ball, Suggest and the depth gate size the cap from one diameter, the engaged diameter at the depth (before, the clamp read the tip and the gate the shank). A depth exceedance is a Caution in the diagnostics list (`load.depth.exceeds`, never blocks export); an unmodelled depth gate has its own id. **The feeds charts draw one line at the suggested value** and fainter band lines only when the vendor row publishes both limits; no shading, no invented width (chart-display ruling, 2026-09-23; `FeedsExplain::published_chipload_band`). A one-value row reads "row publishes one value". **The rubbing floor is a warning, not a clamp** (ruling R4 WP2a, 2026-09-24): Suggest no longer raises a feed to the 0.025 mm/tooth floor (repo rule, unsourced); a commanded advance below it ships as computed and carries `feeds.chipload_below_floor` (Caution) with the consequence and the levers on the Feeds card. **The long-tool de-rate is visible** (R4 WP1): ×0.88 above 4 × D stickout, ×0.75 above 6 × D (repo rule, unsourced) shows as an Info line on the Feeds card and as `feeds.long_tool_derate` in diagnostics and MCP; no number moves. **Machine aggressiveness** (ruling R4 WP3, 2026-09-24; `MachineProfile::aggressiveness`, 0.50–1.50, default 0.85) sets the load of a Suggest recipe as a fraction of the load at full engagement. The chipload stays at the vendor band value times the published depth ladder; Suggest scales the depth per pass and the stepover by one common factor until the predicted force and spindle power fit the target, and the card prints the pairs (depth, stepover, force, power before and after). A long tool (over 4 × D or 6 × D stickout, repo rule, unsourced) lowers the target to 0.88 or 0.75 of the dial and no longer cuts the feed. Above 1.00 the engagement rises inside the rigidity cap, the flute length and one diameter, with a Caution. Finish passes and drills take no dial action, and the card says so; the plunge and the ramp ship the material base with no factor. The hidden ×0.75 feed factor is gone and the spindle power ceiling is the rated power curve, so every feed that the factor moved is now the published value (finish passes load 3–28 % more than before; roughing loads fall to 0.66–0.88 of before). The rubbing floor is min(0.025, the band minimum) and names its source. The workholding selector is gone; the machine aggressiveness dial is the one load margin (ruling R4 Q8). The simulation modulator's multiplier is `modulation_feed_scale` (CLI `--modulation-feed-scale`); the old name is gone with no alias. Known gaps recorded in the literature matrix: no sourced Ipe, micro-tool or aluminium de-rate exists; a tool under 1.5 mm whose only chart row is more than 2× its size refuses a recipe rather than extrapolate (R1 applied to size); the next feeds package is a sourced size-scaling law with a stated valid range.

### Stock changes per setup

- **a setup can add material to the stock or remove material from it before its first toolpath** (stock additions S0–S4, 2026-10-09; `compute::stock_change`, `compute::stock_change_apply`). The capability is generic: a change is Add or Remove; its geometry is a closed mesh model, an outline fill (every space open to the setup's +Z inside closed 2D outlines, up to a level Z; it fills what the earlier toolpaths cut) or an outline extrude (a prism from Z from to Z to); an Add takes any material from the library or a custom name. Every value is in the setup frame. The simulation carries the stock from setup to setup (S0) and applies the enabled changes in list order (S3); a change stales the simulation and the rest results from its setup on (S2). The setup panel lists the changes beside the fixtures (enable, edit, move, delete; a material picker; the volume after a simulation); MCP has `add_stock_change`, `edit_stock_change`, `move_stock_change` and `remove_stock_change`, and `list_setups` / `inspect_stock` list the changes with their volumes (feature `stock_changes`); the CLI `project` command prints one line per change with its volume, and `summary.json` carries them. The three surfaces print one volume text (`ProjectSession::stock_change_rows`, `StockChangeVolume::volume_label`). A remove with an outline fill is refused by name. **Cut as** (S6, operator ruling 2026-10-09, "in theory it is just more stock"): an Add carries `cut_as` (`stock_material`, the default, or `own_material`; a Remove ignores it). By default the gates (chip load, power, deflection, depth), the cut metrics and the feed modulation cut the added material exactly as the stock material, so a fill gives the verdicts and the modulated F-words of plain stock. With `own_material` the samples whose main slot is that material are judged with its own force data in their own verdict (`ToolpathLoadVerdict::material_split`, which joins the export gate); a material with no force data is "not judged: no force data for <material>", counted and named per toolpath in the load-report summary (`not_judged`) and the diagnostics (`load.material.not_judged`). One helper decides (`SimulationCutTrace::effective_material_for_sample`). Toolpath generation and Suggest never read the added material. GUI: a "Cut as" row in the change editor (Add only); MCP: `cut_as` on `add_stock_change` / `edit_stock_change` and in the change JSON (feature `stock_change_cut_as`); CLI: the line reads `material <name> (cut as stock)` or `(own material)`. The stock views draw each added material in its own colour (S5): the mesh builders record the material slot of each vertex (`StockMesh::material_slots`, one byte per vertex, none for a one-material stock), slot 0 keeps the wood depth shade, and another slot takes a default colour (8 hues 45 degrees apart, the wood hue first) or the change's `display_colour` (project file only), darkened with depth so the relief still reads. This holds in the live playback, the paused view, the checkpoints, the final mesh and `screenshot_simulation` (there the stock material keeps the height colours); the deviation and height colours hide it. The viewport legend has a "Stock materials" row with each material and its swatch (`ProjectSession::stock_material_legend`). Not yet: a colour picker in the GUI and MCP; the CLI job TOML has no stock-change keys (a project file carries them). Sentries: `stock_changes_stale_from_their_setup_on_s2`, `stock_changes_apply_to_the_stock_s3`, `stock_change_lines_s4` (CLI), the S4 tests in `rs_cam_viz` (`stock_change_panel_s4`, `the_gui_row_and_the_mcp_reply_print_the_core_volume_s4`), `stock_materials_show_in_every_view_s5`, the S5 legend tests in `rs_cam_viz` (`stock_material_legend_s5`), `added_material_cuts_as_stock_s6`, `stock_change_cut_as_s6` (CLI), `the_gui_and_the_mcp_reply_name_the_cut_as_s6`

## Toolpath modifiers and control layers

- heights system: clearance, retract, feed, top, bottom
- entry dressups: plunge replacement via ramp or helix. The helix radius is the repo rule 0.3 x D or an operator value, capped at the tool's flat bottom so the helix leaves no core; a helix or ramp entry never runs above the cut feed (G10 Part B)
- dogbone overcuts
- lead-in / lead-out arcs
- link moves / keep-tool-down linking
- arc fitting to `G2` / `G3`. **Arcs do not cross an intent boundary** (2026-08-04): the fitter's run key carries `Move::intent` and breaks on `Region` span edges, so a fitted arc's label is exact rather than inherited from its first source move. Fitted arcs are tagged `SpanKind::GeometryRefit` and stay **in** tool-load gate populations; only true dressup bridges (dogbones, links, lead-outs) are excluded
- feed optimization dressup with stock-aware engagement estimation on supported workflows
- air-cut filter dressup: removes cutting moves through cleared stock when using remaining-stock mode
- stock-aware generation: per-toolpath "Start from: Stock / After previous ops" row on the Geometry tab; "After previous ops" reads the simulated material the earlier operations leave, across a setup boundary too. The 2026-09-19 claim "a setup's first such operation reads the previous setup's finished stock" was not true in the simulation until S0 (2026-10-09): before it, each setup started from a fresh block. Now a Top or Bottom setup starts from the finished stock of the Top or Bottom setup before it, mapped into its own frame (flip, origin shift, Z rotation), and its metrics, gates, checkpoints and "After previous ops" snapshot read that stock. A lateral setup (Front, Back, Left, Right) starts from a fresh block, and the simulation result says so per setup (`SimulationResult::group_starts`)
- per-operation manual pre/post G-code blocks (editable in GUI, emitted in export)
- TSP rapid-order optimization (not on Face, 2D Adaptive or 3D Rough: those keep the planned cut order)
- stock-boundary clipping with center / inside / outside containment. **Not unconditional** (2026-08-05): when the boundary offset *collapses*, the path passes through unclipped rather than over-clipped, and the report-only `ToolpathStats::boundary_clip_dropped` finding names it; when the offset *fails* (rejected input or a contained library panic), the operation now refuses instead of silently emitting an uncontained path
- the model-silhouette boundary is the OUTER LOOP of the model's XY projection (R1, 2026-09-18): a through-hole in the model is material for the boundary, so a rough clears it and a finish traces its walls; a keep-out is the mechanism for "do not cut here". `geometry::boundary::silhouette_machining_outline` holds the rule, and the raw `model_silhouette` still reports the hole
- the "Model Outline" boundary source (G-MODELOUTLINE, 2026-09-29) takes the closed 2D shapes of ANY project model (a DXF or SVG), not only the toolpath's own: a 3D rough on a terrain STL or a Project Curve on a rivers DXF cuts only inside another drawing's outline. Holes stay uncut, so a ring machines only the ring. Containment and offset apply as for rest regions. A missing model, or a model with no closed shape, refuses the generation and names the model; it never falls back to the stock. MCP `set_boundary_config` takes `source: "model_outline"` with `model_id`. The "Machine the holes" option (`holes`, MCP `outline_holes: true`, 2026-09-29) inverts the regions: one region per hole ring of the union, less any other shape of the model inside that hole. An edge-band ring then machines the area inside the band and stays off the band; the summary line reads "outline holes of model '<name>'", and a model with no hole refuses and names the model
- a new 3D operation on a mesh model starts with the boundary "model silhouette + one tool diameter", `Center` containment (R2, 2026-09-18; `BoundaryConfig::for_3d_op`), so the cutter reaches the outer faces of the part. The offset is a stored number: a later tool change does not update it, and an existing toolpath keeps its saved offset. Both creation doors (GUI and MCP `add_toolpath`) apply the same rule
- dual compute lanes: toolpath generation plus analysis (simulation / collision)
- lane-status chips and a single `Cancel All` overlay action

Three things moved on 2026-09-08 after a live look reported a terrain painted almost entirely red (F1-F5). (a) The **floor now measures curvature and the verdict abstains on it**: the old figure was a plane-only profile-sampling shortfall, and the term that bites is `cell^2 / (8 (rho - R))` on a concave feature of radius rho. Measured on the reported case (Ø4 tapered ball, 0.645 mm cell) the plane-only term is 0.132 mm and the curvature term 0.234 mm, so the old figure understated the grid's limit by 1.8x — but the larger half of the finding is that 0.132 mm was ALREADY far above the 0.05 mm bar it was read against, and **no operator surface compared the two**. `profile_floor_mm` and `curvature_floor_p95_mm` are now published apart, `tolerance_below_floor` says when the bar is under the arithmetic, and the band between them is `unresolved_area_mm2` rather than unreachable. **Which way the error runs is now stated and was stated BACKWARDS until 2026-09-08**: the sampled minimum sits at or above the continuum minimum, so the gap bias is non-negative, the unreachable percentage OVER-states and the true share is AT OR BELOW it — measured 59.05 against a true 58.6 % at 0.05, 51.11 against 42.1 at 0.146, 36.36 against 26.8 at 0.30. `reached` is the sound side: a cell called reached really is formed. Same tool and cell, before -> after at the three bars: 68.2 % -> **59.05 %** (9.14 % unresolved) at 0.05, 51.11 % (1.71 %) at 0.146, 36.36 % (0.03 %) at 0.30. An independent 0.15 mm rasterisation of that STL puts the truth at 55.0 / 39.5 / 25.2 %, so the error at the default bar falls from +13.2 pp to +4.05 pp — and the red was mostly REAL: that mesh's own facet roughness puts its median gap at the 0.05 mm bar. The residual is a slope-KINK regime the curvature term does not bound (it is a C2 bound); ledgered in `curvature_floor_plane` with a measured table, not fixed. (b) The **bar is derived from the raster**: `drop_cutter` declares a stepover, not a scallop height, so every raster finish fell to 0.05 mm; a 1.5 mm stepover on a R2.0 tip has a 0.146 mm cusp, where the same terrain reads 39.5 %. (a2, P5.2 2026-09-08) The **area base is stated on every surface** and it is not a detail: both halves of the ratio are TRUE 3D SURFACE AREA over the rim-eroded population, and a planar whole-board comparison of the same closing reads 5 points lower on a terrain whose mean sec(theta) is 1.34. An `area_basis` line now rides the MCP reply. Put on that base the independent rasteriser reads 58.6 / 42.1 / 26.8 % against the map's 59.05 / 51.11 / 36.36 %, so 3.5 of an apparent 12-point offset was the rasteriser's own base; the rest is the documented discretisation, which survives the tolerance because it is additive in the GAP (+0.054 mm at the median) rather than in the percentage. The Ø4 taper's CONE was tested as a candidate and contributes **+0.01 pp** — it rises 19 mm per mm of radius, so it almost never rests on a neighbouring flank. (a3) The overlay colours by **GAP DEPTH**, log-scaled from the bar to the deepest gap, with unresolved cells in neutral grey and the ramp's stops in the panel legend; the old ramp saturated at 5x the tolerance, so a 0.3 mm near-miss and a 4.5 mm gorge floor were the same red and the distribution's shape — the thing that says which valleys need the finer tool — was invisible. `tolerance_source` names the rung. (c) The **cell no longer moves with the tolerance** — three probes of one tool came back on 0.645, 0.75 and 0.625 mm, so three percentages meant to be compared sat on three grids; the cell now follows the tool's tip sphere and the model bbox, and `cell_mm` plus the floor lead the MCP reply (`grid_note`) and the panel legend

The stack is not persisted and is empty after a restart. Sentries: `add_toolpath_via_gui_g_guiadd.rs`, `get_notifications_g_toastread.rs`
- **toolpath rebinding** (F3.7 / F3.8, 2026-09-10) — `set_toolpath_tool(index, tool_id)` and `set_toolpath_model(index, model_id)` change a toolpath's cutter and its geometry input over MCP. Before them the two fields were reachable only from the GUI inspector's Tool: / Input: combos, so an operation blocked on its tool shape or holding a missing model reference was a dead end for an agent: `set_toolpath_param` writes the OPERATION's params and refuses both keys ("unknown parameter 'tool_id' for Pocket operation…"), and that refusal is kept — the two namespaces stay disjoint. Both take a project-assigned **id**, not a positional index, and echo the resolved tool / model in the reply. A rebind invalidates the toolpath's own result and every downstream operation that machines the stock it leaves (`ProjectSession::set_toolpath_tool` / `set_toolpath_model` → `invalidate_result_chain`), which is strictly more than the GUI combos do today — they write the same fields and invalidate nothing. `set_toolpath_tool` deliberately allows a tool the operation's shape constraint rejects, so a blocked operation stays repairable; the generator is still the one that refuses. Sentries: `toolpath_rebind_g_mcprebind.rs` (core behaviour), `mcp_rebind_surface_g_mcprebind.rs` (registration and schema)

- **`generate_all` counts what it did not generate** (memory programme wave 3, 2026-10-01). An operation that already holds a current result is not generated again. The reply carries `already_current` and `enabled` beside `generated`, and the GUI toast reads "Generated 5 toolpaths, 2 already current (7 enabled; …)". Before, one project read "Generated 5" or "Generated 7", by whether the GUI's auto-regeneration after load had already run. The call does not change any toolpath's `debug_options` (U4, 2026-10-01; before, it set `debug_options.enabled = true` on every enabled toolpath, and a save wrote that change); `get_generation_debug_trace` answers after it anyway
- **cut-trace figures are `null` without a trace** (U2, 2026-10-01) — MCP `get_diagnostics` and the CLI `project` report give `total_runtime_s`, `air_cut_pct_of_total_runtime`, `air_cut_pct_of_cutting_time`, `average_engagement` and every `triage.counts` tally as `null` (NOT MEASURED) when the simulation kept no cut trace, and `cut_metrics_not_measured` names the reason. Since 2026-10-02 every simulation on every surface captures the trace ("always capture"; the GUI checkbox is deleted). A result that still holds no trace makes Optimize (project and per toolpath) and the tool-load rows name the missing trace and say to re-run the simulation, not "run a simulation first"

## CLI surface

Verified direct CLI commands (T9 cull, 2026-06-07 — the ~13 per-op
subcommands were replaced by the registry-driven generic `run`):

- `version` — build info for all workspace crates
- `job` — TOML job file (multi-tool/multi-op batch; executes through the session pipeline)
- `run` — ANY of the 23 operations: `run <op> --input model --tool type:diameter --set k=v --output out.nc`; `run --list-ops` / `run <op> --list-params` print the registry
- `sweep` — parameter sweep over a job file with fingerprint diffs
- `project` — GUI project file (format_version=3) full-diagnostics executor. `--output-dir <DIR>` is REQUIRED (memory programme U5, 2026-10-01; breaking): the command wrote into `./diagnostics` by default, and its `simulation.json` holds the whole cut trace, gigabytes on a large project. `simulation.json` is written only with `--sim-artifact` (default off, 2026-10-02; breaking: a caller that reads the file must pass the flag), the same default as the GUI cut-trace file; `summary.json` and the `tp_*.json` files are written on every run, and their cut-trace figures are still measured. Without a cut trace the cut-trace figures in its report (`total_runtime_s`, the two air-cut percentages, `average_engagement`, the triage counts) are `null` / NOT MEASURED, never 0, and `cut_metrics_not_measured` names the reason (U2)
- `smoke` — F-037 smoke baseline suite
- `nc-time` — G-code cycle-time prediction

Every operation in the registry is reachable from the CLI; a new
operation appears in `run` with zero CLI code.

The global flag `--memory-limit <SIZE>` (a binary size such as `12GiB`, a
byte count, `unlimited`, or `default`) sets the memory budget of the run.
When the process uses more, the generation plan stops and names the two
values and the remedies, before the system kills the process. The flag
overrides `[memory] limit` in the settings file. With neither, the limit is
half of the system RAM.

The MCP `generation_status` reply carries the GUI's budget as `budget`:
`limit_bytes` (null for no limit), `source` (`default half of RAM`,
`settings file` or `unlimited`), `reserved_bytes` and `process_rss_bytes`.
The MCP server thread reads it, so the reply does not wait for the GUI.

## Settings file

`settings.toml` holds the app settings that the GUI and the CLI share
(memory programme B5, 2026-10-01; File ▸ Preferences, 2026-10-02). One
loader and one writer in core (`rs_cam_core::settings`) read and write it
for both surfaces. A missing key is the default, which is the behaviour
before the key existed. The writer removes a key whose value is the
default, except `[memory] limit`.

```toml
[memory]
limit = "12GiB"            # a binary size (B, KiB, MiB, GiB, TiB), a byte
                           # count, "unlimited", or "default" (half of RAM)
[general]
window_width = 1400.0      # points; read at start
window_height = 900.0      # points; read at start
undo_depth = 100
toast_info_seconds = 4.0
toast_warning_seconds = 6.0
toast_error_seconds = 8.0
confirm_unsaved_quit = true
[display]
show_all_toolpaths = false         # WP27: the selected toolpath only
toolpath_colour_mode = "normal"    # "engagement", "advance_per_tooth"
[display.overlays]                 # an overlay id = true or false in
grid = true                        # every viewport workspace
[simulation]
playback_speed = 500.0     # moves per second
stock_view = "solid"       # "deviation", "by_height"
stock_opacity = 1.0
[paths]
tool_library = "/path"     # RS_CAM_TOOL_DIR wins over it
machine_library = "/path"  # RS_CAM_MACHINE_DIR wins over it
screenshots = "/path"      # else the current folder
[diagnostics]
save_cut_trace = false     # operator ruling 2026-10-02: off
cut_trace_retain = 5
artifact_dir = "/path"     # else <user cache>/rs_cam/artifacts
log_level = "info"         # RUST_LOG wins over it; read at start
present_mode = "fifo"      # RS_CAM_PRESENT_MODE wins over it; read at start
```

- The path: `$RS_CAM_SETTINGS` (a file), else
  `$XDG_CONFIG_HOME/rs_cam/settings.toml`, else
  `~/.config/rs_cam/settings.toml`. On Windows with no `HOME`:
  `%APPDATA%\rs_cam\settings.toml`, else
  `%USERPROFILE%\.config\rs_cam\settings.toml`.
- A missing file, a missing `limit`, or `limit = "default"` gives the
  default memory limit: half of the system RAM (operator ruling
  2026-10-02). When the platform does not give the system memory, the
  default has no limit.
- A file that is not TOML gives the defaults and a warning: a toast in the
  GUI, a log line in the CLI. A key with a bad value gives the default for
  that key and a warning; the other keys stay.
- The library folders resolve in this order for the GUI, MCP and the CLI:
  the environment variable (`RS_CAM_TOOL_DIR`, `RS_CAM_MACHINE_DIR`), then
  `[paths]`, then `tools` or `machines` in the config folder (the folder of
  the default settings file, with the same Windows fallback).
- The simulation cut-trace file is OFF by default (operator ruling
  2026-10-02). The app keeps the cut trace in memory either way; nothing
  in the product reads the file back. When it is on, the file and the
  toolpath debug trace go to `[diagnostics] artifact_dir`, else
  `$XDG_CACHE_HOME/rs_cam/artifacts`, else `~/.cache/rs_cam/artifacts`
  (`%LOCALAPPDATA%\rs_cam\artifacts` on Windows). Before 2026-10-02 they
  went to the build tree's `target/`.
- **File ▸ Preferences** has a category bar on the left: General, Memory,
  Display, Simulation, Files and libraries, Diagnostics (advanced) and
  Automation (MCP, read-only status). Apply writes the file and applies
  the values at once where it can: the memory budget (the next job), the
  undo depth, the quit question, the library and screenshot folders, the
  toast durations (the next toast), the overlay defaults (the next
  workspace switch), the diagnostics files (the next job). The simulation
  defaults apply at the next start or project open. The window size, the
  start colour mode and "All toolpaths", the log level and the present mode
  apply at the next start; the window says so. Cancel discards the draft.
- The window does not offer a value that changes a computed number or an
  instrument switch (`RS_CAM_STAMP_DISPATCH`, `RS_CAM_PLAYBACK_DISPATCH`,
  the feed-modulation switches, timing constants, test and bench variables).
- The precedence in the CLI, highest first: `--memory-limit`, then
  `[memory] limit` in the file, then the default. The CLI flag does not
  apply to the GUI.
