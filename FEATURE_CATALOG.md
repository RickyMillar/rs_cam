# Feature Catalog

Canonical product-surface reference for `rs_cam`.

For source attribution and upstream lineage, see [`CREDITS.md`](CREDITS.md).

## Product surface

| Component | Role |
|-----------|------|
| `rs_cam_core` | CAM library: geometry, import, tool modeling, toolpath generation, dressups, simulation, feeds/speeds, and G-code |
| `rs_cam_cli` | Batch CLI and TOML job runner |
| `rs_cam_viz` / `rs_cam_gui` | Desktop CAM application built with `egui` and `wgpu` |
| `rs_cam_mcp_proxy` | Stdio MCP supervisor in front of `rs_cam_gui --mcp`: keeps the MCP session up when the GUI exits and lets the agent restart the GUI |

## Tooling and setup

- **Tool fact provenance (K3, feeds contract P6)** — Each measured tool fact (flute length, stick-out, flute count, shank diameter, taper half-angle, centre cutting, V tip diameter) states how it is known: stated, catalogue (with its source), estimated (with its basis) or unknown. A file writes each fact as a table (`stickout = { stated = 30.0 }`); a bare number refuses to load with one message that names every bare key (project file, tool library, CLI job file); an absent key is unknown. An unknown fact plans at the old loader default and the toolpath lineage records one `tool.fact_unknown` warning for it; the lineage shows the kind of each fact it used. `scripts/migrate_tool_facts_k3.py` rewrites a bare fact as `estimated` (`--backup` writes a `.bak`). Ruling D12 (P7 A2, 2026-11-04): centre cutting, and the tip of a V-bit, are required: an op whose tool does not state them (stated, or a catalogue row; an estimate does not count) stops with a reason that names the tool and the fact ("state centre cutting for tool T6: yes or no", "state the tip diameter of V-bit T3"), on the GUI, MCP and the CLI, as an unset depth does. The tool panel holds Cuts at centre (Yes / No / ?) and, on a V-bit, Tip Ø; MCP `set_tool_param` and the CLI job file take `v_tip_diameter`. A new tool states neither. `scripts/state_tool_facts_d12.py` writes the operator's statements into project, catalogue and job files (never a key that is present; `--dry-run`, `--backup`).
- **Non-centre-cutting tool model** — Tools can store measured `centre_core_diameter_mm` and `blade_protrusion_mm` as the fact `centre_cutting = { stated = "no", .. }`; `{ stated = "yes" }` states a centre-cutting tool, and no key means not known (the motion of a centre-cutting tool). The GUI tool editor (a yes / no / ? choice), project and tool-library TOML, CLI job TOML, CLI `--tool-set`, and MCP `add_tool` / `set_tool_param` carry it. The core validates finite measurements, `0 < core < diameter`, and `protrusion >= 0`. It derives the maximum plunge depth and descent angle for later planning and simulation gates. A zero protrusion permits lateral cutting only.
- **Physical rules (K5, feeds contract P7, commit A, 2026-11-04)** — One table (`compute::feasibility`, `physical_rules!`) lists each physical rule with its fact and its outcome at the plan, generation, simulation and export stages; no stage can refuse a job (ruling Q6). After generation the session reads the emitted moves, the tool facts and the stock box (no mesh, so a drawing op is judged too) and records one row per rule that warns. Each row reaches the generation diagnostics, the export result and the G-code header (GUI, MCP, CLI), and the lineage `rules`; its text names the fact, its value and how it is known ("flute 25 mm, estimated: cuts 30 mm below the top (by the stock box)"). Rules: `tool.reach_past_flute` (the cut goes deeper below the top than the flute; a Drill measures from the rim of each hole), `tool.reach_to_holder` (the cut goes as deep as the stickout; equality warns; a Tool warning and a Caution, because it reads the stock box), `tool.v_tip_unmodelled` (a V-bit only: the cone height of the stated tip disagrees with the flute). A stated V tip is now in the cutter model and the feeds hint. The pre-simulation reach rows read the stock box, so they over-read where an earlier op removed the material. Commit B (2026-11-04): the simulation measures the flute reach on the carved stock (each fed move that can reach past the flute reads the wood inside the cutter radius before its own cut; a drill reads each hole): `tool.flute_overreach` names the moves with wood over the tip above the flute, and a clean run gives `tool.flute_reach_within` (Info). With a fresh simulation either row replaces the stock-box row in the diagnostics and the export, so a cut inside material an earlier op removed reads clean. Commit C plans the CentreCut limit (see Non-centre-cutting enforcement); the lineage `rules` hold every rule that fires. Sentries: `every_physical_rule_warns_through_a_row_k5`, `a_hole_deeper_than_the_flute_warns_k5_reachflute`, `a_cut_that_reaches_the_holder_face_warns_k5_reachholder`, `a_v_tip_flat_is_modelled_or_named_k5_vtipflat`, viz `the_k5_rule_rows_reach_every_surface_k5`.
- **Non-centre-cutting enforcement (G-CENTRECUT part 2)** — The tool owns the limits, and every entry reads them from the tool (`MillingCutter::non_centre_cutting`). The shared ramp and helix emitters clamp the ramp angle and the helix pitch to `atan(protrusion / core)` and start each descent at the conservative material top. A 3D Rough with entry style Plunge, or a 2.5D op with entry style None, takes the shared ramp at the limit angle instead of a straight plunge. An entry that can only plunge deeper than the protrusion is kept and named (K6, ruling Q6: no finding refuses a job): `safety.non_centre_cutting_plunge`, a Tool warning recorded at generation (`ToolpathStats::non_centre_cutting_plunge`). The simulation records every fed move where the tool goes down into wood steeper than the limit or plunges deeper than the protrusion (`SimulationResult::non_centre_cutting_descents`; absolute limits, a descent in air is allowed), and the export names it (`safety.non_centre_cutting_descent`, a Tool warning in the result and the G-code header). K5 (P7 C, 2026-11-04): the 3D Rough cut and link paths and the terrain-clipped ramp also hold the limit slope (a raised path, never below the surface), and a Trace, Project Curve or Drop Cutter (straight-plunge ops) keeps its plunges and warns on each one deeper than the protrusion instead of taking a ramp. Not yet planned to the limit: the boundary-clip re-entry descents; the simulation gate catches them. Sentry: `a_non_centre_cutting_tool_never_plunges_into_stock_g_centrecut`.

### Stock changes per setup

- **obstacles: one concept for fixtures and keep-out zones** (K1, 2026-10-15; `compute::obstacle`). A setup holds a list of obstacles (`[[setups.obstacles]]`): a box, a prism from closed 2D outlines (outline extrude) or an imported mesh (its XY silhouette), each with a clearance, every value in the setup frame. EVERY operation keeps the tool out of each enabled obstacle, with the machining boundary on or off and with no opt-in: after the dressups a session step splits each move that would put the cutter, the shank or the holder (where its Z band reaches the obstacle) inside an obstacle grown by its clearance; the tool goes up to the obstacle plane (highest grown top + 5 mm), across, and down. The plane is local (K3): the safe and retract Z of an op do not read the obstacles, only a move that crosses an obstacle rises to the plane, and each toolpath starts at the plane so the move between toolpaths clears the obstacles. A stay-down link rises over an obstacle (`LinkCeiling`). Each op plans around the obstacles (K3, `compute::execute::territory`): the 3D finishes, Waterline and Project Curve lose the cutter footprint from their regions, 3D Adaptive pre-clears the cells under an obstacle, and Pocket, Zigzag, Face and 2D Adaptive lose it from their outlines; Profile, Trace and Chamfer keep their outlines and only the step clips them. The pre-clip reads the cutter band only: the shank and holder reach an obstacle only at a low enough tip Z, so the step judges them at the real Z. The model reads an obstacle as solid from its top down. Every simulation checks every move (rapids too) against the obstacles with the whole tool assembly; a hit is a collision (`SimulationResult::obstacle_collisions`, `CollisionKind::Obstacle`, verdict `obstacle_collision`, triage `project.obstacle_collision`) and adds to `collision_count`. An obstacle whose model is missing refuses the generation and the simulation by name. MCP: `add_obstacle`, `edit_obstacle`, `remove_obstacle`; `list_setups` / `inspect_stock` list them (feature `obstacles`). The GUI (K2, 2026-10-16) lists the obstacles on the setup page, each row with an enable checkbox and a visible Remove button, and edits all three kinds on the obstacle page (Apply / Cancel / Remove, the core refusal in a banner); add, edit, toggle and remove are undoable. The viewport draws each obstacle of the displayed setup as a line prism, its clearance as a dim ring at the grown top, and the obstacle plane while the setup or one of its obstacles is selected; one Obstacles overlay row (id `obstacles`) replaced the Fixtures and Keep-out rows. A mesh obstacle's model does not draw in the part view. Before K1 a fixture or keep-out acted only through an enabled machining boundary, so most operations ignored it, and the simulation reported no hit. Sentries: `every_op_conforms_w4` check 8 (every op, top-up and flipped), `a_lift_rises_to_the_plane_only_over_a_clamp_k3`, `a_manual_retract_rises_over_the_clamp_k1`, `compute::obstacle` unit tests
- **machine head and dust shoe** (H1, 2026-10-16; `machine::head`, `compute::shoe`). The machine profile holds a head (`[job.machine.head]`): fixed parts above the tool holder face (a diameter, or a shelf with no width limit; a height; hard or soft) on a fixed mount, and an optional dust shoe (parts from the brush end up, a normal gap, an optional travel range). Hard parts join every check (the obstacle step, the link ceiling, the simulation, `collision_check`); soft parts never block; a shelf is a Z floor for the tip under the highest stock or obstacle top. The shoe solver gives each run of one tool and one setting the lowest gap that keeps the hard shoe parts clear of the fresh stock box and the obstacles, or Raised; the shoe moves no toolpath and enters only the checks. ### Geometry selection

One selection says which items of the models an operation cuts (geometry selection P2–P4, 2026-10-19 and 2026-10-20). An item is a loop, an open path, a circle, a point or a flat face. A selection holds rules, then picks and excludes. Each surface resolves it through one core resolution, the one that generation uses (`ProjectSession::selection_status`), so the GUI, MCP and the CLI cannot disagree. Every selection edit is one `edit_toolpath_selection` command (`ProjectSession::apply`). In the GUI every selection act is one undo step (E4, 2026-10-29: one step per act on every GUI door — a click, a panel edit, the boundary switch — and the panel snapshot moves past the act; an edit that changes nothing pushes no step). ## CLI surface

Verified direct CLI commands (T9 cull, 2026-06-07 — the ~13 per-op
subcommands were replaced by the registry-driven generic `run`):

- `version` — build info for all workspace crates
- `job` — TOML job file (multi-tool/multi-op batch; executes through the session pipeline). C2 (2026-10-16, breaking): every op in the registry is a job op; `type` is the `run --list-ops` token and every other operation key is a schema parameter (`run <op> --list-params`), with dressup fields in `[operation.dressups]`. An unset key keeps the registry default, and an unknown key refuses. The pre-C2 keys `order_by`, `strategy`, `tabs`, `entry`, `entry_3d`, `dogbone`, `stock_to_leave` (3D Adaptive), `spindle_speed` (per op) and the token `drop-cutter` refuse. Geometry selection P2.7 (2026-10-19): the job key `selection` (`[operation.selection]`, with `[[operation.selection.rules]]` and `[[operation.selection.picks]]`) takes the shape of the project file's `operation.params.selection`; the CLI applies it through the `edit_toolpath_selection` command, so a rule on a layer the drawing does not hold refuses and names it, and a 3D op refuses the key (sentry `a_job_layer_rule_cuts_only_its_layer_p2_7`). F7 (2026-10-29): the job key `boundary` (`[operation.boundary]`, the project-file boundary block: `enabled`, `source`, `containment`, `offset`) writes the machining boundary through `set_boundary_config`, and the job key `boundary_selection` (`[operation.boundary_selection]`, the selection shape) writes the boundary selection through `edit_toolpath_selection` with `target: boundary`, after the boundary; a boundary whose source is not `selection` refuses with the MCP text (sentries `a_job_boundary_selection_replays_one_selection_f7`, CLI test and `job.rs` unit test)
- `run` — ANY operation in the registry: `run <op> --input model --tool type:diameter --set k=v --output out.nc`; `run --list-ops` / `run <op> --list-params` print the registry
- `sweep` — parameter sweep over a job file with fingerprint diffs
- `project` — GUI project file (format_version=3) full-diagnostics executor. `--output-dir <DIR>` is REQUIRED (memory programme U5, 2026-10-01; breaking): the command wrote into `./diagnostics` by default, and its `simulation.json` holds the whole cut trace, gigabytes on a large project. `simulation.json` is written only with `--sim-artifact` (default off, 2026-10-02; breaking: a caller that reads the file must pass the flag), the same default as the GUI cut-trace file; `summary.json` and the `tp_*.json` files are written on every run, and their cut-trace figures are still measured. Without a cut trace the cut-trace figures in its report (`total_runtime_s`, the two air-cut percentages, `average_engagement`, the triage counts) are `null` / NOT MEASURED, never 0, and `cut_metrics_not_measured` names the reason (U2)
- `smoke` — F-037 smoke baseline suite
- `nc-time` — G-code cycle-time prediction

Every operation in the registry is reachable from the CLI; a new
operation appears in `run` with zero CLI code.

The global flag `--memory-limit <SIZE>` (a binary size such as `12GiB`, a
byte count, `unlimited`, or `default`) sets the memory budget of the run.
When the process uses more, the generation plan stops and names the two
values and the remedies, before the system kills the process. The flag
overrides `[memory] limit` in the settings file. With neither, the limit is
half of the system RAM.

The MCP `generation_status` reply carries the GUI's budget as `budget`:
`limit_bytes` (null for no limit), `source` (`default half of RAM`,
`settings file` or `unlimited`), `reserved_bytes` and `process_rss_bytes`.
The MCP server thread reads it, so the reply does not wait for the GUI.

## Settings file

`settings.toml` holds the app settings that the GUI and the CLI share
(memory programme B5, 2026-10-01; File ▸ Preferences, 2026-10-02). One
loader and one writer in core (`rs_cam_core::settings`) read and write it
for both surfaces. A missing key is the default, which is the behaviour
before the key existed. The writer removes a key whose value is the
default, except `[memory] limit`.

```toml
[memory]
limit = "12GiB"            # a binary size (B, KiB, MiB, GiB, TiB), a byte
                           # count, "unlimited", or "default" (half of RAM)
[general]
window_width = 1400.0      # points; read at start
window_height = 900.0      # points; read at start
undo_depth = 100
toast_info_seconds = 4.0
toast_warning_seconds = 6.0
toast_error_seconds = 8.0
confirm_unsaved_quit = true
[display]
show_all_toolpaths = false         # WP27: the selected toolpath only
toolpath_colour_mode = "normal"    # "engagement", "advance_per_tooth"
[display.overlays]                 # an overlay id = true or false in
grid = true                        # every viewport workspace
[simulation]
playback_speed = 500.0     # moves per second
stock_view = "solid"       # "deviation", "by_height"
stock_opacity = 1.0
[paths]
tool_library = "/path"     # RS_CAM_TOOL_DIR wins over it
machine_library = "/path"  # RS_CAM_MACHINE_DIR wins over it
screenshots = "/path"      # else the current folder
[diagnostics]
save_cut_trace = false     # operator ruling 2026-10-02: off
cut_trace_retain = 5
artifact_dir = "/path"     # else <user cache>/rs_cam/artifacts
log_level = "info"         # RUST_LOG wins over it; read at start
present_mode = "fifo"      # RS_CAM_PRESENT_MODE wins over it; read at start
```

- The path: `$RS_CAM_SETTINGS` (a file), else
  `$XDG_CONFIG_HOME/rs_cam/settings.toml`, else
  `~/.config/rs_cam/settings.toml`. On Windows with no `HOME`:
  `%APPDATA%\rs_cam\settings.toml`, else
  `%USERPROFILE%\.config\rs_cam\settings.toml`.
- A missing file, a missing `limit`, or `limit = "default"` gives the
  default memory limit: half of the system RAM (operator ruling
  2026-10-02). When the platform does not give the system memory, the
  default has no limit.
- A file that is not TOML gives the defaults and a warning: a toast in the
  GUI, a log line in the CLI. A key with a bad value gives the default for
  that key and a warning; the other keys stay.
- The library folders resolve in this order for the GUI, MCP and the CLI:
  the environment variable (`RS_CAM_TOOL_DIR`, `RS_CAM_MACHINE_DIR`), then
  `[paths]`, then `tools` or `machines` in the config folder (the folder of
  the default settings file, with the same Windows fallback).
- The simulation cut-trace file is OFF by default (operator ruling
  2026-10-02). The app keeps the cut trace in memory either way; nothing
  in the product reads the file back. When it is on, the file and the
  toolpath debug trace go to `[diagnostics] artifact_dir`, else
  `$XDG_CACHE_HOME/rs_cam/artifacts`, else `~/.cache/rs_cam/artifacts`
  (`%LOCALAPPDATA%\rs_cam\artifacts` on Windows). Before 2026-10-02 they
  went to the build tree's `target/`.
- **File ▸ Preferences** has a category bar on the left: General, Memory,
  Display, Simulation, Files and libraries, Diagnostics (advanced) and
  Automation (MCP, read-only status). Apply writes the file and applies
  the values at once where it can: the memory budget (the next job), the
  undo depth, the quit question, the library and screenshot folders, the
  toast durations (the next toast), the overlay defaults (the next
  workspace switch), the diagnostics files (the next job). The simulation
  defaults apply at the next start or project open. The window size, the
  start colour mode and "All toolpaths", the log level and the present mode
  apply at the next start; the window says so. Cancel discards the draft.
- The window does not offer a value that changes a computed number or an
  instrument switch (`RS_CAM_STAMP_DISPATCH`, `RS_CAM_PLAYBACK_DISPATCH`,
  the feed-modulation switches, timing constants, test and bench variables).
- The precedence in the CLI, highest first: `--memory-limit`, then
  `[memory] limit` in the file, then the default. The CLI flag does not
  apply to the GUI.
