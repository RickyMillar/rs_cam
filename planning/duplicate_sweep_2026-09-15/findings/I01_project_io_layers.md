## Evidence
- Writers: core `session/save.rs:110` `ProjectSession::save` → `to_project_file` (`save.rs:141-327`, `format_version: 3`). Viz `io/project.rs:450` `save_project` builds a second `ProjectFile` from `JobState`.
- Save callers: `controller/io.rs:373-392` `save_job_to_path` → `session.save` **only**. Viz `save_project` is called at `io/project.rs:1672,1741,1796,1890` — all its own `#[cfg(test)]` module. **No production writer uses the viz layer.**
- Load callers: `controller/io.rs:398-399` tries `ProjectSession::load`; `controller/io.rs:526-528` falls back to `crate::io::project::load_project` on **any** `SessionError`, then `build_session_from_legacy_job` (`controller/io.rs:626-780`). MCP `load_project` reaches the same `open_job_from_path` (`app/mcp.rs:2302`).
- Viz loader internals: `load_typed_project` (684-821), `load_legacy_project` (823-930), `load_legacy_model` (968-1006), `restore_project_*` (1073-1261), `assign_unique_id` (1263), `persist_model_path` (1283), `resolve_model_path` (1298), `infer_model_kind` (1310).
- Extension→kind copies: core `io.rs:134` (`pub`), core `project_file.rs:557` (`pub(crate)`), viz `io/project.rs:1310`, viz `controller/io.rs:788` (its doc comment names the `pub(crate)` visibility as the reason), plus ext tables at `app/mcp/commands.rs:366` and `ui/mod.rs:66-79`.
- Sentries, core side: `tests/model_path_round_trip_g_modelrelink.rs`, `setup_datum_round_trip_p2.rs`, `post_format_round_trip_p1.rs`, `model_units_survive_reload_g_unitsreload.rs`, `save_temp_path_unique_f124.rs`, `multitool_plan_roundtrip_o1b.rs`, `step_project_load.rs`; unit test `project_file.rs:1165` freezes the `type` key shape and names the viz twin.

## Drift / differences (core is authoritative — it is the only writer)
1. **Id types**: core `Option<usize>` vs viz `Option<ToolId|ModelId|SetupId|FixtureId|KeepOutId>`. Those newtypes derive plain `Serialize` (`stock_config.rs:8-20`, `tool_config.rs:5`), so TOML is `id = 3` on both sides — **wire-identical**. Only `ToolpathId` is `#[serde(transparent)]` (`ids.rs:22-24`). `skip_serializing_if` differs but core always writes `Some`.
2. **Setup-level alignment pins — silent data loss.** Viz has `ProjectSetupSection::alignment_pins` (`io/project.rs:317`) and migrates format ≤2 pins to stock (`745-764`). Core's `ProjectSetupSection` (`project_file.rs:288-320`) has **no such field**, and unknown keys are ignored, so core's parse succeeds and drops the pins before the fallback could run.
3. **`validate_looks_like_cam_project` bypass.** Core refuses non-CAM TOML (`project_file.rs:813-838`, `SessionError::NotACamProject`). The fallback at `controller/io.rs:526` catches *every* error, and viz's `ProjectFile` defaults every field, so a refused file re-opens as an empty project with `Ok(())`.
4. **Stock/post schema strictness inverted.** Viz's `[job.stock]` is core's runtime `StockConfig` (`stock_config.rs:434-468`) with no field defaults; core's `ProjectStockConfig` defaults all (`project_file.rs:71-96`). Viz `[job.post].format` is the typed `PostFormat` (aliases at `gcode/mod.rs:942-955`); core's is a bare `String`. So viz rejects files core accepts, and core persists typo'd post tokens silently (P-1's subject).
5. **Fields only viz writes**: `visible`, `locked`, `auto_regen` (`io/project.rs:229-232,268,587-602`). Core's toolpath section has none — the live save path never persists them.
6. **Fields only core writes**: `boundary_inherit` (viz reads it `skip_serializing`, `io/project.rs:248-250`), `pre_gcode`/`post_gcode` as `Option` (omitted when `None`) vs viz's always-written `String`.
7. **Load behaviour core has and viz lacks**: F-026 `auto_from_model` bbox refit (`project_file.rs:989-1019`); `resolve_model_path` storing the absolute path (G-MODELRELINK F4.3, `project_file.rs:583-590`, `save.rs:67-77`) — viz resolves for the read but infers `kind` from the **raw** string (`io/project.rs:1016`).
8. **Load behaviour viz has and core lacks**: typed `ProjectLoadWarning` list (`io/project.rs:28-117`) including `UnknownToolType` and `FaceSelectionStale` (`1220-1238`); core only `tracing::warn!`s (`project_file.rs:502-510`) and re-derives coarser warnings in `controller/io.rs:442-482`. Also the whole pre-v1 legacy format (`LegacyProjectFile`, `io/project.rs:382-448`) — **the one format core cannot read.** Caveat: a legacy file that omits `post`/`machine` strings still parses in core and mis-loads before the fallback is reached.
9. **In-core pair**: `io::load_model_file` (`io.rs:25-131`) vs `project_file::load_model_geometry` (`project_file.rs:592-700`). Comments record four fixed divergences (G-UNITSRELOAD, G-STEPUNITS, BREP downgrade, DXF scaling). Still divergent: `load_model_file` sets `winding_report` for STL (`io.rs:41,53`); the project door always writes `None`.

## Proposed cleanup
- **Home**: `rs_cam_core::session::project_file` owns the schema. Delete the viz `ProjectFile` family; keep a small `rs_cam_viz::io::project_legacy` for `LegacyProjectFile` only, converting to core's `ProjectFile` and handing it to `ProjectSession::from_project_file`.
- **Core API gaps to fill first** (all additive): (a) `pub` the model-kind helper — drop `project_file::infer_model_kind` and `controller/io.rs::kind_from_extension` in favour of `io::infer_kind_from_path`; (b) a `Vec<ProjectLoadWarning>`-style typed warning channel on `from_project_file`, so viz keeps its toasts; (c) `alignment_pins: Vec<ProjectPinSection>` on core's `ProjectSetupSection` with the ≤v2 → stock migration; (d) optional `visible`/`locked`/`auto_regen` if the GUI wants them persisted.
- **Sequencing** (drift fixes first, they are live bugs): 1. narrow the `controller/io.rs:526` fallback so `NotACamProject` propagates instead of falling through. 2. port the setup-pin migration into core. 3. land (a)–(b). 4. delete viz `save_project` and `load_typed_project` + their struct family. 5. legacy loader converts to core's `ProjectFile`. 6. collapse the two in-core model doors, keeping `winding_report`.
- **Risk**: step 1 low; steps 2–3 low (additive serde with `default` + `skip_serializing_if`); step 4 medium (deletes the viz round-trip tests' subject); step 5 medium; step 6 medium-high — it sits under G-UNITSRELOAD/G-STEPUNITS.
- **Smallest proof test**: a new core sentry `project_loader_parity_i01.rs` — write one project TOML that exercises pins, datum, a `grblhal` post, an unknown tool type and a relative model path; assert `ProjectSession::load` and the viz fallback produce equal `stock.alignment_pins`, `datum`, `post.format`, tool type and resolved model path. It fails today on pins (item 2). Pair it with a viz test that a non-CAM TOML now returns `Err` from `open_job_from_path` (item 3).
- **Migration concerns**: no format change is required — core already reads everything it writes, and files core writes load in viz today. The only compatibility gain is core learning setup-level `alignment_pins`; the only loss risk is deleting the viz writer, which nothing in production calls.
- **Workspace rules touched**: viz `io/project.rs` is the "parallel one-off flow" the root `CLAUDE.md` forbids, and `build_session_from_legacy_job` (`controller/io.rs:626`) is a second session-construction path beside `apply(Command)` (it does route through `ProjectSessionBuilder` + two commands, so it is compliant in letter).
