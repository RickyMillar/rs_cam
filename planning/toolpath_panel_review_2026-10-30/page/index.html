Toolpath Panel Review

I drove the GUI through MCP with two projects: a STEP solid (Pocket, Profile, Drill, Face) and the rivmap100 mesh (Face, 3D Rough, Scallop, Project Curve). I followed one Pocket from "Add" to "Done" and took a shot at each step. Then I read the code that draws each block.

Verdict. The panel does not have a rendering problem. It has a structure problem and a message problem. It shows the same fact in up to four places, shows status words that do not follow the real state, and uses developer prose as operator text. HTML would carry all of this over unchanged. Keep egui, and build a small component set.

Today

Design rules

A design system exists. The premium programme (UP1–UP8, 2026-09-13/14) built the tokens (ui/tokens.rs), the type scale and the component set to planning/ui_premium_2026-09-13/DESIGN_SPEC.md. Its own close-out says it "polished the clutter": its rule 1 forbade removing or moving a control. The declutter phase (2026-09-14), the UI-02 grid kit (2026-09-18) and the text audit (2026-10-02) followed. Since 2026-10-13, 110 commits touched ui/properties/ (geometry selection, reach map, floors), and each new feature added rows and text. The tokens survived; the placement rules did not, because nothing enforces them. The rules below add placement to the existing tokens. The mock-up obeys each one.

1 · One fact, one home

A value, a state or a problem shows in one place. A second mention is deleted, not made smaller.

2 · The header answers two questions

What is this (name, tool)? Can it run (one status word, one button)? Nothing else goes above the tabs.

3 · A problem sits on its field

A missing or wrong value turns its own field red. Only a problem with no field gets an issue row: one line, one Fix, at most three.

4 · One row shape

Label column LABEL_COL_WIDTH, muted. The control fills the rest at ROW_ACTION height. The unit sits inside the control, right side, faint. A read-only value uses the same row with no box. One label width, not three.

5 · Colour means state

Red blocks. Amber asks you to check. Green is done. Blue is the thing you can click. All other text is neutral.

6 · Three text sizes

15 px name, 13 px values, 12 px labels and meta. Sentence case. No category prefixes. 60 characters or fewer; the derivation goes on hover.

7 · Space groups, lines separate tabs

Sections are 14 px apart with a small caps label. The only rule line is under the tabs.

8 · A suggestion is a value with a mark

A suggested value fills its field with ⚡. A suggestion that differs from a typed value is a small ⚡ button beside it. No separate recommendation table on the face.

DANGER · blocks CAUTION · check OK · done ACCENT · action / selected existing tokens: ACCENT · OK · CAUTION · DANGER · SPACE_1–7 · ROW_ACTION · LABEL_COL_WIDTH the swatches above are the tokens.rs values

How it stays fixed

Type. Core Diagnostic gets an owner (field id, op, project, view) and two texts: face (60 characters or fewer, plain words) and detail (the derivation; MCP returns both). The viz crate draws diagnostics through one function that reads the owner. A panel cannot call ui.label with diagnostic text, because the text is not a String it can reach.

Sentry. Render each tab in each bad state (no tool, no feeds, wrong tool, reach on, refused). Assert that each diagnostic id paints at most once on screen and that no face is longer than 60 characters. This replaces the "+3 lines" cap.

Rewrite pass. Each message source in the core diagnostic adapters and the viz crate gets a short face. Examples: "Long tool: stickout 37.0 mm is 6.2 x D … load target x0.75 (repo rule, unsourced). The feed does not take it." becomes "Long tool: load target ×0.75". "the grid over-states gaps by up to its floor (1.062 mm), so the true unreachable share is AT OR BELOW 0.0 %…" becomes the legend hover "Grid accuracy ±1.06 mm".

Proposals

egui or HTML?

The tags answer this. Twelve findings need only the components that exist today. Two need a new egui component: one property row with one label width, and a tab strip that does not wrap. No finding needs a toolkit change.

egui costs more than CSS in two places: text reflow and responsive layout. The clip "Through cut of a 25 mm bc" and the two-row tab strip show this. app.rs:170-176 records that wrap_mode = Wrap was reverted because it broke grid labels mid-word. These items cost real work, but they do not block.

The 2026-09-13 ruling stands: egui stays. The premium programme then built the tokens and the component set, so the parts exist. What is missing is enforcement: a raw ui.label or ui.horizontal row still compiles beside the kit, and each new feature since 2026-10-13 used that door. Build P9 and P6 first, so the property row and the one diagnostic render path are the only doors, and the compiler holds the grid and the placement.

Rulings needed

R1
Feeds seed on empty (P4). You asked for the suggestion to be the default. Today three rulings keep the fields empty: F.5 "the calculator never writes", no underived defaults (2026-10-23), and no background field locking. A Suggest value is derived, so the second ruling allows it. The proposal: on op add and on tool change, write Suggest into empty fields only, mark them "suggested", never overwrite a typed value, never lock.
R2
Op-aware tabs (P5). The tool moves into the header. The proposed tabs are Geometry (selection, floor, boundary), Passes, Feeds, Heights and Linking (entry, links, arc fit, dogbone where it applies). A tab with no control for the op is not drawn. The panel CLAUDE.md pins the current tab order (sentry _d7), so this is a ruled break.
R3
Reach map leaves the panel (P7). The dock toggle and the legend own the reach map. The panel keeps one line with a Show link on the Geometry tab of a finishing op. The grid-floor and over-statement notes move to the legend hover; MCP keeps the full text.
