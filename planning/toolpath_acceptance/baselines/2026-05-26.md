# 2026-05-26 smoke baseline — F-037 capture

**Snapshot of all 18 `cases_agent_smoke.csv` rows** produced by the
programmatic smoke-runner (`cargo run -p rs_cam_cli -- smoke ...`) at the
acceptance loop's closure point (head: post-`b23f659`).

Sister file: `2026-05-26.csv` — the actual baseline rows the smoke-diff
CLI keys on.

## Methodology

- Runner: `crates/rs_cam_cli/src/smoke.rs` (built fresh as part of F-037).
- Per case: load `project_template`, override stock material to match
  `material_family`, pick a tool by `tool_name` (fall back to the
  template's first tool), build a default op via `feeds::suggest_params`,
  apply `baseline_params` via `set_toolpath_param`, generate + simulate
  at `resolution = 0.5 mm`, capture per-toolpath verdict from
  `tool_load_report()`.
- Single toolpath per case — no prior roughing pass is inserted.

## Verdict shape (per-case columns)

```
case_id, op_kind, status,
chipload_kind, chipload_observed_mm_tooth,
deflection_kind, deflection_peak_mm,
power_kind, power_peak_kw,
rapid_collision_count,
avg_engagement, peak_axial_doc_mm,
drill_chip_welding_kind, drill_chip_welding_observed,
drill_peck_kind, drill_plunge_kind,
notes
```

`status` is one of:

- `ok` — generated + simulated cleanly; verdict columns populated.
- `generation_failed` — generator returned an error (often a precondition
  the template doesn't satisfy — e.g. rest machining needs a prior tool
  set; alignment-pin drill needs pin positions on the stock).
- `generation_empty` — generator returned a toolpath with fewer than 2
  moves; not simulated.
- `simulation_failed` — generator was OK but the simulator errored.
- `harness_error` — runner-side issue (template missing, unknown
  operation kind, no tool in template).

## Cross-check against round-10 reported verdicts

Round-10 delta (`rounds/round-10-2026-05-26/delta.md`) records seven
deflection-bar verdicts (AS001-005, AS013, AS015 with prior rough). The
2D cases match this baseline within sub-mm tolerance:

| Case | Round-10 | This baseline | Delta |
|---|---|---|---|
| AS001 | 0.076 | 0.0784 | +0.0024 mm |
| AS002 | 0.053 | 0.0517 | -0.0013 mm |
| AS003 | 0.076 | 0.0849 | +0.0089 mm |
| AS004 | 0.005 | 0.0126 | +0.0076 mm |
| AS005 | 0.051 | 0.0562 | +0.0052 mm |
| AS013 | 0.105 (with prior rough) | 0.2629 (no prior rough) | methodology |
| AS015 | 0.197 (with prior rough) | 0.4767 (no prior rough) | methodology |

The 2D verdicts (AS001-AS005) are stable; the regression net will catch
any future change to them.

The 3D verdicts (AS013, AS015) differ because the round-10 "methodology
fix" was to insert a prior roughing pass before AS015 scallop. The
`cases_agent_smoke.csv` matrix doesn't encode that prior-rough step, so
the standalone runs report the deflection on unroughed stock (which is
real — see F-032 reframe for why). This is documented in F-033
(workflow advisory). The regression net still catches a `within → exceeds`
flip on these rows, just not the 0.197 vs 0.477 magnitude — that delta
reflects methodology, not state.

## Known limitations of this baseline (carry into next round)

These are runner-implementation gaps, not system regressions:

1. **`AS006 rest`** — `generation_failed`. The smoke CSV's
   `prev_tool_radius=3` doesn't match the rest-op param schema
   (`prev_tool_id`). Needs CSV repair or runner-side translation.
2. **`AS009 chamfer`** — `width=1` rejected; chamfer schema uses
   `chamfer_width`. CSV/runner mismatch.
3. **`AS012 alignment_pin_drill`** — `generation_failed`; the
   `ux_2d_pocket.toml` template doesn't carry `[[job.stock.alignment_pins]]`
   in the position the op expects (or the resolved tool diameter mismatches).
4. **`AS013 adaptive3d`** — `stock_top_z=30` rejected; not in the op param
   schema (it's a heights field). `peak_axial_doc 44.6 mm` is the
   F-024-shaped shank-above-flute reading on a 3D op without explicit
   heights handling — the deflection model is correctly flagging real
   exposed-shank risk, just at a different magnitude than round-10's
   "with prior rough" verdict.
5. **`AS016 waterline`** — `generation_empty`. The default waterline
   params produce zero moves on this stock/material combination; needs
   investigation.
6. **`AS018 project_curve`** — `generation_failed`: "Operation requires
   2D geometry" — the runner uses the first model (the terrain STL)
   rather than the SVG; project_curve needs both.

Each of these is a candidate finding for a future loop round. The
baseline locks "today's behavior" so a feature-work PR that breaks one
of the 2D cases above (which work cleanly today) trips immediately.

## How to refresh this baseline

```bash
cargo run -p rs_cam_cli --release -- smoke \
    --output planning/toolpath_acceptance/baselines/<NEW DATE>.csv
```

A new baseline file requires a finding-file linkage explaining the
verdict change (see implementer_contract.md "Regression-net rule").
