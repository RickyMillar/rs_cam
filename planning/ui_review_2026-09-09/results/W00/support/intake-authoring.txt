# R01+R03 Supporting Investigator Report — GUI Path & Defaults (expert code walkthrough)

**Scope:** Source-backed intake → stock/setup → tool → first pocket/profile authoring. Checkout `ef91cb03`; live binary `8a4df241-dirty` → **CODE ≠ live parity**. All findings are CODE-evidence; live confirmation required.

## (1) Precise human UI path / defaults map

**Startup / getting-started (`properties/mod.rs:217-243`).** When `Selection::None` AND no models AND no toolpaths anywhere, the Properties panel shows a hard-coded "Getting started:" list: 1. Import a model (File > Import); 2. Configure stock dimensions; 3. Add a cutting tool; 4. Create a toolpath; 5. Generate and export G-code. Otherwise (models present but nothing selected) it shows italic "Select an item in the project tree." There is no separate welcome/empty-state screen; this is the only onboarding wording.

**Import routes (`menu_bar.rs:37-84`).** File menu has separate `Import STL/SVG/DXF/STEP…` buttons each opening a native `rfd` file dialog, plus `Open Job… Ctrl+O` and `Save Job Ctrl+S`. Open Job is distinct from import — it loads a whole `.job`, not an appended model. Import always *adds* a model to the current session and auto-selects it (`Selection::Model`).

**Import → stock auto-sizing (`controller/io.rs:17-67`).**
- `import_stl_path` (18-33): imports, and **if `auto_from_model`** calls `stock.update_from_bbox(&mesh.bbox)`.
- `import_step_path` (54-67): same — updates stock from mesh bbox when `auto_from_model`.
- `import_svg_path` (34-43): imports, sets selection, marks edited. **No `update_from_bbox` call at all** — stock is never adjusted, regardless of `auto_from_model`.
- `import_dxf_path` (44-53): identical — **no stock update**.

**Stock defaults (`compute/stock_config.rs:475-491`).** `StockConfig::default()`: x=100, y=100, z=25, origin 0, **`auto_from_model=true`**, padding=5.0. `update_from_bbox` (505-532) handles both 3D (Z follows bbox) and **2D** (preserves `self.z`, shifts `origin_z = bbox.min.z − self.z` so stock top sits at the SVG plane). So the 2D-Z-frame logic *exists* and is correct — it is simply **never invoked from the SVG/DXF import path**.

**Units/dimensions visibility (`properties/mod.rs:763-893`).** The "Dimensions (after scaling)" block (X/Y/Z with mm ranges) **is gated on `if let Some(mesh) = &model.mesh`**. SVG/DXF produce `polygons` only (no mesh), so **a freshly imported SVG shows `Type: Svg`, `Path: …`, then jumps straight to the collapsed "Details" disclosure** — no dimensions, no size hint, no winding warning. The "Units / Scale" ComboBox + Custom scale (840-893) are also inside the `mesh` block, so **SVG/DXF models expose no units selector or custom scale in the GUI**. `RescaleModel` handler (`io.rs:70-115`) early-returns `Ok(None)` for `ModelKind::Step` (75-77) — STEP units changes are silently no-ops in CODE.

**Add operation / no-tool behaviour (`toolpath_panel.rs:649-710`, `toolpath.rs:12-177`).** The Setup panel's "+ Add" menu (`add_toolpath_menu`) groups ops under "2.5D (from SVG)" and "3D (from STL)". `add_op_menu_item` checks `GeometryRequirement` against `has_mesh`/`has_polygons` and **disables** ops whose geometry is absent, with `on_disabled_hover_text` giving a reason (e.g. "Requires 2D geometry (SVG/DXF)"). Clicking an available op pushes `Select(Setup)` then `AddToolpath(op)`.

`handle_add_toolpath` (`toolpath.rs:12`):
- **Target setup:** resolves from current selection (Toolpath→its setup, Setup/Fixture/KeepOut→that setup); **else defaults to setup index 0** (`.or(Some(0))`, line 31).
- **No tools:** `tools().first()` is None → warns "Cannot add toolpath: no tools defined" and pushes a Warning notification; returns without adding. This is the **no-tool refusal** — it is distinct from a wrong-tool default.
- **First tool = `tools().first()`** (line 35), NOT the selected tool. The currently selected `Selection::Tool` is ignored.
- **First model = `models().first()`** (line 106), NOT the selected model.
- **Suggest refusal:** `suggest_params` Err → "Cannot add toolpath: {e}" Warning, returns (e.g. flat endmill on Scallop). This is a tool×op compatibility gate at add time.
- **Stock-aware depth defaults** via `apply_stock_defaults` (`suggest.rs:1375-1401`): Profile depth = `stock_z`; Drill depth = `stock_z`; **Pocket depth = `(stock_z*0.5).min(5.0)`**; Adaptive = `stock_z*0.5`; Face = `padding.max(1.0)`; DropCutter `min_z = stock_bottom_z`. `stock_z` comes from `StockContext::from_stock_bbox(stock_bbox, padding)` — the **stock** bbox, not the model.

**Pocket/Profile forms (`operations/boundary_2d.rs`).** Pocket (62-119): Pattern (Contour/Zigzag), Stepover pill, **Depth** (`0.1..=100.0`, step 0.1, suffix " mm"), Depth/Pass pill, Climb checkbox, optional Angle (Zigzag), Finishing Passes (0..=10). Profile (123-196): Side (Outside/Inside), Depth, Depth/Pass, Climb, Compensation (In Computer/In Control), then a collapsible "Tabs" (Count/Width/Height + diagram), then Finishing Passes. **No "target" / "contour" label exists in these forms** — "Contour" is a *pattern* enum value for Pocket, not a target selector. Depth here is total cut depth (positive mm); the Heights tab (separate) controls Z planes.

**Generation validation / error visibility (`properties/mod.rs:3617-3682`).** Generate button is `add_enabled(can_generate, …)` where `can_generate = !tools.is_empty() && validation_errors.is_empty()`. Status label: Pending→"Ready", Computing→"Computing…", Done→green "Done", AwaitingPriorStock→amber "Waiting on upstream stock" (hover names blocker), Disabled→grey, Error→red "Error: {e}". Validation errors render as small orange labels below the button. `validate_toolpath` (`operations/mod.rs:1840+`) checks: "No tool selected", stepover ≥ tool diameter, VCarve/Inlay/Chamfer require V-Bit, Rest requires prior tool + same-model earlier enabled op, and model geometry presence (2D/3D/both). "Ready" is shown when `ComputeStatus::effective` is Pending — i.e. **"Ready" means "not yet computed / can generate", not "verified/safe"**.

## (2) Candidate risks (≤4), with verified file:line refs

### Risk A — SVG/DXF import never auto-sizes stock despite `auto_from_model=true` default
- **Refs:** `controller/io.rs:34-43` (svg), `44-53` (dxf) — no `update_from_bbox`; contrast `18-33` (stl), `54-67` (step). `compute/stock_config.rs:484` (`auto_from_model=true` default), `505-532` (`update_from_bbox` exists incl. 2D-Z path).
- **Starting state:** Blank job, `auto_from_model=true`, import raw F1 SVG.
- **Expected (CODE):** Stock XY/Z should follow the 2D frame logic (XY = bbox+2·padding; Z preserved, origin_z shifted). **Actual (CODE):** stock stays at the 100×100×25 default; only STL/STEP trigger `update_from_bbox`. Getting-started step 2 ("Configure stock dimensions") is therefore *mandatory* for SVG/DXF but presented as if auto-sized.
- **Confidence:** confirmed CODE gap. Live parity unverified (dirty build).
- **Live probe:** Import a 200mm-wide SVG into a blank job; read stock X in the Stock panel — expect 100.0 (default) if the gap is live, ~210 if fixed. Then import an STL of known width and confirm it *does* auto-size.

### Risk B — SVG/DXF models show no dimensions, units selector, or scale control
- **Refs:** `properties/mod.rs:765-893` (entire Dimensions + Units/Scale block is inside `if let Some(mesh) = &model.mesh`); `io/import.rs:36-39` (SVG → polygons only).
- **Starting state:** SVG imported, select it in the tree.
- **Expected:** dimensions in mm, units combo, custom scale (R01 task 5 asks to "correct a known scale mismatch" and "inspect dimensions" for drawings). **Actual (CODE):** only `Type:`/`Path:` then a collapsed "Details" disclosure; no dimensions, no units combo, no custom scale. A user cannot rescale an SVG that came in wrong without re-importing.
- **Confidence:** confirmed CODE. Note `RescaleModel` would handle polygons if the UI emitted it — the gate is purely presentational.
- **Live probe:** Import F1 SVG, select it, screenshot the Properties panel — confirm absence of "Dimensions (after scaling)" and "Units / Scale". Compare with an STL import.

### Risk C — First tool/model default ignores the user's current selection
- **Refs:** `controller/events/toolpath.rs:35` (`tools().first()`), `106` (`models().first()`); `toolpath_panel.rs:696-704` (emits `Select(Setup)` then `AddToolpath`).
- **Starting state:** Multiple tools/models imported; user selects Tool #2 and Model #3, then clicks + Add → Pocket on Setup 1.
- **Expected:** the new op binds the selected tool/model, or at least the tool currently selected. **Actual (CODE):** always binds `tools().first()` and `models().first()`, regardless of `Selection::Tool`/`Selection::Model`. The pre-emit `Select(Setup(setup_id))` only fixes the *target setup*, not tool/model.
- **Confidence:** confirmed CODE. Live probe: in a session with ≥2 tools, select the second, add a Pocket, inspect the new toolpath's `tool_id` in the properties header — expect tool #1.

### Risk D — STEP rescale is a silent no-op while the UI still offers the units combo
- **Refs:** `controller/io.rs:75-77` (`if model.kind == Some(ModelKind::Step) { return Ok(None); }`); `properties/mod.rs:840-893` (Units/Scale combo labelled "all formats including STEP" per comment line 840).
- **Starting state:** Import F4 STEP; change units in the combo.
- **Expected:** model re-imported at new units / dimensions update. **Actual (CODE):** `RescaleModel` returns `Ok(None)` immediately for STEP; the `AppEvent::RescaleModel` fires, the handler no-ops, and the UI likely shows no change and no error.
- **Confidence:** confirmed CODE no-op; live error visibility unverified. **Distinguish from Risk B:** B is *no control shown at all* (SVG); D is *control shown but silently inert* (STEP).
- **Live probe:** Import a STEP, switch the units combo to inches, confirm whether dimensions change or a notification/error appears.

## (4) How MCP add/import can mask or differ from GUI authoring

- **MCP `add_toolpath` with explicit IDs** bypasses `handle_add_toolpath`'s `tools().first()`/`models().first()` defaults (Risk C). An MCP-driven add that specifies `tool_id`/`model_id` will *look* correct while the GUI path silently picks #1 — so an MCP-verified authoring flow does **not** reproduce the GUI first-use default mismatch. R03 task 3 ("a backend add with explicit IDs is not a substitute for this test") is directly supported by `toolpath.rs:35,106`.
- **MCP import/stock:** if MCP mutates stock directly or calls a path that *does* invoke `update_from_bbox` for SVG (or sets stock from a model bbox the GUI path skips), MCP-STATE will show a sized stock while the live GUI stays at 100×100×25 (Risk A). MCP-VIEW screenshots taken after MCP mutation would then *not* reflect what a GUI-only user sees.
- **MCP Suggest** uses the same `suggest_params` engine, so a refusal observed via MCP *does* mirror the GUI add-time refusal — but MCP cannot confirm the **notification** is visible to a GUI user (`toolpath.rs:46,99` push notifications are GUI-only surface).
- **Rescale via MCP** vs GUI: an MCP `rescale_model` on a STEP returns the same `Ok(None)` (Risk D), so MCP parity holds there — but MCP cannot expose whether the GUI *shows* an error or silently refreshes the (unchanged) combo.
- **Validation parity:** `validate_toolpath` is shared by GUI and the toolpath list ("A/M11: same resolver the toolpath list and MCP use", `mod.rs:3632` comment) — so validation *content* is parity; only its **visual presentation** (orange labels, disabled Generate) is GUI-specific and needs DESKTOP/MCP-VIEW confirmation.

**Cross-handoff:** R02 should receive that SVG/DXF stock is *not* auto-sized (Risk A) before physical-setup review. R04 should receive that Pocket/Profile *depth* defaults derive from **stock** `stock_z`, which is stale/default for SVG jobs until Risk A is addressed — so suggested depths on an SVG job are computed against 25 mm default stock, not the drawing's frame.
