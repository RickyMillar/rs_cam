## (2) Three concrete sequences

**A. Find a priority and locate it.** User is in Simulation with results. The inspector header (`sim_diagnostics.rs:139-169`) shows the verdict banner (collision/air>40%/OK). Below it, the **Project** section's "Must address" grid (`:446-469`) lists issue kinds with bare counts: e.g. "Annotation 15", "Hotspot 3". Clicking a row does nothing — the grid is label+count only, no click handler (`:460-466`). To actually locate, the user must open the **"Top hotspots"** collapsible (`:476-511`) and click a `selectable_label` row → sets `focused_hotspot` + `SimJumpToMove(global_start)` (`:501-504`). Or use the timeline verdict-HUD pills (`sim_timeline.rs:181-221`): `✗ exceeds` and `collisions` pills are `actionable()` and seek to the first offending move (`:200,216`). The focused issue card (`sim_diagnostics.rs:289-326`) offers `◀ Prev`/`Next ▶`/`Jump`/`Optimize this op` — but you can only *enter* that card by already being focused on an issue (via timeline marker click, `sim_timeline.rs:2208-2214`). **Gap:** annotations and the highest-priority current triage action are not surfaced as actionable; the green "✓ No collisions, air under threshold" banner can coexist with a critical plunge-rate action (W01 UX-R06-001).

**B. Leave to correct inputs and return.** From a focused issue card, the only edit affordance is `Optimize this op` → `OpenOptimizeModal(toolpath_id)` (`sim_diagnostics.rs:323,266`). There is **no "return to authoring" / "edit this op's parameters" button** in the Simulation workspace. To manually correct feed/stepover the user must: switch workspace (menu/shortcut) → find the op in `toolpath_panel.rs` → edit → the op goes `PEND`/stale → `Generate` → switch back to Simulation → see stale banner → `Re-run`. The closed loop is only through Optimize: `ApplyOptimizeCandidate` → auto-regen → auto-resim (`mod.rs:630`, `compute.rs:979-981`) → freshness returns to live, toast "Applied… regenerating and verifying…" (`mod.rs:633`). For non-Optimize corrections the loop is open and relies on the user remembering to re-run.

**C. Interrupted / failed / waiting generation.** A failed generation sets `ComputeStatus::Error(msg)` via `fail_toolpath_submit` (`compute.rs:77-87`) or the drain `Err(Message)` arm (`compute.rs:1054-1063`); the `toolpath_panel.rs:408` "ERR" chip shows the message on hover, and a `push_notification(…, Error)` toast fires (`compute.rs:684,729`). **No in-panel error list** — recovery means reading the toast or hovering the chip. ## (3) Structural IA problems remaining after correctness fixes

1. **No actionable priority in the primary overview.** The verdict banner is a 3-state collision/air/OK summary (`sim_diagnostics.rs:139-169`); the "Must address" grid is counts without subjects, scope, or jump (`:446-469`). The single most important current triage action (e.g. a critical plunge-rate load, a named annotation) is not visible as a *named, located, actionable* item at the top. Even with all gates correct, a user cannot answer "what must I address first?" without hunting into collapsed sections, hovers, or the timeline markers. (W01 UX-R06-001, W02 UX-R06-003.)

2. **The issue→edit loop is open for manual corrections.** Simulation offers `Jump` (playhead) and `Optimize this op` (modal), but **no "edit this operation's parameters" route**. The only closed verify loop is Optimize-Apply-auto-resim. A user who decides a feed or stepover is wrong must mentally context-switch workspaces, locate the op, edit, regenerate, return, and re-run — with staleness banners as the only signpost. The `handle_inspect_toolpath_in_simulation` path (`toolpath.rs:426-447`) goes Toolpaths→Simulation, never the reverse.

3. **Scope is three independent selection sources with no shared model.** "Now playing" = `current_boundary()` from `playback.current_move` (`simulation.rs:1053-1063`). "Focused toolpath" = `focused_toolpath()` (`:1066`). "Selected span" = `span_scope.span_id` lock or `playhead_span_id` fallback (`sim_diagnostics.rs:1325-1344`). "Pinned semantic item" = `pinned_semantic_item` (`:1380`). These are distinct datums; the inspector title says "Now playing: X" while the Selected section can show a *different* span from a *different* toolpath than the playhead. There is no single "you are looking at: op X / move Y / span Z" statement reconciling them. The Project/Toolpath/Span tiering helps, but each tier draws from a different selection well.

4. **Notifications are ephemeral and the only error log.** Toasts GC and vanish (`app.rs:894`); the `ERR` chip holds one message on hover; there is no persistent issues/notifications panel. A user who looks away during a multi-op `Generate All` loses the "cancelled", "prior stock waiting", or "resolution coarsened" messages. The status bar shows lane state only while non-idle. Recovery from a missed toast requires re-reading the chip hover or reproducing the failure.

## (4) Proposed feedback hierarchy + Simulation wireframe

**Hierarchy (top→bottom), each level names scope + freshness + a next action:**

1. **One primary action line** — the highest-priority *current* triage item: "⚠ Op 2 'rough': plunge load 2.5× over rate at move 312 — [Jump] [Optimize] [Edit op]". Replaces the bare verdict banner as the glance. Verdict (collisions/air) demoted to a compact pill row beside it.
2. **Freshness strip** — always present: "✓ live" or "⚠ stale — last run 14:02, params changed since → [Re-run]". Governs everything below; when stale, levels 3-5 dim and carry "last run" tagging (preserve current `FreshnessGate` behaviour).
3. **Project rollup** — within/exceeding/unmodeled load (denominators), collision count, cycle time+basis, measurability strip. Pills are navigation (`✗ exceeds`→first exceedance). Keep the existing `summary()` producer so rollups cannot diverge.
4. **Now-playing op** — name, tool, per-op load badges (chipload/power/L/D as **separate** badges, never one fake score), `Optimize this op` / `Jump to start` / `Edit this op`.
5. **Selected span / move** — span label + lock glyph, in-span findings list, generator-item + generation-trace drill-downs. Lock explicit so "selected" vs "now-playing" divergence is a user choice, not a mystery.

## (5) Alternatives, expert depth to keep, validation tasks, untraced assumptions

**Alternatives:** (a) A persistent notifications/issues drawer instead of only toasts — trades screen space for recoverability; keep toasts for transient lane events. (b) A single "issue list" panel replacing the Must-address grid + Top-hotspots list — risks re-collapsing distinct kinds (collision vs annotation vs hotspot) into one fake priority; prefer the L1 primary + scoped lists. (c) Auto-resim on every edit (like Optimize-Apply) — rejected: wastes wall-clock and hides the "what changed" reasoning; keep manual Re-run but make the stale→re-run path one click from where stale data shows (already true in timeline/op-list).

**Expert depth to preserve:** separate chipload/power/L/D badges (`sim_diagnostics.rs:611-660`) — never collapse to one score; the `∅` vacuous badge (`:627-634`) and `≈` approximate-confidence markers; the measurability strip that abstains rather than judges (`:474-514`); `Within` vs `Unmodeled` vs `∅` distinctness; per-op and per-span drill-downs (generator item, generation trace); the verdict-HUD pills as *navigation* not just labels (`sim_timeline.rs:181-221`); `AwaitingPriorStock` as a non-failure amber state with named blocker.

**Later validation tasks (HUMAN/DESKTOP needed):** (1) Does a user identify the L1 primary action without hover/source? (2) Can a novice find `Re-run` from the stale banner in the timeline vs the op-list? (3) Is the now-playing vs selected-span divergence noticed or confusing? (4) Toast discoverability during long Generate All. (5) `Edit op` round-trip time and "← back to issue" re-orientation.

**Untraced assumptions:** that a `CancelCompute`/`CancelToolpathGeneration` GUI button exists and is reachable (events traced, button not); that the `ERR` chip hover message is sufficient to recover without the toast; that `pending_apply_resim` auto-resim is always desired (it only fires when a baseline sim existed, `mod.rs:628`); that the three scope datums (now-playing/focused/selected) are intended to diverge rather than being a bug; that stale-signal timing across the four surfaces (header chip, op-list banner, timeline skin, readiness dim) is consistent — they all read `is_stale(edit_counter)` but render at different frame points. **Generated ≠ verified; empty/unknown/stale/Within remain distinct in the code; this proposal does not merge them.**
