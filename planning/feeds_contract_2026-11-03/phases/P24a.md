## 1. Survey: the tool-side carrier

- Candidate: `compute::tool_config::BitCutDirection` gains `Straight` (token `straight`, label
  "Straight"). The enum is the flute form of the tool: up, down, both (compression), none
  (straight). The four values exclude each other, so it is one fact.
- The helix has a second home today: `ToolConfig::helix_deg`, a public field (file key
  `helix_deg`, default 30, GUI row "Helix"). Product code reads the field directly, not through
  the cutter, at: `feeds/operating_point.rs:582`, `:599`, `:671`; `feeds/predict.rs:493`;
  `session/compute.rs:2306` (the modulation context); `session/save.rs:171`; and the cutter
  build.
- A clean single place exists, on the write side, not the read side. Rule: a straight tool has
  helix 0 in its record. The setter door (`ToolParamKey`, the GUI editor's write-back) writes
  `helix_deg = 0` with `cut_direction = Straight`; the loaders (project file, tool library) set
  helix 0 on a straight tool and file one load warning when the file states another helix
  (never a refusal); `ToolConfig::validate` holds the pair. Every reader of `helix_deg` then
  reads 0 with no change. The alternative, a read accessor, needs seven readers changed and a
  scan to keep them changed.
- The doors and the exhaustive matches that need the new variant:
  `tool_config.rs` (`BitCutDirection::ALL`, `label`), `feeds/series.rs::for_cut_direction`,
  `session/save.rs::cut_direction_to_key`, `session/project_file.rs::parse_cut_direction` (a
  token chain; an unknown token warns and takes up-cut today), `io/tool_library.rs` (serde
  snake_case), the GUI combo (`ui/properties/tool.rs:316`, iterates `ALL`), MCP `set_tool_param`
  and `add_tool` (the enum through the wire types), the CLI job file (serde).

Not a stop: the carrier has a clean single place.

## 3. The stop: a generic tool picks the straight rows

### 3.1 The rule in the code

`vendor_lookup::prefer_series`: the series decides only between rows that tie on material AND
size. Where no standard row prints the size of the straight row, the score decides, and the
score prefers the nearer diameter (`score_observation`: up to 200 points for the diameter).

### 3.3 What it means

- The wanaka 18 mm tool is `up_cut` in the project file. With the rows loaded, idx 0, 1, 11, 12
  and 14 (Face, 3D Rough) move from 0.1791 to 0.2204 with no edit of the file. The prediction
  "no wanaka value moves" does not hold, and every generic tool of 16 mm or more in hardwood
  reads a straight-bit chip.
- The operator ruling of 2026-10-31 reads: "a generic tool uses standard rows first and falls
  back to a specialty row only when no standard row exists". The code holds a narrower rule (a
  tie on material and size, lead ruling of the same day).

### 3.4 Options for the lead

1. **Series first, as the operator's sentence reads.** A row of another specialty series is a
   candidate for a tool only when no row of the tool's own series and no standard row is a
   candidate for the query (any size inside the size window). One rule for every series. Blast:
   every cell where a generic tool reads a specialty row at a size no standard row prints today
   (to measure on FM1 before code).
2. **A straight row serves only a straight tool.** A must-match filter for this one series: the
   edge form is not a preference, a spiral tool is not a straight tool. No existing cell moves.
   It is a special case of one series.
3. **Load no straight row until the rule is ruled.** The tool-side fact and the helix-0 force
   land alone; a straight tool reads the spiral rows, as today.

I recommend 2 for P24a (no existing value moves; the sentry "a spiral tool never takes a
straight row" then holds by construction), and 1 as its own phase with an FM1 measurement.
