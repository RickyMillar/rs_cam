### Root cause of defect 2 (Profile skips the axial-chip bound)

`feeds/plunge.rs::axial_chip_bound` gave the G6 axial-chip bound only to an op whose entry
contract is `StraightPlunge { feed: PlungeFeedRule::AxialChip }`. Only Project Curve has that
contract (`compute/catalog/registry.rs`, `compute/config.rs`). This was lead decision Q8a
(`PLAN.md`: "Project Curve only; widening it to every flat-end plunge with a G6 claim is a
separate decision after the FM1 diff"). The P20b brief widens it: every plunge that is not a
drill cycle takes the bound where a G6 claim covers the tool. Q8a is superseded.

For a 2F flat on the G6 side row, feed / Z = side chip x rpm = axial chip x rpm x Z, so the
bound binds only where the feed row prints a higher chip than the Spektra pocket row (a finish
or contour row), or where the plunge rule reads a feed above the chart chip.

### Design (written before the code)

One projection exists: `governing_max_rate` behind `effective_max_rate_mm_min` and `cruise_ceiling`.
P20c adds no second one.

1. `MachineKinematics::rate_bound_feed_mm_min(commanded, dir)` = `min(commanded,
   effective_max_rate_mm_min(dir))`. `machine::kinematics::cap_feeds_at_axis_rates(toolpath,
   kinematics)` walks every fed move with the direction the integrator reads (`move_directions`,
   the chord for an arc) and lowers its feed to that value. It only lowers. With no per-axis rates
   it changes nothing.
2. Write side (a), generation: `JobPhases::run_stages` calls it once, after
   `clip_and_split_entries` (the last stage that writes a feed, W12) and before the entry records.
   It covers W4-W12 and gap 1 (the dressup entry plunge, ramp and helix) at the true direction of
   each move. The dressup pipeline step is not used: W12 runs after the pipeline.
3. Write side (a), modulator: after the `feed_cap` step, the modulated feed is lowered to the
   rate bound (`BindingConstraint::KinematicReach`). It closes the floor defect of W13 for the
   rate. The floor above the ACCEL reach stays (the existing rule: the floor holds the chip).
4. Gate side (b): the modulation stamp (G3) writes the REACHED feed of the modulated toolpath
   (`predicted_feeds_for_toolpath` on the re-time clock) when the flag is on and the machine has
   kinematics; else the modulated commanded feed, as today.
5. The flag `use_predicted_feed_in_gates` becomes `true` at every product site (G2 list). Lead to
   ratify: it is the operator goal, and it moves gate verdicts on every machine with kinematics
   (the accel reach on short moves, F-035).
   Export consequence (from the code, not measured on wanaka): a lower graded chip can trip the
   chipload LOW side. That side is hard (it can refuse an export) only for a calibrated
   `ChipBoundsSource::VendorLut` band; a point row, an extrapolated row or a row with no `ae`
   calibration gives a burn advisory only (`ChipBoundsSource::low_side_is_advisory`,
   `tool_load/verdict.rs`). So the flip CAN block an export where a calibrated band's low side
   trips. The strategy advisor's candidate simulation (`simulate_candidate_isolated`) keeps the
   flag `false` (its doc: it scores candidates before modulation); not changed.
6. Both (a) and (b): (a) makes the IR and the G-code state what the machine runs; (b) grades the
   accel reach, which no command can state.

Compiler route: not taken. A `ReachableFeed` type inside `MoveType::{Linear, ArcCW, ArcCCW}` would
touch about 450 writer sites (W4). The one site in `run_stages` plus the sentry hold the rule;
recorded as open.

Out of scope (not changed): the G6 axial chip on an operator-typed plunge (W3; a chip limit, not
a machine limit, P20b binds Suggest values only); the drill gate and plunge-stress inputs (G4, G5
grade the config value; with the generation cap the emitted drill and plunge moves are capped, but
these two gates read the op config); W15.

### Design (written before the code)

- New `feeds/section.rs`: `EngagedSection` (no `Default`), the one input of the power model:
  - `Rectangle { ap, ae, d_eng, psi }`: a flat or bull side cut; an upper bound for a ball or a
    tapered ball (the crescent is inside the rectangle). Area `ap ae`; edge
    `F_edge ap pi d_eng n Z psi / 2pi`, the same arithmetic in the same order as before.
  - `VGroove { depth, half_angle, tip_diameter, width, diameter }`: a V-bit side cut. At the
    height `z` above the tip the cone radius is `r(z) = tip/2 + z tan a` (capped at `D/2`, the
    cutter's own width rule); the new width is `min(width, 2 r(z))` (two passes at one depth,
    `width` apart); the arc is `psi(z) = acos(1 - min(width, 2r)/r)`. Area = integral of the width
    over `z`; edge term = `F_edge Z n x integral of psi(z) r(z) ds`, `ds = dz / cos a` on the cone.
    Both integrals are closed forms (in `section.rs`). A slot (`width >= 2 r` at every height,
    no tip) gives the table's triangle: area `h^2 tan a`, edge `F_edge Z n pi R^2 / (2 sin a)`.
  - `AxialCircle { diameter }`: a straight plunge of a flat end mill. Area `pi D^2 / 4`; every
    flute cuts the whole turn along the radius `0..R`, so the edge term is
    `F_edge Z n x integral of 2 pi r dr = F_edge Z n pi D^2 / 4`. The chip is the axial chip
    `feed / (rpm Z)`.
- Every caller chooses: `EngagedSection::side_cut(hint, ..)` and `EngagedSection::axial_plunge(hint,
  D)` match `ToolGeometryHint` with no wildcard, so a new shape is a compile error. A plunge of a
  ball, bull, V-bit or tapered ball has no section (`axial_plunge` refuses): power `None`, the
  reason named, never 0.0.
- `Engagement` holds the section (built in `from_cut` / `from_sample` from the hint);
  `PowerModelInputs` holds the section in place of the four rectangle fields. The axial plunge
  has its own constructor `PowerModelInputs::axial_plunge`. Deleted: the two rectangle and
  half-rectangle copies `ToolGeometryHint::mrr_cross_section_mm2` and
  `MillingCutter::mrr_cross_section_mm2` (trait default, V-bit override, wrapper).
  `tool_load::load_fraction` reads `depth x width` (the old V factor 1/2 cancels in its ratio).
- P18 item 3b: `FeedsResult::power_kw: Option<f64>`; `None` = not modelled (no force line, depth
  after the simulation, a plunge with no section). The removal rate is the section area x feed.
- Drill power is advisory: Step 6 (the power ladder) does not run on an axial plunge, Suggest pass
  10 and the envelope do not act on it. `PowerFigure::section` names the section and its basis on

### Design (written before the code)

1. `machine/mod.rs`: `MachineProfile::op_cutting_ceiling(feed_max_rate) -> CuttingCeilingMmMin`
   = `cutting_ceiling().at_least(1.0).capped_at(feed_max_rate)`. It is THE cap of one op. The
   modulator (S11) and the advisor (S12) call it in place of their own copies.
2. `CuttingCeilingMmMin::steady_feed(op_feed) -> SteadyFeedMmMin` = `min(op_feed, ceiling)`,
   with `SteadyFeedLimit::{OpFeed, OpFeedCap, MachineCeiling(CuttingCeilingSource)}`. A tie is
   `OpFeed` (no cap binds). `MachineProfile::op_steady_feed(op_feed, feed_max_rate)` composes the
   two, so the gate path and the modulator path both pass through `op_cutting_ceiling`.
3. Gates: `ToolpathLoadContext::steady_feed: SteadyFeedMmMin` (and the same field on
   `LoadContextParts`), set in `load_context_parts` from `self.machine` and `tc.dressups`.
   `steady_state_samples_for_toolpath` takes it (S1, S2). `operation_feed_rate_mm_min` stays
   for S3. Test door: `SteadyFeedMmMin::op_feed_only(mm_min)` (the op feed binds).
4. Suggest and card: `power_at_shipped_point` takes `feed_max_rate`. It evaluates the figure at
   `machine.op_steady_feed(op feed, feed_max_rate)`. `PowerFigure` gains
   `steady_feed: Option<SteadyFeedMmMin>` (`Some` from the shipped-point door, `None` from
   `power_at_operating_point`, which reads the op feed as given) and `op_feed_mm_min`.
   `CutterOpProfile` keeps `context.dressups.feed_max_rate` (the existing Suggest context path,

5. Card: when the limit is not `OpFeed`, the Feed row carries a status chip (`cap 3000`) and

6. P20d hover: on `SectionKind::AxialCircle` the power hover labels `ap_mm` "advance per rev"
