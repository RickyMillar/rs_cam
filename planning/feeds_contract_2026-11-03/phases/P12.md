# P12: Hand-off for an independent review and number verification

Status: NOT STARTED (added by the operator, 2026-11-04) | Runs last, after every other phase

## Goal

The lead session builds the engine. A separate session then reviews it: it runs many variations of
toolpath, tool and cut, and checks that the numbers that come out agree with industry practice.
This phase writes everything that session needs, so that it starts with no context from this one.

Operator (2026-11-04): "You build the engine. But I will get another session to go through many
variations of toolpath, tool, cut. And check that the results that come out are in line with
industry thinking."

## Deliverables (all in `planning/feeds_contract_2026-11-03/handoff/`)

1. `WHAT_IS_DONE.md`: one section per phase (P0 to P11) and per ruling (Q1-Q10, D1-D12):
   - what changed, in the operator's terms, with the commit hashes;
   - the contract it holds (K1-K8) and its sentry;
   - what was NOT done, and each known red with its cause.
2. `MODELS.md`: every model that produces a number the operator sees (Suggest, the envelope, chip
   thinning, the engagement force, deflection, power, the rigidity caps, the K5 rules, the
   simulation measures). For each: the formula, its inputs, its source (file:line and a
   `CREDITS.md` row), each constant with `Cited` or `Unsourced`, and its known limits
   (`research_ae/`, `research_p11_step0/`).
3. `VERIFICATION_BRIEF.md`: the brief for the review session, ready to paste:
   - the matrix to run: tool kinds and sizes (flat, ball, bull, tapered, V; 1F/2F/3F; 1-25 mm),
     materials (soft and hard wood, MDF, plywood), ops (each family of the registry), cut
     geometry (slot, 50 %, 20 %, 5 % stepover; 0.5/1/2/3 x D depth), machines (the Shapeoko
     profile and one rigid profile);
   - how to run it: the CLI `suggest` command and the MCP tools (named), with the exact commands;
     where the outputs land;
   - the references to compare against: the vendor rows in
     `crates/rs_cam_core/data/vendor_lut/observations/`, the printed rules (Garr chip thinning,
     the vendor 1/2/3 x D table, the Amana/Onsrud/Freud charts), and named industry sources that
     the reviewer may add (each with a citation; no number from memory);
   - the pass rule, written before the run (as P11 step 0 did): which outputs must fall inside a
     printed band, which may differ and why;
   - the output: a report, an HTML page and an assert script per claim (operator preference),
     and a list of disagreements, each with the missing term it suggests.
4. `INDEX.md`: where each artefact is, and the order to read them.

## Rules

- The lead writes these from the repo, not from memory: each claim cites a file, a commit or a
  sentry.
- The brief states what the review session may change (nothing in `crates/`; it reports) and
  where it writes (`planning/feeds_review_<date>/`).
- STE style (short sentences, active voice).
