# P22-0c D1: the simulation-prefix key holds the centre-core facts

Defect D1 (`P22-0c_DESIGN.md`): `hash_tool` built the prefix memo key from no
centre-core fact. Since P22-0a the stamp of a non-centre-cutting tool cuts only
the blade ring. Two tools that differ only in the core could share a key.

## Changed path

`crates/rs_cam_core/src/compute/sim_prefix.rs` (the only path):

- `hash_tool` reads `tool.non_centre_cutting()`. This is the accessor that
  `RadialProfileLUT::for_stock_stamp` and the core gate
  (`stock/collision.rs`) read. The key holds a present/absent byte and all
  three `NonCentreCuttingLimits` fields: `max_plunge_depth_mm`,
  `max_descent_angle_deg` and `centre_core_diameter_mm`. The pattern
  destructures the struct without `..`, so a new limit field does not compile
  until it is in the key.
- The `hash_tool` doc names the third half ("Centre core").
- New unit test `tests::a_core_change_changes_the_prefix_key_d1`.

## Scope facts

- `hash_tool` has one caller: `hash_entry_scalar` (the prefix key). No other
  memo key uses it.
- The memo is in memory only (`DefaultHasher`, single slot, no disk form).
  No version constant exists, and no old entry survives a restart. No
  constant changes.
- The simulation does not read `ToolDefinition::cut_direction`, so the key
  does not need it.

## Red / green

Before the fix the new test failed:

```
assertion `left != right` failed: a centre-cutting and a non-centre-cutting tool give different keys
  left: 16970839683385084783
```

After the fix the test passes. It checks equal keys for equal tools (centre
and non-centre), and different keys for centre vs non-centre, for core
8 vs 10 mm and for protrusion 1.0 vs 1.5 mm.
