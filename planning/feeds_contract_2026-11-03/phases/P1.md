## Goal

After this phase, the compiler refuses a `_` (or a binding) match arm that stands for two or
more enum variants. Each such arm in the workspace at HEAD either names its variants, or carries
`#[expect(clippy::wildcard_enum_match_arm, reason = "..")]` that states why the arm is safe for a
new variant. A new variant of an in-workspace enum then fails to compile at each decision arm,
which K1, K3 and K4 need. No number, toolpath or G-code byte changes.

## Decisions (for the lead)

- **D1. Test targets.** `crates/rs_cam_core/CLAUDE.md:56-61` says a test module may expect only
  `unwrap_used`, `expect_used`, `panic` and `indexing_slicing`. A test arm such as
  `_ => panic!("unexpected {other:?}")` fails loud at run time. Options: (a) make every test
  arm exhaustive; (b) add `wildcard_enum_match_arm` to that list for a per-item expect with the
  reason "test: an unexpected variant panics". Recommendation: (b) for `_ => panic!` arms only,
  (a) for every other test arm. (b) changes an operator rule in a `CLAUDE.md`, so it needs the
  operator.
- **D2. Expect placement.** The workspace has no `#[expect]` for a wildcard lint today
  (`rg 'expect\(\s*clippy::match_wildcard'` gives 0 hits), so no precedent exists. Clippy may
  read the lint level at the `match` expression or at the enclosing item, not at the arm. Try
  the `match` statement first; if the expect is unfulfilled, put it on the smallest enclosing
  item. For the dispatch arms in `rs_cam_viz/src/app/input.rs:440,444`, the enclosing item is
  the whole event loop: the lead may prefer one small helper `fn` per dispatch arm.
