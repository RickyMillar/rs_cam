# P10: Geometry defaults come from the tool (operator ruling D8)

Status: NOT STARTED (card draft by the lead, 2026-11-03) | Contracts: K1 (the cut), K2 (`Basis`) |
Rulings: Q4, D8 | Numbers move: yes (the registry geometry defaults and every FM1 cell that reads
them)

## Goal

After this phase, an op has no geometry default without a tool. When the op has a tool, each
geometry default is a fraction of that tool: for example, stepover = k x D. Each k is a
`FormulaConstant` with a printed source in the repo, or a row marked Unsourced. The add door and
the tool change write the derived value as a stated value with `Basis::Rule` (the lineage names
the rule and D). Suggest still never writes geometry by itself (Q4).

## Why (operator, 2026-11-03)

After P5 a registry default is a stated value (P5 D1), and Suggest no longer fixes it at the add
door. A fixed millimetre default does not fit every tool: Face `stepover = 5.0` on a 3.175 mm tool
gives stepover > D and a Critical warning at add. The operator ruled: "I don't think they should
have defaults without a tool. Fractions are good."

## Preconditions

- P5 committed (`Basis`, the envelope, the pick-only geometry write, FM1 re-blessed).
- P4 `CutSpec` and `CutRule`: the rule names which field is radial, axial or a peck.
- Read the P5 commit message: it counts the FM1 cells whose operator point is outside the
  envelope and the cells that gain a Critical diagnostic. Those counts are the "before" of this
  phase.

## The fixed defaults today (`compute/operation_configs.rs` at c0db8dcb6)

Find each by `rg -n "^\s+(stepover|depth_per_pass|z_step|peck_depth|offset_stepover)\s*:\s*[0-9]"
crates/rs_cam_core/src/compute/operation_configs.rs` (28 lines at c0db8dcb6). Examples: Face
stepover 5.0, depth_per_pass 1.0; Drill and Pin Drill peck 3.0; Pocket and Zigzag stepover 2.0,
depth_per_pass 1.5 or 2.0; 3D Rough stepover 2.0, depth_per_pass 3.0; finishes stepover 0.5-1.0,
z_step 1.0; Pencil offset_stepover 0.5.

`scallop_height` (0.1) is a surface tolerance, not a tool length. It stays a fixed default.

## Changes (outline; the implementer completes it)

1. **The rule type.** `GeometryDefault { field, rule: ToolRule }`, `ToolRule::FractionOfD(&'static
   FormulaConstant)` (and only the forms a source supports). One rule per geometry field per op,
   on the registry row beside `cut_rule` and `entry` (a required field: a row without it does
   not compile).
2. **No default without a tool.** An op with no tool has `Unset` geometry for the tool-derived
   fields (S11 unset: generation stops with "set a tool", ruling Q10). The add door with a tool
   writes k x D.
3. **The tool change.** When the operator changes the tool of an op, a field that still holds
   its derived value (the lineage says `Rule`, not `Operator`) follows the new D. A field the
   operator edited stays.
4. **Sources.** Each k comes from a printed source in the repo or is Unsourced. Start with what
   the repo already holds:
   - the vendor `ap_rule` text in `data/vendor_lut/observations/*.json` (23 files; example:
     Amana "Depth of Cut: 1 x Tool Diameter");
   - `feeds::suggest` `STEPOVER_BACKOFF_DIAMETER_FRACTION` (an F201 row since P5);
   - `feeds/ramp.rs` `HELIX_RADIUS_OVER_D` as the pattern for a "k x D" repo rule.
   Never type a k from memory. A k with no source is an Unsourced `FormulaConstant` and the
   F201 count moves by it.
5. **Surfaces.** The GUI row, MCP and the CLI show the derived value with its rule (one glyph,
   the existing `ProvKind`, no new sentence).

## Tests

- Sentry `every_geometry_default_is_a_fraction_of_the_tool_d8`: for each op and each
  tool-derived field, two tools (D and 2D) give values in ratio 2; no tool gives `Unset`.
- Sentry: a tool change moves a derived field and keeps an operator field.
- FM1 re-bless: name the moved cells; the count of Critical cells at add (from the P5 notes)
  falls to the cells that stay outside for a reason other than the fraction.
