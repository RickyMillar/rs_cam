## 1. Finding: only one move-count model reads the depth

`runtime_limit` (`feeds/envelope.rs:2762-2816`) clones the op, changes only the stepover
(:2771-2775), and bisects the smallest stepover with `predict_move_count` <= the move budget; it
emits `Edge::AeFloor`. `predict_move_count` (`feeds/predict.rs:704-797`, checked by the reviewer):

| Model | Ops (`registry.rs`) | Formula | Reads the depth? |
|---|---|---|---|
| `PocketCell` | Pocket (:164) | dx dy / s^2 | no |
| `Raster` | DropCutter, Scallop, Waterline and others | (dy / s) x dx / (D x density) | no |
| `Adaptive2d` | Adaptive (:284) | dx dy / (s x woc) | no |
| `Adaptive3d` | Adaptive3d (:929) | dx dy / (s x woc) x max(dz / dpp, 1), dpp = `operation.depth_per_pass()` | **yes** |

Measured `Runtime` floors (mm, debug build, temporary test):

| Case | dpp 0.5 | dpp 1 | dpp 3 | dpp 6 |
|---|---|---|---|---|
| Pocket, 40 x 40 x 12 box | 0.05657 | 0.05657 | 0.05657 | 0.05657 |
| Pocket, 600 x 400 x 30 box | 0.6928 | 0.6928 | 0.6928 | 0.6928 |
| Adaptive3d, 40 x 40 x 12 | 0.05120 | 0.02560 | none | none |
| Adaptive3d, 600 x 400 x 30 | 3.0 (saturated) | 3.0 (saturated) | 3.0 (saturated) | 1.600 |

- Pocket 40 mm: sqrt(1600 / 500 000) = 0.0566 mm (500 000 = `STEPOVER_BACKOFF_TARGET_MOVES_ROW`,
  `invariants.rs:79-83`).
- Adaptive3d follows ae x ap = K (0.0512 x 0.5 = 0.0256 x 1; 600 x 400 x 30 at dpp 6: K / 6 =
  1.600). At dpp 3 on the 40 mm box K / 3 is below `MIN_AE_MM`, so the limit drops out (:2784).
- "Saturated": the budget fails even at 0.5 D, and the code draws the floor at the ceiling
  (:2786-2799). Points on that line also fail the budget: a second dishonesty.

The GUI draws Diameter, CuttingLength, FluteGuard and EngagementFloor as frame edges
(`rs_cam_viz/src/ui/feeds/envelope.rs:258-275`). Two straight width lines remain inside the plot:
CornerCoverage (a constant 0.854 D, it cannot move) and Runtime ("Min width (moves)", viz :174).
So the report is about Runtime, and the op was most probably an Adaptive3d (the rivmap100 roughing
benchmark is one). If the op was a Pocket, the moving line has another cause, which the audit did
not find. The op type is to be confirmed in the live GUI.

## 3. Notes per limit

- FluteGuard, CuttingLength: `geometric_limits` (:2042-2075) reads tool facts only.
- VendorAxial (:2076-2091): `max_doc_vendor(row, D)` (`cutter_constraints.rs:233`, :391-399);
  `axial_envelope_for_operation` reads the stepover only for its deflection and chip-floor fields.
- VendorDepthTable (:2264-2356): each column uses fz x sin psi(ae) against the band (:2324-2333);
  the chip is the operator's, else the grid chip at the shallowest sample (`speeds.at(0, j)`,
  :2314), the largest chip of the column, so the edge is conservative there.
- Rigidity, Adaptive factor arm (:2608-2629): `rigidity_cap_mm` (`invariants.rs:214-237`) at the
  span top; the cap does not depend on ae.
- Rigidity, force-budget arm (:2630-2748): each column solves `depth_at_budget(tool, material,
  ae, fz, budget)` (`force_budget.rs:351-409`); `refine_budget_columns` (:2489-2593) refines it.
  Defect: after the proposal, `add_exact_budget_samples` (:1094-1097, :1614-1648) adds a sample at
  the proposal width with `BudgetChip::Pick` = max(operator fz, suggested fz) (:1514-1516) and keeps
  the lower depth where two samples share a width. With an operator chip and a larger suggested
  chip, this notches the drawn curve at another chip; the notch follows the proposal, whose box is
  bounded by the stated ap and ae (:1716-1726).
- CornerCoverage (:2093-2110): d x (1 + 1/sqrt 2) / 2 (`force_budget.rs:427`).
- Power (:2158-2262): each column bisects ap (`EDGE_BISECTION_STEPS` 12, :63); each probe sets
  both axes (`operator_fits_power` :679-701, `calc_at` :661-675).
- Deflection (:2364-2469): `invert_deflection` (`cutter_constraints.rs:274-313`) at the column ae.
- ChipBand, RubbingFloor, FeedCap (:2818-2869): `place` skips `PerPoint` (:1236-1241) and viz
  `edge_points` returns `None` (viz :729).
- Diameter (:2111-2116): nominal D; `measured_edge` (:1202-1207) uses d_eng only for measured
  samples.
- Runtime (:2762-2816): besides the drawing, `place` judges points at any depth against the dpp
  floor (:1209-1265); viz `safe_region_quads` starts the fill at the largest `AeFloor` (viz
  :1180-1190); `propose_removal_rate` uses `AeFloor` as its lower bound (:1703-1726, only on the
  Pocket family and AxialBar routes, where the floor does not depend on depth). The operator's own
  point is placed correctly (the floor is exact at the stated dpp). With no stated dpp, Adaptive3d
  uses D x 0.5 (`predict.rs:275`, :767-770).
- EngagementFloor (:2117-2128): `MIN_AP_MM` 0.05, `MIN_AE_MM` 0.02 (`mod.rs:2010`, :2013).

## 4. No existing `Edge` variant carries a curved floor

`Edge` (:297-331): `ApCeiling`, `ApCurve`, `ApFloor`, `AeCeiling`, `AeFloor`, `PerPoint`,
`Unmodelled`. Every consumer reads `ApCurve` as a ceiling (ap <= f(ae)): `ap_ceiling_at` (:350),
`margin` (:366), `judged_value` (:1153), `place` (:1209), the `propose` cap search (:1405-1414),
`exact_ap_ceiling_at` (:1578), the `coarse` scorer (:1757-1761), viz `safe_region_quads`. The
Adaptive3d boundary is a floor (ae >= K / ap). An honest Runtime edge needs a new variant, which
breaks P17b's viz match arms. One variant can serve both open cases, for example
`AeCurve { bound: Floor | Ceiling, points: Vec<[ap, ae]> }`: the Runtime floor and the non-flat
Diameter ceiling.

## 6. Recommendation and order

1. Confirm the operator's op type in the live GUI.
2. Now, no new variant: when the move model reads the depth (`MoveCountModel::Adaptive3d`), emit
   `Edge::Unmodelled { reason: "the move budget depends on the depth per pass" }`, not `AeFloor`;
   the stated point is still checked. Fix the saturation case in the same change: when the budget
   fails at the 0.5 D ceiling, state it; do not draw a floor at the ceiling.
3. Now, no new variant: keep the `BudgetChip::Pick` sample out of the drawn Rigidity curve.
4. Now: give the time-budget sentry a model box, so it times `runtime_limit`.
5. After P17b: one new `Edge` variant for an ae(ap) floor or ceiling; fill the Runtime floor by
   bisection of `predict_move_count` per ap column (`ENVELOPE_GRID_N` columns plus the stated dpp
   as an exact sample), clamped to [MIN_AE, 0.5 D]; collapse to `AeFloor` when all columns are
   equal (Pocket, Raster, Adaptive2d stay as they are). Wire it into every consumer listed in
   section 4 and into viz `edge_mm`, `edge_points`, `safe_region_quads`.
6. Later, optional: the same variant for the non-flat Diameter ceiling; the feed-cap region as a
   width floor.

Every other limit is honest over the plane at the stated speeds; the ones with no stated chip are
conservative.

### Phase 2a: red on HEAD (before the fix)

Sentry `an_envelope_edge_does_not_move_with_the_stated_cut_p19.rs`; curves compared by a two-sided
point-to-polyline distance, TOL 0.02 mm (4 x `BINSEARCH_CONVERGENCE_MM`).
- (i) predicted, fix (a): Adaptive3d, stated ap 0.5 -> 1: Runtime `AeFloor` 0.0512 -> 0.0256.
- (ii) predicted, fix (b): force-budget Pocket at chip share 0.6, Rigidity: sample (ae 1.0, ap
  16.6298) 0.3633 mm off; sample (ae 2.0, ap 3.9419) 0.6199 mm off (the notch at the proposal
  width). At chip share 1.0 no Rigidity move, so the notch comes from the Pick chip.
- (iii) NOT predicted: VendorDepthTable moves with the stated ae (Pocket: sample (ae 1.0, ap 6.0)
  0.6058 mm off). Cause: `vendor_depth_limit` (~2296-2306) adds an exact sample at the stated ae
  when an operator chip is given. The sample is on the true curve, but with 8 grid columns (a step
  of about 0.85 mm) it bends the drawn polyline between columns, so the drawn line changes shape
  with the stated width. The Rigidity curve has the same stated-ae sample but stays inside 0.02 mm
  (`refine_budget_columns` makes it dense). Ruling asked of the lead; the reviewer recommends
  keeping the stated-ae sample out of the drawn curves and judging the stated point exactly in
  place (`table_ceiling_at`).

Lead ruling on (iii) (2026-11-07): option (A) with one addition. The stated-ae sample stays out of
the drawn VendorDepthTable and Rigidity curves; the stated point is judged exactly with
`table_ceiling_at`. Addition: the drawn curve agrees with the exact judgement near the line (a dot
drawn inside the line never gets an "outside" verdict, and the reverse), so the drawn
VendorDepthTable curve is refined until it is within TOL of the exact ceiling everywhere, from the
plane only (the `refine_budget_columns` pattern). Sentry case: the drawn polyline against
`table_ceiling_at` at 50 widths, max error <= TOL. The column count and the time cost go in the
result.
