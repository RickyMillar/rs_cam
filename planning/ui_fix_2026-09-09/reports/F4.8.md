## 2. Why this is a wrong cut and F4.4 could not reach it

F4.4 repaired `LoadedModel::drill_targets` on all three refresh doors. The
generator does not read that field when a pick exists. So after F4.4 the
record is right, the viewport is right, and the emitted motion is the
previous version's — which is a worse shape than before, because every
visible surface now agrees with the file and only the machine disagrees.

## 3. The design option I chose, and why

The brief offered three. I chose **(b) and (c) together**, gated on
evidence.

- **(a) store an identity — REJECTED.** There is no id to store (§1), so
  "identity" would have to be the INDEX into `drill_targets`. An index is
  strictly worse than a coordinate: delete one hole from the drawing and
  every later index shifts by one, so each pick silently moves to its
  neighbour. That converts a detectable wrong cut into an undetectable one.
  A new stable key on `DrillTarget` would have to be produced identically by
  the DXF and SVG importers and survive project IO — a schema change well
  beyond this lane, and it would still not identify a hole the operator
  MOVED.
- **(b) re-resolve the coordinate against the current targets — ADOPTED.**
  A pick IS a copy of a target's `(x, y)` (§1), so an exact-tolerance match
  is the identity the data already has. Resolving THROUGH the matched target
  also makes the model the source of truth rather than the config.
- **(c) refuse when a pick matches nothing — ADOPTED.** No information
  anywhere says which target a moved hole used to be, so a pick that matches
  nothing CANNOT be preserved. The brief's own ranking then applies: refuse.
  A "nearest target" snap was considered and rejected — it is a guess, and a
  wrong guess here is a hole in the wrong place with a green card.

### The scope boundary, stated plainly

The check runs **only when the model exposes at least one target**. An empty
target list means two different things at this seam and the function cannot
tell them apart:

1. the model exposes no targets, or
2. the CALLER resolved no model.

Case 2 is a shipped production path, not a hypothetical:
`execute_operation_annotated` passes `&[]` with a comment saying so
(`.../src/compute/execute.rs:3313`, "a `Drill` op on this path drills only
what it carries in `selected_holes`"), and **every drill fixture in the
suite** builds its model with `drill_targets: Arc::new(Vec::new())` — I
checked all eight (`drill_fed_descents_motion.rs`,
`drill_peck_depth_g_wanaka_peck.rs`, `drill_pick_emission_frame_g_drillpick.rs`,
`drill_entry_dressup_g_wanaka_drill_ramp.rs`,
`retract_intent_move_type_census_w6.rs`, `lateral_setup_end_to_end.rs`,
`adversarial_2d_campaign_r2.rs`, `pindrill_emission_frame_g_pindrill.rs`;
the model builders are `tests/common/session.rs:81-96` and local literals).

**The residual this leaves**: the operator DELETES every hole from the
drawing, the list goes empty, and the stale picks stand. That is failure
mode 2 of `reports/F4.4.md` §1, reached through the pick door instead of the
target door. Closing it needs a "was a model resolved" signal on
`ExecutionContext` — one field, plus the parameter on
`execute_operation_annotated_with_regions` and every construction site. I
did not attempt it in this lane. It is recorded in §7, in the module doc of
the sentry, in the doc comment of `stale_drill_picks_refusal`, and in
`CLAUDE.md`. The sentry pins the boundary as a passing test so a later lane
cannot mistake it for an oversight.

## 4. What changed

### Core — `/home/ricky/personal_repos/rs_cam_wt_p1/crates/rs_cam_core/src/compute/execute.rs`

| new item | what it is |
|---|---|
| `pub const DRILL_PICK_MATCH_EPS_MM: f64 = 1e-6` | the pick-identity distance |
| `pub fn drill_pick_matches(pick, target) -> bool` | the one matcher |
| `pub const STALE_DRILL_PICKS_PHRASE: &str = "no longer"` | the phrase every stale refusal carries |
| `pub fn stale_drill_picks_refusal(picks, targets) -> Option<String>` | the shared refusal |
| `fn resolve_drill_picks(picks, targets, setup_transform) -> Vec<[f64; 2]>` | maps each pick onto the target it names, then into the emission frame |

`drill_holes_for_config` calls the refusal and then the resolver.
`pin_holes_in_emission_frame` gained a `drill_targets` parameter and now
returns `Result<Vec<[f64; 2]>, OperationError>`; its two callers are
`generate_alignment_pin_drill` (`?`) and `build_drill_op_for_config`'s pin
arm (`.ok()?`, which is what its Drill arm already did). **Both families run
through the same two functions**, so they cannot drift — the pattern
`drill_targets_refusal` already set.

**`drill_targets_refusal` is UNCHANGED**, deliberately. Its two other
callers see only a COUNT, never coordinates: the core precondition adapter
reads `PreconditionContext::target_model.drill_target_count`
(`.../src/diagnostics/adapters/from_preconditions.rs:235-236`) and the GUI's
static validator reads `ToolpathValidationContext.models[].drill_target_count`
(`.../rs_cam_viz/src/ui/properties/operations/mod.rs:1835-1846`). Neither can
see a stale pick. **Consequence to know: the Generate button stays enabled
and the diagnostics ribbon says nothing; the refusal arrives as a generation
error.** Threading coordinates into those two contexts is §7.

### The epsilon is a consolidation, not a new threshold

`1e-6` was already this repo's pick-identity distance, in **three**
hand-written copies: `TARGET_EPS` in the drill panel, `EPS` in the viewport
toggle, and an inline literal in the viewport's drill-marker loop
(`crates/rs_cam_viz/src/app/gpu_upload.rs`). All three now read
`DRILL_PICK_MATCH_EPS_MM`, and the marker loop reads the shared
`drill_pick_matches` predicate. **No numeric value changed anywhere in this
lane.** The value is right for the job because a pick is a bitwise copy of a
target's `(x, y)` produced by the same importer, so the two agree exactly;
the tolerance exists only to avoid `==` on floats. It is deliberately NOT
loosened — a loose tolerance would re-introduce the "nearest target" guess
rejected in §3.

### A stale pick is INVISIBLE, which is what the refusal has to say

I read the viewport's drill-marker loop (`gpu_upload.rs`, the block guarded
by `active_drill`). **It iterates `model.drill_targets`** and colours each
marker green when a pick names it, orange otherwise. A pick that names no
target is drawn NOWHERE. `AppEvent::ToggleDrillTarget` fires from clicking a
target, so the operator can neither see a stale pick nor click it off.

The first draft of the refusal said "Re-pick the holes in the viewport, or
press Clear". **That instruction does not work**: picking the moved hole ADDS
it and leaves the stale coordinate in the vector, so the op refuses again.
The message now says the marker is drawn only at a target, that the stale
pick is therefore not on screen, and "Press Clear, then pick the holes
again" — which is unconditionally correct. Fixed in the fifth commit of this
lane; §7 records the deviation from the four-commit protocol.

### Saved projects — the assumption this refusal rests on

A refusal on an existing project's first regeneration would be a bad
outcome, so state what it depends on. `selected_holes` round-trips through
`toml::to_string` (`crates/rs_cam_core/src/session/project_file.rs:1171`).
The `toml` crate writes an `f64` through Rust's own `Display`, which is
shortest-round-trip, so a saved pick reloads bit-identical and matches the
re-imported target well inside 1e-6. **I did not run a round-trip.** The
assumption is: the serializer preserves the f64 exactly. If a future
serializer truncated, every saved project with picks would refuse on the
next generate.

### MCP surface — a contract change

`ProjectSession::set_toolpath_param`
(`crates/rs_cam_core/src/session/compute.rs:283`) has a GENERIC fallback: it
inserts the key into the operation's serde params object and re-deserialises
`OperationConfig`. `selected_holes` is a serde field on `DrillConfig`, so an
MCP agent can most likely write an arbitrary coordinate through it. On a
model that exposes targets, such a write now produces a generation error
where it previously produced a hole. That is the correct behaviour — the
agent was writing a coordinate that names nothing — but it is a contract
change on that surface. **I read the dispatch; I did not run it**, and there
is no MCP tool dedicated to picks (`set_drill_selected_holes` has no MCP
route).

### GUI — the operator-visible half

### The non-vacuity floor

Two floors, not one.

1. The fixture check: drawing A and drawing B each expose exactly one
   target, the target MOVES by more than 1 mm between them, and the no-hole
   model exposes none. Without it every arm could compare empty lists.
2. **Every arm first asserts `drill_targets_refusal` returns `None`** for
   the picked config at target counts 0, 1 and 2. Two refusals already
   existed on this path (no pick and no targets; an EMPTY pick), so without
   this a refusal from either of them would satisfy the new assertions
   vacuously. With it, a refusal observed in the file is the new check.

The two refusing arms also assert the message contains
`STALE_DRILL_PICKS_PHRASE` ("no longer"), which neither existing refusal
sentence contains. The phrase is asserted as a literal in the sentry rather
than by importing the constant, so the file compiles unchanged at the sentry
commit and at the fix commit.

### The refusal reaches the assertion — checked

The three refusing arms read `SessionError::to_string()`, not
`OperationError::to_string()`. `SessionError`'s Display carries the inner
string — `Self::OperationFailed(msg) => write!(f, "Operation failed: {msg}")`
(`crates/rs_cam_core/src/session/mod.rs:154`) — and
`drill_no_targets_refuses_g_drillcentroid.rs:175-199` is the precedent: it
matches on the refusal sentence through this same session door.

### One weakness I am naming rather than hiding

The sentry file is generic over the pick's staleness, but it asserts the
message contains a literal phrase rather than importing
`STALE_DRILL_PICKS_PHRASE`. That is what lets the file compile unchanged at
both commits, and it is the cost: renaming the constant's text would not
break the sentry at compile time. The in-file unit test in `execute.rs` DOES
import the constant, so the two together cover both directions.

## 7. What I did NOT do, and why

- **The empty-target-list residual is open.** §3 states it, and
  `a_pick_on_a_model_that_exposes_no_targets_still_generates` pins the
  boundary as a passing test. The fix is a `model_resolved` signal on
  `ExecutionContext`. I did not attempt it because it changes the signature
  of `execute_operation_annotated_with_regions` and every construction site,
  which is a second lane's worth of blast radius and would have put my RED
  evidence at risk behind a compile error.
- **The static surfaces cannot see a stale pick.** The Generate button and
  the diagnostics ribbon read a target COUNT (§4). Publishing the target
  COORDINATES into `PreconditionContext` and `ToolpathValidationContext`
  would let the shared predicate run there too. Recorded, not done.
- **No pick is migrated or repaired automatically.** A rescale, in
  particular, moves every target by the unit scale and leaves the picks —
  so after F4.7 lands, rescaling a drawing that has picks drops the results
  and the regeneration REFUSES. `rescale_model` knows the scale factor and
  could move the picks with it. That is a follow-on; the refusal is the safe
  behaviour and a silent 25.4× wrong hole is not.
- **`set_toolpath_model` still does not clear picks** (§1). The generation
  check covers the wrong-cut consequence. Clearing at the rebind would be
  the tidier repair and is a separate behaviour change.
- **The GUI stale label is unverified.** I started no GUI and the MCP server
  is down.
- **The sentry looks the model up by SLOT.** `refresh_model` uses
  `models_mut().first_mut()`. `reports/F4.4.md` ruled against slot lookup and
  its own sentry looks up by path then by id. Correct here because
  `session_with` adds exactly one model to a `ProjectSession::new_empty`, but
  it is the weaker form and I am naming it rather than editing the sentry
  commit after the fact.
- **A fifth commit exists.** The brief specified four. The fifth reworded the
  refusal, because the first draft told the operator to "re-pick the holes in
  the viewport", which does not work (§4) — re-picking adds the new target
  and leaves the stale coordinate. Shipping an instruction that does not work
  would be the exact defect class this programme exists to remove, so I fixed
  it in a separate commit rather than amending a commit the orchestrator was
  about to run.
- **I ran no cargo command**, so I have not compiled this.
