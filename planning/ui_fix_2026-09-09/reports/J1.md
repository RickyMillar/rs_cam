### Why

`1 items, regions 0, rings 0` is the exact G-LINKTRACE signature. The
finishing link stage (`0c36a2f0` G-LINKSTAGE) made
`relink_fragments_with_kinds` return `MoveProvenance::Permutation` where it
used to return `Remap`. `Permutation` carries the `foreign_intrusion` rule,
and the relinker creates intrusion at EVERY junction by construction: the
deleted junction rapid and the next fragment's first move land on
overlapping output ranges. `ScallopAnnotationChannel` asked
`remap_range(i, i+1)` for each of its ring annotations, so every annotation
was dropped.

`f84136fb` adds `MoveProvenance::remap_point`, which runs no intrusion check
because a single-move ANCHOR has no width and a width of one cannot widen —
the intrusion rule guards a multi-move CLAIM. Only
`ScallopAnnotationChannel` uses it; `SemanticLinkChannel` carries genuine
ranges and keeps the drop.

**Verdict: the pin was never stale. The code regressed and is now fixed.**
The C8 sentry did its job — it named a real defect and stayed red until the
defect was fixed. It also independently corroborates the G-LINKTRACE
measurement from a different surface (narration, not a digest).

### Attribution — measured, not reasoned

The pin was last written at `a68292ff`. Five commits between there and
master touch `dressup.rs` / `execute.rs` / `arcfit.rs`. The test binary was
built and run at two of them, with the SAME test file checked out at both so
only the library differs:

| Commit | `moves` | `arcs` | `Retract` | `pre_arcfit_moves` | Result |
|---|---:|---:|---:|---:|---|
| `01ec1e41` G-ISOCLIPENTRY | 74 | 13 | 7 | 159 | **pass** |
| `38f8d151` G-ISOCLIPRAPID | 80 | 13 | 13 | 165 | **fail** |
| `3d88406b` master | 80 | 13 | 13 | 165 | fail |

`01ec1e41` is the parent of `38f8d151` for every commit in the range that
touches core code; the 19 commits between them are docs, evidence and
render. The reading at `38f8d151` is identical to master's, fingerprint
included (`fnv=06526175378945769562`), so nothing after it moved the number
again.

### Mechanism

The delta is exactly six `MoveIntent::Retract` moves, 7 → 13.
`38f8d151` (G-ISOCLIPRAPID) added a pure-vertical lift to
`apply_lead_in_out` before its pre-position rapid, quoting the code:

> Move 0 (G-ISOCLIPRAPID): LIFT before traversing. Where the tool is still
> down in the cut, going straight to `(lead_start.xy, safe_z)` is a rising
> DIAGONAL out of the material — safe once the post splits it but a strike
> to every reader of the IR, including `collision::RapidClearanceCheck`,
> whose pure-vertical exemption a diagonal does not get.

It is emitted only when `safe_z > here.z`. `face_full` has 7 lead-ins; six
stood below the retract plane and gained a lift, one did not. The test
reaches the guard because it calls `apply_dressups` with `safe_z = 30.0`,
and `apply_dressups` is the production caller that passes its own `safe_z`
as `retract_z`.

### Why this is a re-pin and not a regression

The quantity this file exists to measure is the **arc** cost of the F1 Q3
intent run-key ruling. It did not move:

- `arcs` 13 → 13 on `face_full`, and unchanged on all four other fixtures.
- The seam census is unchanged: `(118, 20, 0, 0)`.

Both follow from what was added. A `Rapid` is not a `Linear` move, so it
creates no same-feed linear join for the census to count and no geometry for
`try_fit_arc` to collapse. Six added rapids, zero arc cost.

The added moves are a SAFETY improvement — they make the stored motion say
what the machine does. Reverting them to make this pin pass would undo a
fix. The pin is what went stale, because `38f8d151` did not re-baseline it.

1. `face_full` `Expect.out` `(74, 13)` → `(80, 13)`, above a comment that
   names `38f8d151`, the date, the mechanism, the two measured readings, and

2. The `pr6_measure_arcfit_intent_key_cost` doc paragraph claiming every

Nothing else in the file changed. `census` was NOT touched. The other four
fixtures were NOT touched.
