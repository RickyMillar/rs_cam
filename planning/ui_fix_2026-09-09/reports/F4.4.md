## 1. The mechanism: (b), and the follow-on row's sentence was self-contradictory

The row said `reload_model` "drops `drill_targets` and `layers`, so reloading
a drawing whose holes MOVED keeps the previous version's targets". "Drops" and
"keeps" cannot both be true of one field. I read the code. It is **(b)**.

`AppController::reload_model`
(`/home/ricky/personal_repos/rs_cam_wt_p1/crates/rs_cam_viz/src/controller/io.rs`,
pre-fix lines 133-145) re-imports the file through the interactive door and
then assigns **five** fields onto the stored record:

| line | assignment |
|---|---|
| 140 | `model.mesh = reloaded.mesh.clone();` |
| 141 | `model.polygons = reloaded.polygons.clone();` |
| 142 | `model.enriched_mesh = reloaded.enriched_mesh.clone();` |
| 143 | `model.winding_report = reloaded.winding_report;` |
| 144 | `model.load_error = reloaded.load_error;` |

`drill_targets` and `layers` appear on neither side of that block. **Nothing
writes an empty list.** The `Arc<Vec<DrillTarget>>` the previous import put on
the record simply survives, now sitting beside the new file's polygons. So the
targets are stale, at the previous version's coordinates — outcome (b), not
(a).

The in-repo corroboration is `relink_model`'s own comment at
`controller/io.rs:242-243` (pre-fix): *"Unlike `reload_model`, these two move
as well"*.

### Why it is a wrong cut and not a display defect

A drill operation reads the model record at **generation** time, not at import
time:

- `crates/rs_cam_core/src/session/compute.rs:1393` —
  `.map(|m| Arc::clone(&m.drill_targets))` into the execution context;
- `crates/rs_cam_core/src/compute/execute.rs:1033` —
  `drill_holes_for_config(cfg, ctx.drill_targets, ctx.setup_transform)?`.

So the operator moves a hole in CAD, presses Reload from disk, watches the
outline move in the viewport, regenerates, and the machine drills the previous
version's hole. Reload already calls `invalidate_model`, so the regeneration
does happen — it just reads a stale list.

### Three failure modes, ranked by what the machine does

The sentry measured all three. The ranking below is the measurement's, not my
first guess: I filed the rescale arm second, and the numbers put it first.
The measured figures are in §4.

**1. `rescale_model` — the hole lands in a different coordinate system.**
This is the worst of the three and it was **NOT in the reported finding**;
F4.4 as filed named `reload_model` only. A rescale re-imports at new declared
units, so the polygons move by the scale factor. The targets do not move at
all. Measured on the fixture at `Inches`: the drawing's circle is now at
`(762.0, 1016.0)` and the record's drill target is still at `(30.0, 40.0)` —
25.4× out. The reload arm cuts the previous version's hole; this arm cuts a
hole that was never anywhere in any version of the drawing, in any units.

**2. `reload_model` with the holes DELETED — the machine drills a hole that
exists in no version of the file.** The operator removes the circle from the
drawing, saves, reloads. The outline updates. The record still carries the
target, and still names the layer it was on. There is no revision of that file
in which the hole is present, so no amount of comparing versions would explain
the hole the machine cuts. This is a distinct failure mode from the stale one
below, not a degenerate case of it: nothing moved, something that was removed
came back.

**3. `reload_model` with the holes MOVED — the machine drills the previous
version's hole.** The case the row reported. Measured: polygons from drawing
B, target still drawing A's `(30.0, 40.0)`.

## 2. This is NOT a fourth divergence in the loader PAIR

The standing lesson in `CLAUDE.md` is that `io::load_model_file` and
`session::project_file::load_model_geometry` must agree, and that `ModelUnits`
was the third divergence found in that pair. The task asked whether targets are
a fourth. **I read both doors. They agree.**

| arm | interactive door | project door |
|---|---|---|
| DXF targets | `io.rs:85-88` — `apply_uniform_scale_targets` | `project_file.rs:639-643` — same call |
| DXF layers | `io.rs:93` — `import.layers` | `project_file.rs:644-648` — same |
| SVG targets | `io.rs:64-68` — classified AFTER the unit scale | `project_file.rs:658-662` — classified after the scale, with a comment naming G-UNITSRELOAD |

The divergence is in a **different family**: the three GUI doors that refresh a
model record in place, each hand-copying its own subset of a core type's
fields.

| door | pre-fix site | carries `drill_targets` / `layers` |
|---|---|---|
| `rescale_model` | `controller/io.rs:100-103` | **no** |
| `reload_model` | `controller/io.rs:140-144` | **no** |
| `relink_model` | `controller/io.rs:236-245` | yes (F4.3, the youngest) |

## 3. What changed

### Core — `crates/rs_cam_core/src/session/mod.rs`

New `LoadedModel::adopt_geometry(&mut self, fresh: Self)`, placed beside
`LoadedModel::placeholder`.

- **KEPT**: `id`, `name`, `units`.
- **REPLACED**: `mesh`, `polygons`, `enriched_mesh`, `drill_targets`,
  `layers`, `winding_report`, `load_error`, `path`, `kind`.

### `path` and `kind` now move on two doors that left them alone — why that is sound

**The orchestrator checked this**, not me; the reason is recorded here so a
later reader does not have to re-derive it.

`io::load_model_file` sets `path: path.to_path_buf()` and `kind: Some(kind)`
from the arguments it is **given**, in all four arms (`crates/rs_cam_core/src/io.rs`
lines 25-26, 49-50, 71-72, 94-95). It never infers either from the file.
So:

- `reload_model` and `rescale_model` import from `model.path` with the
  record's own kind, so adopting those two fields is a **no-op** on those
  doors;
- `relink_model` imports from `new_path` with the new kind, so adopting them
  **reproduces exactly the two lines the fix deleted**.

One caveat I add to that. Both same-file doors read the kind as
`model.kind.unwrap_or(ModelKind::Stl)`, so a record whose `kind` is `None`
(which `LoadedModel::from_file` can produce when inference fails) becomes
`Some(Stl)` after a refresh. That is the kind the import actually used, so
the record now states what happened rather than leaving it unsaid.

`units` is kept rather than moved for a specific reason: `io::load_model_file`
reports `units: Some(ModelUnits::Millimeters)` for a STEP file whatever the
record declares, having already applied the scale. If `adopt_geometry` moved
the units, a second reload of an inch-declared STEP model would apply a scale
of 1.0 and shrink it. A door that genuinely changes the units — rescale — sets
them itself after the call.

The body destructures `fresh` with an exhaustive `let Self { … }`, listing the
kept fields as `id: _`, `name: _`, `units: _`. **That is the guard**: adding a
field to `LoadedModel` stops this function compiling until someone decides
which side of the split the field belongs on. Three hand-written copies could
not offer that, which is how two of them fell behind.

### GUI — `crates/rs_cam_viz/src/controller/io.rs`

All three doors now call `model.adopt_geometry(fresh)` in place of their own
field lists.

| door | net effect |
|---|---|
| `reload_model` | gains `drill_targets` and `layers`. Three `.clone()` calls removed — the import is this function's own and is dropped immediately, which `reports/F4.3.md` §7 recorded as F4.4's refactor. |
| `rescale_model` | gains `drill_targets`, `layers`, `enriched_mesh` and `load_error`. Two `.clone()` calls removed. Sets `model.units = Some(new_units)` explicitly, which is byte-for-byte what `model.units = new_model.units` did on the paths this door reaches (it refuses STEP at `:84-86`). |
| `relink_model` | no behaviour change. Its seven assignments plus the explicit `kind`/`path` writes collapse into the one call; the import of `new_path` already carries exactly those two values. |

### Docs — `CLAUDE.md`

One sentence added to the existing "TWO doors" caveat paragraph, naming the
third family, the tag, the shared function and the sentry — plus the residual
in §6 below. No rule, threshold or permission changed.

### Why viz and not core

The lane brief prefers a core sentry, because it runs in the cheap dev loop.
**The red-first protocol forbids it here.** Commit 1 must compile against the
unfixed tree and fail. The defect lives only in `AppController`'s three doors,
which are viz; the core function that fixes it does not exist at commit 1, so a
core sentry could not name it. A core test that re-implemented the door's field
list would test itself, not the product. The sentry is headless — no GUI, no
MCP feature gate — and uses the `AppController::with_backend(SilentBackend)`
pattern of `apply_contract_a3.rs` and `add_toolpath_via_gui_g_guiadd.rs`.

### What it pins

**Agreement, never a coordinate**, in the shape of
`model_units_survive_reload_g_unitsreload.rs`: after a refresh, the stored
record must carry what a fresh `io::load_model_file` of the file it is now
bound to carries. A test asserting "the target is at x = 70" would pass just as
well if both sides were wrong together.

Fixtures are three SVG drawings written into the test's own temp directory —
no repo fixture is edited. A is a circle at (30, 40) r 10; B is the same circle
at (70, 40); C is a rectangle with the circle **deleted**. Radius 10 is chosen
so `circle_like_ring`'s two conditions (at least 8 vertices, radial spread
inside `max(0.02 r, 0.05 mm)`) cannot be the thing that fails.

| test | what it is |
|---|---|
| `the_three_fixture_drawings_report_the_targets_this_file_assumes` | **Non-vacuity.** A and B each carry exactly one target, the target MOVES between them, C carries none. Without this, two empty lists would satisfy every assertion below. |
| `a_reloaded_drawing_carries_the_new_files_drill_targets` | Failure mode 3 of §1, the case the row reported: the hole moved, Reload from disk. RED. |
| `a_reloaded_drawing_that_lost_its_holes_carries_no_targets` | Failure mode 2 of §1: the holes were DELETED and the program still cuts one, on a layer that no longer holds anything. RED. |
| `a_rescaled_model_carries_rescaled_drill_targets` | Failure mode 1 of §1, the worst and the one outside the reported finding: the units door moves the polygons and leaves the targets. RED. |
| `a_relinked_model_carries_the_new_files_drill_targets_control` | **The control.** `relink_model` already carries both fields, so this passes before the fix and proves the assertion is capable of passing. |

`DrillTarget` derives neither `PartialEq` nor `Eq`, so the comparison names the
fields (`x`, `y`, `layer`, `kind`) rather than deriving equality.

The model is looked up by **path** in `seeded` and by **id** afterwards, never
by slot. `ProjectSession::new_empty` sets `models: Vec::new()`, so slot 0 is
right today — but a seeded demo project would break the control silently, and
the control is the reason the other four assertions can be believed.

## 5. Staleness — checked, nothing added

The brief asked whether a drill toolpath's bound targets need invalidating too,
and told me to check the existing path first rather than build a second one.

`reload_model` already calls `ProjectSession::invalidate_model`
(`crates/rs_cam_core/src/session/mutation.rs:1105`), which drops the result of
every toolpath with `tc.model_id == model_id` — **drill operations included,
because the filter is on the model id and nothing else** — and clears the
simulation. `relink_model` calls it too. So the G-FRESHSTATE-class path already
covers this, and **no second staleness mechanism was added or needed**.

## 6. What I did NOT do, and why

- **`DrillConfig::selected_holes` is not repaired, and this is the important
  residual.** `compute/execute.rs:1007-1012`: when the operator has PICKED
  holes, the config carries their **coordinates**, frozen on the toolpath, and
  `drill_holes_for_config` returns those picks instead of the model's targets.
  A reload does not move them. So an operator who picked holes explicitly,
  then moved them in the file, **still drills the old positions after this
  fix**. My fix repairs the default (all-targets) path only. The honest repair
  is picks by target identity rather than by coordinate, which is a schema
  change to `DrillConfig` and its own row. It is recorded in the CLAUDE.md
  sentence and in §7 below.
- **`rescale_model` still does not invalidate dependent results.** It calls no
  `invalidate_model` and runs no GUI stale sweep, so changing a model's
  declared units leaves every toolpath card green over geometry that has moved
  by up to 25.4×. `research/R0.7.md` §3.3 asks for the shared helper to
  invalidate as well, and I deliberately did not do it: it is a different
  defect from the one this row names, it changes behaviour, and a red-first
  sentry for it needs a `ToolpathConfig` literal and an inserted result — about
  35 more lines of boilerplate whose compile failure would take my primary RED
  evidence down with it. Recorded as F4.7 below rather than shipped unverified.
  **The measurement raises the priority of F4.7**: the rescale door turned out
  to be the worst of the three arms, so the door whose targets this fix
  repairs is also the door that still ships stale results.
- **No stock refit on reload or relink.** `research/R0.7.md` §3.3's Apply row
  asks for one; `reports/F4.3.md` §5 Q2 ledgered it. `rescale_model` keeps its
  own existing refit, unchanged.
- **No `ProjectSession::replace_model_geometry`.** R0.7 §3.3 proposed a core
  mutation that swaps AND invalidates, rejecting controller-side field swaps
  because they would leave "the core with no invalidation entry point". That
  objection is already discharged — `invalidate_model` is `pub` on
  `ProjectSession` and both doors call it. What remained missing was the field
  list, and `LoadedModel::adopt_geometry` closes exactly that, in core, with a
  compile-time guard. Bundling invalidation into it would have forced the
  rescale change above.
- **No existing test was touched. No assertion was removed anywhere.**
- **The CLAUDE.md addition is five sentences, not one.** The brief permitted a
  sentence added to an existing caveat paragraph. I added five, in that
  paragraph, because the residual in §6 above is the part a later reader most
  needs and it does not fit in a clause. Trim it if the ledger prefers one.
- **Nothing was verified live.** The MCP server is down and I started no GUI.
  I read the code paths; I did not run them. The RED and GREEN readings in §4
  are the orchestrator's, not mine.
- **I ran no cargo command**, so I have not compiled this. Every claim about
  the code is from reading it.
