## 1. The three facts, with file and line

### Fact 1 — which toolpath wins, and what happens when none does

`AppController::request_collision_check`
(`crates/rs_cam_viz/src/controller/events/simulation.rs:375-397`, pre-fix)
runs `find_map` over `session.toolpath_configs().iter().enumerate()` and
takes the **first index, in configuration order, that satisfies all four**
of:

| Requirement | Line (pre-fix) |
|---|---|
| a GUI runtime entry — `gui.toolpath_rt.get(&tc.id)` | `:383` |
| a result on it — `rt.result.as_ref()` | `:384` |
| a tool whose raw id is `tc.tool_id` | `:385-391` |
| a model whose id is `tc.model_id` and which carries a **mesh** | `:392-398` |

Two things it does **not** do, both confirmed by reading the same
`find_map`:

- **It does not skip a DISABLED toolpath.** There is no `tc.enabled` test
  anywhere in the closure. A switched-off first operation with a stale
  result is the one that gets checked. **This is reachable today**:
  `AppEvent::ToggleToolpathEnabled`
  (`crates/rs_cam_viz/src/controller/events/mod.rs:120-129`) flips the
  config and calls `mark_edited`; it does **not** drop
  `gui.toolpath_rt[id].result`, and the readiness module's own comment
  (`ui/readiness.rs:86-93`) records that the GUI store keeps results after
  an edit on purpose, so the viewport can go on drawing them. So a job of
  "op 0 disabled, op 1 enabled" is checked on op 0 and the verdict
  describes motion the job does not contain.
- **It does not look for the toolpath most likely to strike.** Position in
  the list is the whole selection rule.

When NO toolpath satisfies the four, the `else` arm
(`:420-426`, pre-fix) logs `tracing::warn!` and pushes the toast "No
toolpath with STL mesh available for collision check". **Nothing is
submitted, and no state is written** — so the row keeps whatever verdict
it already had. On a project that has never been checked that reads "Not
checked" (F2.12); on a project checked earlier it reads the earlier
verdict, which the F2.12 staleness stamp then withdraws if an edit
followed.

A 2D-only job therefore cannot be holder-checked at all: no model in it
carries a mesh. That is pre-existing and it is not fixed here.

### Fact 2 — where the result lands, and whether the shape can hold a per-toolpath answer

The reply lands in the Collision `Ok` arm of `drain_compute_results`
(`crates/rs_cam_viz/src/controller/events/compute.rs:1292-1352`):

| Slot | What it holds |
|---|---|
| `SimulationChecks::holder_collision_count` | `collision.report.collisions.len()` — **one scalar for the whole project** |
| `SimulationChecks::min_safe_stickout` | `Some(..)` only when the count is `> 0` (F2.12) |
| `SimulationChecks::collision_report` | the whole `CollisionReport` |
| `SimulationChecks::checked_at_edit_counter` | the F2.12 submit stamp |

**The shape cannot hold a per-toolpath answer today, and neither can the
request.** `CollisionRequest`
(`crates/rs_cam_viz/src/compute/worker.rs:330-338`) carries exactly one
`annotated`, one `tool`, one `mesh` and one obstacle set;
`CollisionResult` (`:340-343`) carries one `CollisionReport`. The report
itself (`crates/rs_cam_core/src/collision.rs:143-152`) is a flat
`Vec<CollisionEvent>` plus one `min_safe_stickout`, and `CollisionEvent`
carries `move_idx` — an index into **the one toolpath that was checked**,
with no toolpath id on it.

**Core does carry the per-toolpath vector, and the GUI is not throwing it
away — the GUI never asks for it.**
`ProjectSession::holder_collision_counts`
(`crates/rs_cam_core/src/session/compute.rs:3499-3512`) walks every
toolpath that has a result and calls `collision_check(idx, ..)` per
toolpath, returning `Vec<(ToolpathId, usize)>`. Its own doc calls it "the
expensive sweep … Interactive surfaces should reuse their last dedicated
check instead of calling this per frame". The GUI has **no call site for
it**: `grep` finds callers only in `session/compute.rs` itself
(`:3463`, `:3474`) — the CLI/batch diagnostics path.

What the GUI has instead is
`SimulationState::holder_collision_counts_by_tp`
(`crates/rs_cam_viz/src/state/simulation.rs:1190-1203`), which
re-attributes the stored report. **It is in the wrong frame** — see §6
finding (i).

### Fact 3 — is the check expensive per toolpath?

**I could not price it, and I did not guess.** What I read:

`run_collision_check` (`crates/rs_cam_core/src/compute/collision_check.rs:63-107`)
does, per call:

1. `SpatialIndex::build_auto(request.mesh)` — a fresh index per call, with
   no dedupe across toolpaths that share a mesh;
2. `check_collisions_interpolated_with_cancel(.., step_mm = 1.0)` — for
   every **cutting** move, `interpolate_samples` at 1 mm, and for every
   sample and every assembly segment wider than the cutter, one
   `point_drop_cutter` query against the mesh
   (`crates/rs_cam_core/src/collision.rs:205-283`);
3. `check_obstacle_collisions_with_cancel` at the same 1 mm step.

So the cost scales with total cut length ÷ 1 mm × segments, plus one index
build per toolpath. That is a real cost of unknown size on a 3D finish
pass, and pricing it needs a run.

### The denominator is the ENABLED operation list

Not "toolpaths a check could examine". That alternative re-opens the same
defect through a different door: a job of one generated STL operation and
three enabled 2D operations would have `eligible == examined == 1` and the
row would read a clean `Pass` for a job three quarters of which was never
asked about.

**The consequence, stated plainly: under (b) a multi-operation job's
holder row can no longer read `Pass`.** A mixed 2D/3D job cannot reach
`Pass` at all, because a meshless operation is one this checker cannot
examine (Fact 1). That is the honest outcome of narrowing the claim, and
it is the reason (a) is worth measuring later. The row is now a `Warning`
that names what it measured, instead of a `Pass` that names nothing.

| `checked_at_edit_counter` | live counter | count | `covers_the_job()` | State | Status | Detail |
|---|---|---|---|---|---|---|
| `None` | — | — | — | `NotChecked` | Warning | "Not checked" |

| `Some(n)` | `n` | > 0 | true | `Collisions(k)` | Fail | "k collision(s)" |
| `Some(n)` | `n` | > 0 | false | `Collisions(k)` | Fail | "k collision(s) in Op 2 — 3 more not checked" |

Two rules inside that table, both deliberate:

- **A verdict about a DISABLED operation examines none of the job.**
  `examined` counts the ENABLED toolpath the check reached, so the
  "op 0 disabled, op 1 enabled" job stamps `examined: 0, population: 1`,
  `covers_the_job()` is false, and the row reads `PartialClear` →
  `Warning`. Without that, the scope would read `1 of 1` and the row would
  return to `Pass` on the one job where the only operation that will cut
  was never examined — the same overstatement through the door the
  selection rule leaves open. **The arithmetic closes it; the selection is
  not changed.**
- **A measured strike keeps `Fail` whatever the scope.** A partial check
  that found a strike UNDERSTATES the job; it does not overstate it. The
  detail still names the scope, so the operator knows the other operations
  were not asked about, but the tier does not move.
- **Staleness and partiality are not crossed.** A stale verdict is
  withdrawn whatever its scope: the remedy is one re-check either way, and
  the scope shows again on the answer. That keeps the enum at six variants
  instead of eight and leaves F2.12's four `assert_eq!` on
  `HolderClearance` untouched.

## 6. Findings recorded, not fixed

1. **`holder_collision_counts_by_tp` reads the report in the wrong frame.**
   `crates/rs_cam_viz/src/state/simulation.rs:1190-1203` maps each
   `collision.move_idx` through `move_to_local_toolpath_move`, which
   expects a **global simulation** move index. `move_idx` is a **local**
   index into the one toolpath the checker walked
   (`crates/rs_cam_core/src/collision.rs:214`). The two agree only when
   the examined toolpath is the simulation's boundary 0. Everything
   downstream inherits it: `project_evidence`
   (`state/simulation.rs:1808`), the core triage's holder findings
   (`rs_cam_core/src/sim_triage.rs:323`) and MCP `get_diagnostics`.
2. **The MCP wire carries the same scope overstatement.**
   `app/mcp.rs:2237,2249` publishes `holder_collision_count` totals, and
   `notify_mcp_collision_complete`
   (`controller/events/compute.rs:1345-1352`) sends `is_clear` with no
   population beside it. Same class as this row, different surface.
3. **What (a) would need**, precisely:
   - `CollisionRequest` becomes a batch of per-toolpath entries, or the
     controller submits one job per toolpath and the drain accumulates;
   - one `SpatialIndex` per **distinct mesh `Arc`** (dedupe by pointer) —
     today each call rebuilds one;
   - `CollisionResult` keyed by `ToolpathId`, and the drain stores a
     `Vec<(ToolpathId, usize)>`, which also closes finding 1 by removing
     the re-attribution entirely;
   - a wall-clock measurement on a real multi-operation fixture (the
     wanaka job) BEFORE it is default-on, because the sweep is a
     drop-cutter query per 1 mm sample per assembly segment;
   - `HolderCheckScope { examined: n, population: n, position: None }`,
     at which point `covers_the_job()` is true and every assertion in this
     lane's sentry still holds unchanged.
4. **A 2D-only job cannot be holder-checked.** The submit door requires a
   mesh, though the checker's fixture arm
   (`check_obstacle_collisions_with_cancel`) needs no mesh at all. Not
   introduced here; it is now visible in the row instead of silent.
