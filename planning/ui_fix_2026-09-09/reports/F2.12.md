## 1. The defect, as read

`readiness::holder_clearance_check` answered from `SimulationChecks`
alone (`crates/rs_cam_viz/src/ui/readiness.rs:140`, pre-fix):

```rust
if sim.checks.holder_collision_count > 0 {
    CheckStatus::Fail
} else if sim.checks.min_safe_stickout.is_some() {
    CheckStatus::Pass
} else {
    CheckStatus::Warning
}
```

No counter, no stamp, no comparison. The collision check reads the tool
holder and its stickout, the workholding obstacles and the emitted
motion; the operator could change any of them and the row went on
reporting the verdict computed against the previous machine setup.

Two shapes, and the second is not the one the follow-on note predicted.

- **A `Fail` survives the edit that resolves it.** The operator reads "3
  collision(s)", lengthens the stickout or moves the clamp, and the row
  keeps accusing a configuration that no longer exists.
- **`Pass` was unreachable.** The drain writes `min_safe_stickout` only
  when the check FOUND collisions
  (`controller/events/compute.rs:1310`, pre-fix), and the `count > 0`
  arm wins in that case. So the `Pass` branch needed
  `count == 0 && min_safe_stickout.is_some()`, which no shipped path
  produces. A clean, current check reported **"Not checked"**. The row
  that exists to say the cutter will not hit the workholding had no way
  to say it.

F2.10 §9 wrote that the verdict "survives any edit as `Clear`". `Clear`
is the word the two surfaces printed on the `min_safe_stickout` arm, and
that arm was dead. The surviving verdicts were `Fail` and "Not checked".
The class F2.10 named is right; the observed string is not.

I read these paths. I ran nothing: the MCP server is down, no GUI was
started, and this lane runs no cargo command.

**There is one counter.** `GuiState::edit_counter`
(`crates/rs_cam_viz/src/state/runtime.rs:170`) counts `mark_edited`

The collision check stamped it **zero** times. The fix is the same two
stamps on the collision job, read by the same kind of comparison. No
second counter was added, and no parallel freshness path was created.

`state::freshness::FreshnessState` (F2.1) is the OTHER half of the
project's freshness model, and it is not the one this row needs: it
answers about a toolpath's cached result, keyed by
`generation_inputs_signature` and `ProjectSession::toolpath_revision`.
The holder verdict is not a per-toolpath result — it is a whole-check
artefact with its own submit, so it belongs on the `edit_counter` side,
beside the simulation.

### The state table

| `checked_at_edit_counter` | live counter | `holder_collision_count` | State | Status | Detail |
|---|---|---|---|---|---|
| `None` | — | — | `NotChecked` | Warning | "Not checked" |
| `Some(n)` | `> n` | 0 | `StaleClear` | Warning | "Checked, then edited — re-check" |
| `Some(n)` | `> n` | > 0 | `StaleCollisions(k)` | **Fail** | "k collision(s) found, then edited — re-check" |
| `Some(n)` | `n` | 0 | `Clear` | **Pass** | "Clear" |
| `Some(n)` | `n` | > 0 | `Collisions(k)` | Fail | "k collision(s)" |

**Staleness withdraws a clearance claim. It never withdraws a measured
strike.** The two stale rows are not the same kind of thing. A stale clear
verdict is an abstention: absence of a strike was never proof of clearance,
so once an input moves there is no evidence either way. A stale colliding
verdict is positive evidence of a strike taken slightly earlier, and a feed
edit cannot move a holder out of a clamp — so it keeps `Fail` and the detail
names the count first and the age second. This also keeps the row and the
export gate in step: `preflight.rs:227` computes `has_failures` from the raw
count, which a stale strike still trips.

Only ONE of the five rows changes tier against the pre-fix code — the
current-clear row, from Warning to Pass. Pre-fix and post-fix agree on the
other four, because the pre-fix `Pass` arm was unreachable and everything
else fell through to the same answer. **The staleness therefore reaches the
operator through the DETAIL STRING, not through the tier**, which is why §6
pins the strings.

## 4. Operator-visible changes beyond staleness

Three, all disclosed rather than buried.

0. **A stale STRIKE keeps `Fail`. My first draft de-escalated it to
   `Warning`, and that was wrong.** The draft treated every stale verdict
   as one thing and mapped `NotChecked | Stale` to `Warning`. The
   consequence: a check finds three holder strikes, the operator changes
   a feed rate, and the row drops from red to amber — on the one row an
   operator scans for red, and while the export gate beside it still
   treats the same count as a failure. The coordinator caught it. The
   corrected rule splits the stale case by what the stale verdict said,
   because the two are different evidence: a stale clear verdict is an
   ABSENCE of evidence about the state now, and a stale colliding verdict
   is positive evidence of a strike, measured slightly earlier. An
   unrelated edit is not evidence that a strike is gone. The programme's
   own rule — `None` means NOT MEASURED, never clean — cuts the same way:
   a measured strike is not `None`, and nothing about a later edit turns
   it into one. Only the DETAIL changes for that state, and it names the
   count before the age. Recorded here because the record should carry
   the correction, not only the answer.
1. **The row can now read Pass, and the headline banner can go green
   where it did not before.** This is a consequence of the staleness fix,
   not scope added beside it: `min_safe_stickout.is_some()` was standing
   in for "was it checked", `checked_at_edit_counter` answers that
   question directly, and the proxy has no job left. The row now reports
   what a clean current check found. The banner is `worst` over the
   operations, simulation, rapid, holder and tool-load rows, so a green
   holder row only removes a warning the holder row itself was
   contributing.
2. **The pre-flight card's wording changed from "N issues" to "N
   collision(s)".** The two surfaces named the same fact differently.
   The Readiness panel's word won, because "collision" is what the
   producer, the status bar and the MCP wire all call it.

### It walks classes, not one edit

`edit_classes()` is a table of seven operator edits, each naming the
collision input it moves and driving the real GUI route:

| Class | Input it moves | Route |
|---|---|---|
| stock height | the motion, and the frame the fixtures sit in | `AppEvent::StockChanged` |
| fixture position and size | the obstacle the holder must clear | `AppEvent::FixtureChanged` |
| a fixture added | the obstacle set | `AppEvent::AddFixture` |
| a keep-out zone added | the obstacle set | `AppEvent::AddKeepOut` |
| tool stickout | how far the holder sits from the tip | `commit_tool_draft` |
| holder diameter | the holder's own geometry | `commit_tool_draft` |
| operation switched off | which motion the job contains | `AppEvent::ToggleToolpathEnabled` |

The table is walked **twice**, and the two runs pin OPPOSITE contracts:

- `a_clear_verdict_is_reported_and_then_withdrawn_g_holderstale` — a
  clear verdict must be withdrawn after any covered edit.
- `a_colliding_verdict_keeps_its_severity_after_an_edit_g_holderstale` —
  a colliding verdict must NOT be. It stays `Fail` and the count
  survives. This is a **preservation guard**: it passes on the unfixed
  code by construction, because the pre-fix row also answered `Fail`
  there. What it stops is a later change to the staleness rule turning
  red into amber.

Two further tests hold the withdrawal half honest:
`a_check_with_no_edit_after_it_stays_current_g_holderstale` (Pass stays
Pass, Fail stays Fail) and
`an_unchecked_project_is_not_a_verdict_g_holderstale`. A fifth,
`an_edit_during_the_check_leaves_the_verdict_stale_g_holderstale`, runs
F2.10's late-arrival race on the collision lane, on the dangerous
direction — a stale ALL CLEAR — and carries its own no-edit control so
it discriminates rather than firing on everything.

### Non-vacuity floors

Three, because a gate handed an empty population passes and looks
healthy:

1. `assert!(!classes.is_empty())` — an empty walk proves nothing.
2. **Every class must move `edit_counter`.** A class that does not fails
   BY NAME, with the words "this class is NOT COVERED by the project's
   freshness model". This is what turns the walk into a coverage
   instrument rather than a regression check: a collision input that no
   counter follows is exactly the defect this row exists to catch.
3. The verdict must arrive through the real drain arm — the mock lane
   counts collision submits and the test asserts one happened, and
   `collision_report.is_some()` after the drain — so the walk cannot
   pass on a verdict the test wrote by hand.
