## The builder

```text
profile_through_cut_line(depth, thickness, tabs)
  None                                                       depth + 1e-6 < thickness,
                                                             or thickness not finite / <= 0
  "Through cut of a 12 mm board · Holding: no tabs configured"   tabs == 0
  "Through cut of a 12 mm board · Holding: 1 tab"                tabs == 1
  "Through cut of a 12 mm board · Holding: 4 tabs"               tabs >= 2
```

- The comparison is `depth >= thickness` within the same `1e-6` mm epsilon
  G-DEPTHSTOCK uses, so the two rules partition the boundary: depth exactly
  at the thickness is a through cut and not an exceedance; depth beyond it
  shows this line first and the amber caution under it.
- The board thickness prints with no decimal when it is whole (`12`,
  `18`) and one decimal otherwise (`18.5`). `19.05` prints `19.1`.
- The PLAN wording was `Holding: {k} tabs`. One tab prints `1 tab`. This is
  the one deviation from the literal string; the tests pin it.
- Informational only. `validate_toolpath` is untouched, no severity, no
  block. Zero tabs stays valid, and the hover says when it is the right
  answer (vacuum table, double-sided tape).

## Which depth the inspector form compares

`profile_through_cut` reads the cut bottom the profile generator cuts:
`resolved.top_z - cfg.depth` (`OperationConfig::cutting_levels(top_z)`
steps from the resolved Top Z; a pinned Bottom Z does not reach the
generator). The depth compared is that bottom measured from the STOCK top,
`ctx.stock_top_z - bottom_z`, against `ctx.stock_top_z - ctx.stock_bottom_z`.
So a Profile at depth 12 on an 18 mm board is a rebate in `Auto`, and a
through cut when Top Z is pinned 6 mm down after a face pass. `ThroughCut::
depth_mm` carries the compared value so the sentry can read it.

Frame: `stock_top_z` / `stock_bottom_z` come from
`SetupEvalContext::heights_stock_bbox` (world for an identity setup,
zero-rooted local for a flip), the same source F1.6 uses, so a flipped setup
has the same thickness.

## The Tabs default

`CollapsingHeader::default_open` reads only on the header's first frame, so
a header first drawn closed (depth 6) would stay closed when the operator
drags the depth up to the board. The form therefore also forces the header
open (`.open(Some(true))`) on the ONE frame the condition `through cut &&
tab_count == 0` becomes true, tracked by a temp flag on the `Ui` id, and
passes `.open(None)` on every other frame. The operator can collapse the
section afterwards and it stays collapsed; setting tabs back to zero
re-opens it once. The flag is per panel, not per toolpath, which matches the
disclosure's own stored state (the header id was and is `"Tabs"` in that
`Ui`).

## The `On` side: not added

`ProfileSide` (`crates/rs_cam_core/src/profile.rs:13`) has two variants,
`Outside` and `Inside`, serde `snake_case`. The generator's offset match
(`profile_contour_reported`, `profile.rs:143-146`) has two arms, `+r` and
`-r`. There is NO on-line arm. The `compensate_in_controller` branch follows
the exact boundary, but it is the "controller applies G41/G42" path, not an
on-line cut, and `export.rs:287-290` maps it from the two sides only.

Per the brief, a combo entry that generates the same as Outside would be a
new untruth, so `On` was not added to the combo or to the enum. What
remains true and is reported here: the schema row `PROFILE_PARAMS`
(`catalog.rs:1503`) advertises `enum:on|inside|outside`, and an MCP
`set_toolpath_param side=on` would fail at serde. The schema over-states.
Fixing it (drop `on`, or add the variant with a zero-offset arm plus the
export mapping and the `properties/mod.rs:4246` display arm) is a core
change and is out of this task's scope. `FEATURE_CATALOG.md` now says the
`on` value has no generator arm.

Also seen, not touched: `FEATURE_CATALOG.md:150` says "In Control" is hidden
from the Profile UI; the form draws it (`boundary_2d.rs`, `prof_comp`).
