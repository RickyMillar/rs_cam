## 2. The state model as implemented

```rust
pub enum FreshnessState {
    Current, EditedSince, Regenerating,
    WaitingOnUpstream(AwaitingPriorStock), Error(String),
    NoResult, Disabled,
}
```

Derivation (`state/freshness.rs::freshness`), in order:

1. `!tc.enabled` → `Disabled`. Wins over everything, as `ComputeStatus::effective` already ruled for the chip.
2. `ComputeStatus::Computing` → `Regenerating`.
3. `ComputeStatus::AwaitingPriorStock(b)` → `WaitingOnUpstream(b)`.
4. `ComputeStatus::Error(e)` → `Error(e)`.
5. `session.get_result(index).is_some()` → `Current`.
6. `rt.result.is_some()` → `EditedSince`.
7. otherwise → `NoResult`.

The core result cache is the truth about result validity; the GUI's
retained `ToolpathRuntime::result` supplies only the one distinction the
core cannot make — "never generated" versus "had a result, then edited" —
which is a display matter and stays one.

`ToolpathRuntime::stale_since` is **not** part of the derivation any more.
It keeps its remaining job, the 500 ms auto-regeneration debounce clock,
and stops being a claim about correctness. It was not renamed — see §5.

## 5. Deviations from R0.1, each with the reason

1. **A new `AppEvent::HeightPlanesChanged`, not in R0.1.** The heights
   write-back pushed `AppEvent::StockChanged` purely to trigger a GPU
   re-upload of the height planes. Once a stock edit drops every toolpath
   result (Q1), borrowing that event would have staled the entire project
   on any heights nudge — a regression the ruling does not ask for. The
   new event does the re-upload and nothing else.
2. **`stale_since` was NOT renamed to `regen_requested_at`, and the
   controller pump that would replace its 27 write sites with one
   result-set diff (R0.1 §4.3 row 2) is not implemented.** Reason: the
   rename touches the MCP wire (`"stale"` on `list_toolpaths` and
   `get_toolpath_params`), the rest badge and four render sites that F2.2
   rewrites, so doing it here would collide with F2.2 and put a wire
   change inside a state task. Consequence to know: rows that drop a core
   result but set no regeneration request — toggle enabled, reorder,
   move-to-setup, setup orientation — now read `EditedSince` with no
   auto-regeneration. That is strictly better than the pre-fix green card,
   and no row LOST a request it used to have. Ledger it for F2.2 or a
   follow-on.
3. **`compute_stale_set` / `mcp_apply_stale` were not deleted** (R0.1
   §4.3's last line). They are the regeneration-request mechanism on the
   MCP side, which is item 2's territory. Both routes now agree about the
   STATE, because both reach the same core setters.
4. **`RuntimeSnapshot::freshness` carries `#[allow(dead_code)]`.** The
   field is required by the F2.1 acceptance ("`RuntimeSnapshot` carries
   it") and its only reader is the chip F2.2 draws. `has_result` was kept
   rather than removed for the same reason — removing it is a render
   change. The allow is on the field, with a comment naming F2.2.
5. **`invalidate_tool` changed its return type** from `()` to
   `Vec<usize>`. No caller was relying on the unit value.
6. **The GUI panel keeps writing `ToolpathConfig` fields directly** rather
   than being restructured to build a whole `ToolpathConfig` and call
   `replace_toolpath_config` (R0.1 §4.3). The signature comparison plus
   `invalidate_toolpath_inputs` gets the same invalidation with a far
   smaller diff through a 5 600-line panel. `replace_toolpath_config` was
   still upgraded to chain-invalidate, as R0.1 asks.
