## 1. Point 1 — the row's vocabulary predates the model

The row names three things:

> `ToolChange` undo calls `invalidate_tool`; every undo arm calls
> `mark_edited`; `ToolpathParamChange` undo re-stales the simulation.

Those are three symptoms of one rule, and stating the rule makes them fall
out:

> **After any undo or redo, the derived `FreshnessState` of every affected
> toolpath, the project's dirty flag, and the simulation's staleness are what
> they would be if the operator had made that same edit by hand.**

That framing decides every question below without further argument. It is also
why `apply_tool_snapshot` routes through `commit_tool_draft`'s door rather
than a second one that happens to agree today, and why the parameter arm does
NOT clear the simulation — a hand parameter edit stales it, so an undo must
stale it, not clear it.

## 2. Point 3 — the per-arm table

Five arms. "Hand equivalent" is what the same change does through the panel.

| Arm | Undo did | Core effect | Freshness | dirty | simulation | Verdict |
|---|---|---|---|---|---|---|
| `StockChange` | `set_stock_config` + `invalidate_simulation` | `drop_all_results()` (F2.1 Q1) — every toolpath | `EditedSince` ✅ | **no** ❌ | cleared ✅ | dirty only |
| `PostChange` | writes `gui.post` + `set_post_config` | none | `Current` ✅ (post config is emission, not geometry) | **no** ❌ | untouched ✅ | dirty only |
| `ToolChange` | **wrote `tools_mut()` directly** + `invalidate_simulation` | **none** ❌ | `Current` over geometry cut with the OTHER tool ❌ | **no** ❌ | cleared ✅ | **both** |
| `ToolpathParamChange` | `apply_toolpath_param_snapshot` + `stale_since` | `drop_result` ✅ | `EditedSince` ✅ | **no** ❌ | GUI results untouched AND not stale ❌ | dirty (which fixes the sim) |
| `MachineChange` | `set_machine` + `invalidate_simulation` | none ✅ (R0.1 Q3: timing, not geometry) | `Current` ✅ | **no** ❌ | cleared ✅ | dirty only |

Two real defects, and the third clause is a consequence of the second:

1. **`ToolChange` bypassed `invalidate_tool`.** Both arms wrote the tool slot
   by hand. Every operation that tool machines kept its CORE result — geometry
   cut with the other tool's diameter and profile — so it read `Current` on
   every surface F2.2 wired and would have passed the gate F2.3 built. This is
   the row's first clause and it is the serious one.
2. **No arm called `mark_edited`.** Two consequences. `dirty` stayed false, so
   an undone project was not offered for saving and the close interception let
   the operator walk away from it. And `edit_counter` never moved, so
   `SimulationState::is_stale` stayed false: the GUI went on presenting a
   simulation computed from the configuration the undo had just discarded, as
   current evidence.
3. **The row's third clause needs no separate fix.** "`ToolpathParamChange`
   undo re-stales the simulation" is exactly what `mark_edited` does on that
   arm — `apply_toolpath_param_snapshot` already cleared the CORE
   `simulation`, but the GUI's `state.simulation` is what every surface reads,
   and staling it is `edit_counter`'s job. Fixing clause 2 fixes clause 3, and
   it does so with the treatment a hand edit uses (stale, not clear) rather
   than a heavier one.

`mark_edited` is called **once, after the match**, not five times inside it.
The defect was that five arms each had to remember; putting it in each arm
would reproduce that for the sixth.

### Two treatments, one property

Three arms CLEAR the simulation, two only stale it — and that is correct,
because it mirrors the hand equivalents: a stock or machine change clears, a
parameter edit stales. The sentry therefore asserts the property both satisfy:
**cleared or stale, never present-and-fresh.** Asserting `is_stale` alone
would have been wrong, and did in fact fail on the clearing arms while they
were behaving correctly — `is_stale` requires `last_run.is_some()`, and
clearing sets it to `None`.

## 3. Point 2 — an undone edit does NOT restore `Current`

The question: an operation is generated at config A; the operator edits to B
(core result dropped, `EditedSince`, the GUI still holding A's geometry); they
undo. The retained geometry now matches the configuration again. Restore
`Current`, or stay `EditedSince`?

**Decision: stay `EditedSince`.** Three reasons, in order of weight.

1. **Nothing records which configuration the retained result answers.**
   `ToolpathRuntime::result` holds the last thing the lane delivered, and that
   is all it holds. Since F2.4 it may itself be a *late* result for a
   superseded config — stored deliberately, marked stale — in which case
   promoting it on undo would make current a result that never matched any
   configuration the operator asked for. F2.4's `submitted_revision` does not
   help: it records what was last SUBMITTED, not what the retained geometry
   answers.
2. **The snapshot is narrower than the geometry's inputs.**
   `UndoAction::ToolpathParamChange` carries operation, dressups and face
   selection — three of the nine fields in F2.1's
   `generation_inputs_signature` (which also covers heights, boundary, rest
   analysis, tool id, model id and stock source). And time has passed: the
   stock may have been resized, the tool edited, the model reloaded, each of
   which drops results for its own reasons. "The configuration is back" is
   true only of the three fields the snapshot holds.
3. **`toolpath_revision` only moves forward, and should.** Restoring `Current`
   would mean either rolling the revision back — which breaks F2.4's guard, as
   a late result stamped with the rolled-back value would then be *accepted* —
   or re-inserting the core result without touching the revision, which is
   possible but runs straight into reasons 1 and 2.

**The cost, stated plainly:** undo-then-redo on a generated operation leaves
it needing a regeneration although nothing net changed. That is the price and
it is the right one — being wrong this way costs compute, being wrong the
other way exports a program that does not match the project, which is the
class of defect this entire phase exists to close.

Pinned by `an_undone_param_edit_does_not_resurrect_the_old_result`, which
asserts the configuration really is restored AND the state is still
`EditedSince`, so reversing the decision has to be somebody's decision rather
than a side effect.

## 4. Point 4 — redo

**Redo had every one of the same defects**, because it is the same five arms
in the other direction: the tool arm wrote `tools_mut()` directly, and no arm
marked the project edited. The row does not name redo.

**Fixed in the same commit, not ledgered.** Splitting them would have left a
release where Ctrl+Z was honest and Ctrl+Shift+Z was not, which is worse than
either state on its own — and the fix is literally the same two lines, since
both directions now share `apply_tool_snapshot` and
`apply_toolpath_snapshot`. `every_undo_arm_marks_the_project_edited_g_undofresh`
drives both directions for all five arms.

## 8. What this task did NOT do

- **It did not widen `UndoAction`.** Reorder, enable, move-to-setup, delete,
  duplicate and planner Apply are still not undoable (R08 §3, R0.1 §6 "out of
  scope"). This task makes the five arms that exist honest; it does not add a
  sixth.
- **It did not change which arms clear the simulation and which stale it.**
  Both treatments now match their hand equivalents, and no arm's treatment
  moved.
- **It did not make `PostChange` stale anything.** Post configuration decides
  emission, not geometry; it marks the project dirty and nothing else. If a
  spindle-strategy change should stale the tool-load report, that is a
  separate question about `PostChange` generally, not about undo.
- **It did not verify anything live.** No GUI, no MCP.
