# F2.3 — the export gate: a result that is not current blocks the file

Task: `PLAN.md` §4 row F2.3, reordered ahead of F2.2 by the team lead
because F2.1 widened the fallback it closes. Tag: **G-STALEXPORT**.
Worktree `/home/ricky/personal_repos/rs_cam_wt_p2`, branch
`ui-fix/lane-p2`, stacked on F2.1 (`5765a179`).

---

## 1. The hole this closes

`io::export::emitted_result_toolpath` read `session.results` first and
`gui.toolpath_rt[id].result` — the compute worker's output, kept so the
viewport can draw the old path — second, **silently**. That fallback was
written for one narrow case, documented on `emitted_toolpaths`: a GUI
tool edit called `invalidate_tool`, which dropped the core result while
the viz store kept its copy.

F2.1 made **every** input edit drop the core result. The narrow case
became the normal one: edit a stepover, export, and the file was the
geometry from before the edit, with nothing on any surface saying so.

### The texts

| State | Sentence |
|---|---|
| `EditedSince` | `'X' was edited after it was generated — the stored result is the previous parameter set's geometry, not what the panel now shows; regenerate it, or accept the previous geometry to cut it as it was` |
| `Regenerating` | `'X' is still generating — wait for it to finish` |

moved. `Regenerating` is new as a distinct sentence: under
`ComputeStatus` it fell into "is not generated", which was wrong — the op
has a result, it is being replaced.

## 3. The four points the lead asked me to get right

1. **One builder, extended — not a second refusal path.** There is still
   exactly one text builder and one row type; both were renamed, because
   `ungenerated` stopped being true of the family once an edited op joined
   it. The three F1.9 sentences are unchanged, and F1.9's sentry still
   asserts row text == builder text, now through `FreshnessState`.

2. **The fallback: KEPT, but gated — and here is why not deleted.**
   Deleting it would make the accept flag unimplementable: the previous
   geometry lives *only* in the viz store, because the edit dropped the
   core slot. So `emitted_result_toolpath` still reaches
   `gui.toolpath_rt`, but only when the operator has said so for this
   export. The default path never touches it. Consequences checked:
   - The G-MODEXPORT invariant is intact. `session.results` is still read
     first and is still the only store the modulation post-pass writes.
     What the acceptance emits is the pre-modulation worker IR — exactly
     what the old fallback emitted, and there is nothing modulated for
     such an op anyway. The G-MODEXPORT sentry's second test is rewritten
     accordingly (§6).
   - The viewport is untouched. Drawing the old path and cutting it are
     now different permissions, which is the whole point.

3. **Every surface agrees.** Export, pre-flight and MCP `export_gcode`
   all print `blocking_toolpath_message`'s output for the same op in the
   same state. `preflight_rows_and_the_export_refusal_share_one_text`
   pins the pair; F1.9's equivalent test pins the other three states.

4. **The flag names what is accepted and is hard to pass by accident.**
   In-process it is an enum, not a `bool`: a call site reads
   `StaleResultPolicy::AcceptPreviousGeometry`, and there is no `true` to
   fat-finger. On the wire it is `accept_previous_geometry`, whose schema
   doc says the file will cut geometry that is not what the parameters
   describe. In the modal the checkbox reads "Cut the PREVIOUS geometry —
   the file will not match the parameters on screen", in its own framed
   block, never folded into the tool-load overrides: those accept a
   predicted *consequence* of cutting the emitted geometry, this accepts
   emitting *different* geometry.

**The acceptance waives one situation only.** A missing, failed or
still-generating result refuses under it too, because there is no
geometry to put in its place. `the_acceptance_does_not_waive_a_missing_result`
pins that.

**The MCP route does not inherit the GUI checkbox.** `mcp_export_gcode`
builds the policy from its own parameter, so an automation client cannot
pick up a box a human left ticked in the modal.

## 4. R0.1 §7 Q5 — answered by assumption

The operator has **not** answered whether `accept_stale` is a per-export
flag or a project setting. I implemented R0.1's own recommendation:
**per-export, never persisted**, held on `GuiState` beside
`ToolLoadOverrides` and reset whenever a project loads. If the operator
rules the other way, the change is to move the field onto the project
file and give it a serde default; nothing else in this commit depends on
where it lives.

Two smaller namings are also mine, not R0.1's: the wire parameter is
`accept_previous_geometry` rather than R0.1's placeholder `accept_stale`,
and the in-process type is an enum rather than a `bool`. Both follow the
lead's instruction that the flag must name what is being accepted.

## 6. The one existing sentry that had to change its expectation

`tests/modulated_feeds_reach_gcode_g_modexport.rs::viz_export_falls_back_to_the_worker_result_when_the_session_slot_is_invalidated`
asserted the silent fallback as correct behaviour — it was, before F2.1.
Rewritten as `viz_export_refuses_the_worker_result_when_the_session_slot_is_invalidated`,
which now asserts BOTH halves: the default refuses and names the op, and
the acceptance emits the same pre-modulation feed the old test expected.
The file's first test, the actual G-MODEXPORT byte assertion, is
untouched. R0.1 §5 anticipated this rewrite in those words.

No other sentry changed its expectations. F1.9's file was updated for the
rename and for the `FreshnessState` key; every text it asserts is
unchanged, and it gained one assertion (a missing result is never
waived).

Six further tests needed their FIXTURE corrected rather than their
expectation, all of the same shape: they seeded ONLY the viz store and
exported through the silent fallback. That state now reads `EditedSince`
and the gate refuses it — correctly.

- `controller::tests::controller_save_open_and_export_smoke` now seeds
  both stores.
- `tests/wizard_e2e.rs` gained one helper, `seed_generated_result`, which
  writes both stores exactly as `drain_compute_results` does, and its four
  seed sites now call it. `export_with_policy_emits_gcode_from_viz_results`
  was renamed `…_from_the_generated_results`, because its old name
  asserted the store the export must no longer prefer.
- `per_setup_export_puts_identity_setup_in_the_stock_relative_frame` also
  called `set_stock_config` AFTER seeding, which under F2.1's stock rule
  drops every result in the project. It now re-seeds afterwards. That
  failure was F2.1 working, surfaced by F2.3's gate; nothing was weakened
  to make it pass.

Every assertion in all six is unchanged. Worth knowing for the next
fixture author: **seeding `gui.toolpath_rt[..].result` alone no longer
means "generated"**, and a stock edit after seeding un-generates
everything.
