## What was wrong

Three copies of the rule "does this Rest op have an operation to follow?"
existed in `crates/rs_cam_viz`, and one of them disagreed with the other two.

- `ui/toolpath_panel.rs::draw_rest_badge` accepted ANY other toolpath in the
  same setup that used the previous tool. It did not read plan order, the
  `enabled` flag, or the model. A Rest card dragged above its roughing pass
  kept a green `dep`; a Rest card whose roughing pass was disabled kept a
  green `dep`; a roughing pass on another model counted.
- `ui/properties/operations/mod.rs::has_prior_rest_source` (called by
  `validate_toolpath`) required an EARLIER, ENABLED toolpath in the SAME
  setup, on the SAME model, with the previous tool. This is the rule the
  Generate button refuses on.
- `validate_toolpath_config` (the GUI worker's pre-submit validator,
  `controller/events/compute.rs:220`) carried an inline copy of the
  validator's rule.

So the card could say "dependency present" for an operation the generator
refused, and the inspector said "Rest machining requires an earlier enabled
operation …" at the same time.

  `RestCandidate { id, tool_id, model_id, enabled }` with

  `SetupData::toolpath_indices`);
  `rest_predecessors(candidates, rest_id, rest_model_id, prev_tool_id) -> Vec<ToolpathId>`
  (every qualifying predecessor, in plan order; empty when `rest_id` is not

- `crates/rs_cam_viz/src/ui/toolpath_panel.rs` — new `pub enum RestBadge
  { Resolved, Stale, Missing }` with `text()` (`"dep"` / `"dep"` /
  `"no dep"`), and `pub fn rest_badge(&AppState, &RestConfig, ToolpathId) -> RestBadge`,
  pure with respect to egui. It calls `rest_predecessors_in_session` with

  `draw_rest_badge` maps the enum to the three theme colours; label text

  still passes the DRAFT entry's `model_id`, so an inspector edit that moves

- `crates/rs_cam_viz/tests/rest_badge_one_predicate_g_restbadge.rs` — the

- `planning/ui_fix_2026-09-09/reports/F1.8.md` — this report.

## The predicate and its callers

One rule, three call sites:

| Caller | Before | After |
|---|---|---|
| `toolpath_panel::rest_badge` (card badge) | own rule: any other toolpath, same setup, previous tool | `rest_predecessors_in_session(session, tp_id, stored model, prev_tool_id)` |
| `operations::validate_toolpath` (inspector, Generate button) | `has_prior_rest_source` own body | `has_prior_rest_source` → `rest_predecessors` |
| `operations::validate_toolpath_config` (worker pre-submit) | inline copy of the validator's body | `has_prior_rest_source` → `rest_predecessors` |

The Rest generator itself (`rs_cam_core::compute::execute`) reads only the
previous tool's analytic radius and never a predecessor toolpath; that is
unchanged and out of scope (R05 §1).

two 2D models, one or two setups), adds toolpaths through
`session.add_toolpath`, registers a `Done` runtime per toolpath, then asks
BOTH surfaces (`rest_badge` and `validate_toolpath` via
`ToolpathValidationContext::from_session`) and asserts they agree.

| Case | Setup | Expected on both |
|---|---|---|
| (a) | only candidate is BELOW the Rest op | `no dep`, validator refuses |
| (b) | candidate above, `set_toolpath_enabled(false)` | `no dep`, validator refuses |
| (c) | candidate above, enabled, same setup and model, previous tool | `dep` (`Resolved`), validator passes |
| (c2) | as (c) with the candidate's runtime `Pending` | `dep` (`Stale`), validator passes |
| (d) | candidate in setup 0, Rest op in a second setup (`add_setup`, `FaceUp::Bottom`) | `no dep`, validator refuses |
| model | candidate above but on the other model | `no dep`, validator refuses |
| tool | candidate above but with the Rest op's own tool | `no dep`, validator refuses |
| unset | `prev_tool_id: None` | badge `Missing` |
| unit | `rest_predecessors` on a hand-built list returns the qualifying ids in plan order and nothing for an unknown Rest id | — |
