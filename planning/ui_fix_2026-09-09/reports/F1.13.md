## The completeness rule — G-WSMENU

**Claim.** Readiness added to the Workspace menu, with an
`overlays_registry`-style completeness test.

**Confirmed.** `Workspace` has four variants (`state/mod.rs`). The switcher
bar (`ui/workspace_bar.rs`) named all four; the Workspace menu
(`ui/menu_bar.rs`) named three, hard-coded one `ui.button("…")` at a time.
Readiness has been on the tab bar since W3.8 and was never added.

**Not a reachability defect, and the review says so.** `IA/CURRENT_MAP.md` §1:
"Readiness remains available by tab; this omission is not a claim that
Readiness is unreachable." So the interesting half is the rule, not the entry.

**What it really was: four hand-written copies of one enumeration** —
`menu_bar.rs`'s three buttons, `workspace_bar.rs`'s four `workspace_tab`
calls, `workspace_bar.rs`'s four-arm `hint` match, and `app/mcp.rs`'s
`workspace_keys_round_trip` test, which iterated a literal
`[Setup, Toolpaths, Simulation, Readiness]`. That last one is the sharpest
illustration: the test whose job is to prove every variant round-trips could
itself miss a variant, because it re-typed the list.

**Changed.**

- `crates/rs_cam_viz/src/state/mod.rs::Workspace` — `ALL`, `order()`,
  `label()`, `hint()`. `ALL` is the one list; `label` and `hint` move the two
  string tables off `workspace_bar.rs` onto the enum.
- `crates/rs_cam_viz/src/ui/menu_bar.rs` — the Workspace menu iterates
  `Workspace::ALL` and prints `target.label()`. Readiness appears as a
  consequence, not as a fifth hand-written arm.
- `crates/rs_cam_viz/src/ui/workspace_bar.rs` — the bar iterates the same
  list. The badge stays a per-tab `match` because each badge reads different
  state; the ORDER and the labels no longer live here. Order and labels are
  unchanged, so the bar looks identical.
- `crates/rs_cam_viz/src/app/mcp.rs::workspace_keys_round_trip` — iterates
  `Workspace::ALL` instead of its own copy. This is hardening, not a defect
  fix: the copy happened to be complete.

**How the rule is enforced.** `order()` is an exhaustive `match`, so a new
variant does not COMPILE until it is given a position; the sentry then fails
unless that position is a real, unique slot in `ALL`, and unless every slot is
claimed. The pair is what makes `ALL` complete rather than merely four items
long — a bare `assert_eq!(ALL.len(), 4)` would be a hand-maintained number,
which is the defect this is meant to end.

**Scope note, as asked.** This was NOT a larger refactor than F1.13 warrants,
so the full assertion is pinned and no weaker one was substituted. What is
still per-surface: the badge functions (three different state reads), the
per-workspace layout `match` in `app.rs`, and the per-workspace overlay
defaults in `ui/overlays/registry.rs`. Each is behaviour rather than a list,
and each already has an exhaustive `match` that will not compile without a new
variant's arm, so none is a missing-entry risk of the kind fixed here.

## Getting started: review before export

**Claim.** The list gains "Simulate and review" before "Export".

**Confirmed.** The list ran 1–5 with "5. Generate and export G-code" — one
step carrying two actions and no verification between them.

**Changed.** `ui/properties/mod.rs`, three steps in place of one:

| before | after |
|---|---|
| 5. Generate and export G-code | 5. Generate toolpaths |
| | 6. Simulate and review |
| | 7. Export G-code |

Generate is split out rather than left welded to export, because otherwise
"Simulate and review" would have to sit either before generation (nothing to
simulate) or inside the export step (not a step). This list is the first thing
a new operator reads, and it ended by walking them from a generated path
straight to the machine.

## Camera Fit on `load_project`

**Claim.** Camera Fit on `load_project`. **Match the interactive import path
rather than inventing a second fit.**

**Confirmed.** `ProjectSession::open_job_from_path` has three call sites and
none of them touched the camera:

| route | file | before |
|---|---|---|
| `RS_CAM_JOB` at startup | `app.rs` | no fit |
| File > Open | `app/input.rs`, `AppEvent::OpenJob` | no fit |
| MCP `load_project` | `app/mcp.rs::mcp_load_project` | no fit |

The import dispatch beside them has always fitted:
`AppEvent::ImportStl` / `ImportSvg` / `ImportDxf` / `ImportStep` and
`RescaleModel` call `fit_camera_to_bbox` on the returned bbox, and the 2D arms
fall back to `fit_camera_to_first_model`. A project load replaces every model
in the project, so it is the same situation and it kept the previous project's
framing.

**Changed.** All three routes call `fit_camera_to_first_model()` — the routine
`AppEvent::ResetView` already uses. No second fit was written. `open_job_from_path`
returns `Result<(), VizError>` and no bbox, so `fit_camera_to_first_model` is
also the only one of the two that fits: it walks the loaded models itself and
falls back to a fresh `OrbitCamera` when the project has none.

**The startup route needed different handling.** `RS_CAM_JOB` is loaded inside
`RsCamApp::new`, BEFORE the struct — and therefore the camera — exists. It now
records `loaded_a_job` and fits once the app is built. Without that, an
`RS_CAM_SCREENSHOT` run would frame an empty default scene.

**Does MCP `load_project` get it too? Yes — deliberately.** An agent's next
call after a load is usually `screenshot_gui` or `screenshot_toolpath`, and
before this the viewport still held the previous project's framing. It changes
the camera only, which is a view and not project data, and it is the same fit
the human File > Open route now does. An agent that wants a specific framing
sets it after the load, as it must already do after an import.
