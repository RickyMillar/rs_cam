# J6 — F1.16 / G-SCHEMAENUM: the operation schema advertised six values no config can hold

Date: 2026-09-10. Branch: `core-consolidation`.

## The ruling: DROP the value, do not implement the arm

F1.16 offered two ways out — implement an on-the-line profile arm, or drop
`on` from the schema. I dropped it. The reason is not that the arm is hard.
It is that **the on-the-line cut already ships in this repo, twice, under the
repo's own names**:

- `project_curve` with `side: center`. `ProjectCurveSide::Center`'s doc reads
  "Tool centerline rides exactly on the curve", and its `label()` is
  literally **"On Line"**.
- `trace` with `compensation: none`. `TraceCompensation::None`'s doc reads
  "No compensation — tool center follows the path exactly".

A third spelling on `ProfileSide` would not add a capability. It would claim
the capability lives somewhere it does not, which is a new untruth of exactly
the kind the brief forbade.

Nothing was lost by dropping it. Nothing in the workspace stores
`side = "on"`, and both GUI surfaces (`boundary_2d.rs`, `properties/mod.rs`)
already offer two values only.

## The `enum:` string is documentation, and nothing validates it

`ProjectSession::set_toolpath_param` never parses it. It merges the value
into the config's own JSON and hands the result to serde
(`session/compute.rs:407-525`); `param_type_name` is read only to decide
numeric coercion. So an advertised value that serde rejects reaches the
operator on two surfaces and fails on neither of them until they type it:

- MCP `get_operation_schema`
- the CLI `PARAM / TYPE / OPTIONAL` table (`rs_cam_cli/src/run.rs:219`)

Dropping the value therefore changes no behaviour. It changes what the two
surfaces claim.

## Red first — and the sentry found three more

The pre-fix probe, verbatim:

```
J6: profile 'side' schema = enum:on|inside|outside
J6: serde REJECTED 'on' -> unknown variant `on`, expected `outside` or `inside`
J6: project_curve 'side' schema = enum:center|inside|outside (its Center variant is labelled 'On Line')
```

The sentry is deliberately generic — the claim is "no operation advertises a
value its config cannot hold", not "profile is fixed". Its first run found
**six bad values across four operations**, verbatim:

```
G-SCHEMAENUM: 24 operations, 20 enum params, 53 advertised values
  REJECTED: Profile.side advertises 'on' (enum:on|inside|outside) — unknown variant `on`, expected `outside` or `inside`
  REJECTED: Trace.compensation advertises 'center' (enum:center|left|right) — unknown variant `center`, expected one of `none`, `left`, `right`
  REJECTED: Scallop.direction advertises 'x' (enum:x|y) — unknown variant `x`, expected `outside_in` or `inside_out`
  REJECTED: Scallop.direction advertises 'y' (enum:x|y) — unknown variant `y`, expected `outside_in` or `inside_out`
  REJECTED: SpiralFinish.direction advertises 'outward' (enum:outward|inward) — unknown variant `outward`, expected `inside_out` or `outside_in`
  REJECTED: SpiralFinish.direction advertises 'inward' (enum:outward|inward) — unknown variant `inward`, expected `inside_out` or `outside_in`
```

Three of the four are worse than F1.16 in one way: **both** advertised values
are unusable, so the whole parameter is unsettable through MCP and the CLI
prints a dial that cannot be driven. `Scallop.direction` names `x|y`, a
raster-axis dial `ScallopConfig` does not have at all.

## What changed

`crates/rs_cam_core/src/compute/catalog.rs`, four `ParamDef` rows, each with a
comment naming the correction:

| Operation | Was | Now | Kind of fix |
|---|---|---|---|
| `Profile.side` | `enum:on\|inside\|outside` | `enum:inside\|outside` | value DROPPED — no such capability here |
| `Trace.compensation` | `enum:center\|left\|right` | `enum:none\|left\|right` | wrong spelling of an existing variant |
| `Scallop.direction` | `enum:x\|y` | `enum:outside_in\|inside_out` | stale row, names a dial that does not exist |
| `SpiralFinish.direction` | `enum:outward\|inward` | `enum:inside_out\|outside_in` | wrong spelling of both variants |

The three renames are not new claims. Each names the variant the code already
has, in the spelling serde already accepts. No enum gained or lost a variant,
and no generator changed.

`crates/rs_cam_core/tests/schema_enum_values_g_schemaenum.rs` — the sentry.
It walks `OperationType::ALL`, builds the default config for each, and
round-trips every advertised enum value through the same JSON merge
`set_toolpath_param` uses. It carries a non-vacuity floor (at least ten enum
params must be measured) so an empty population cannot pass it green.

Nothing in the workspace stored any of the four retired spellings, checked
across every `.toml` and `.json` outside `target/`.

## What this does NOT prove

That the generator does something DIFFERENT for each advertised value. Serde
accepting `climb=false` says nothing about whether the path reverses. That is
a per-operation question and it needs per-operation evidence.
