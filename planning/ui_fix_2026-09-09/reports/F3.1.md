## 1. The event, and that it really is the widget's own

Unlike F3.7 there IS a real widget event, and the tool dispatches it.

- `crates/rs_cam_viz/src/ui/toolpath_panel.rs`, in `add_op_menu_item`'s
  click arm: `events.push(AppEvent::AddToolpath(op));` — that is the Add
  menu, and it is the ONLY producer of that variant outside tests.
- `crates/rs_cam_viz/src/controller/events/mod.rs`, in
  `handle_internal_event`: `AppEvent::AddToolpath(op_type) =>
  self.handle_add_toolpath(op_type)`.
- The handler is `controller/events/toolpath.rs::handle_add_toolpath`.

`mcp_add_toolpath_via_gui` calls
`self.controller.handle_internal_event(AppEvent::AddToolpath(op_type))`.
That is the same public entry point `controller/tests.rs` already uses for
this event in four places, and it runs the real dispatcher rather than
reaching for the handler directly. **No binding logic is reimplemented
beside it** — not the `tools().first()` pick, not the Suggest call, not
the `models().first()` fallback, not the B.7 boundary auto-enable. If the
GUI path and a direct core add ever diverge, this tool shows the
divergence; that is the point of having it next to `add_toolpath`.

`setup_index` needs care, because `handle_add_toolpath` takes no setup
argument: it derives the target from `self.state.selection`, falling back
to setup 0. So the handler honours a click, not a parameter. The tool
therefore does what a click does — sets `Selection::Setup(id)` for the
named setup and *then* raises the event. An out-of-range `setup_index` is
refused BEFORE the event is dispatched, so a typo never reaches the GUI
path and never leaves a toast on the operator's screen. Omitting
`setup_index` leaves the selection alone, which is what the operator's
next click would do and is not necessarily setup 0; the tool description
says so.

## 2. What the reply carries, and why it has to read the toast stack

`handle_add_toolpath` returns `()`. On every refusal path — no tools
(R0.3 §2.2 row A3), tool not found, the Suggest door (row A1), no models
for a non-stock op (row A4) — it calls `push_notification(...)` and
returns. **The refusal text exists nowhere else.** There is no `Result`,
no error field, nothing on the config. So the reply is built by observing
the controller either side of the dispatch:

| Reply field | How it is obtained |
|---|---|
| `created` | ids snapshotted before; after, the one config whose id is new — its index, id, name, operation, setup index, and the tool/model it bound with their names |
| `refusal` | the first non-`info` toast this call pushed, verbatim |
| `notifications` | every toast this call pushed, as `get_notifications` formats them |
| `ok` | `true` when a toolpath appeared, `false` when none did |

Both snapshots read `AppController::notifications()` — the accessor F3.5
adds. That is the pairing the brief asked for: F3.1's "whether a
notification was pushed" is not a separate story it tells about itself,
it is the same stack `get_notifications` publishes, read through the same
method. A test can assert F3.1's `notifications` array and then confirm
it against a `get_notifications` call.

Two details worth stating because they could have been done carelessly:

- The tail is read by INDEX (`skip(toasts_before)`), not by counting one.
  The GUI path pushes at most one toast today, but nothing enforces that,
  and a count of one would silently mis-attribute if it ever pushed two.
  `the_stack_only_grows_so_the_tail_belongs_to_the_latest_add` pins the
  property the tail read depends on.
- The new toolpath is found by id-set difference, not by
  `len() - 1`. `add_toolpath(setup_idx, tc)` inserts into the setup's
  ordering, so the new row is not necessarily last.

## 3. The one deliberate exception to F1.1

**The `AddToolpathViaGui` dispatch arm pushes no toast of its own.**

F1.1 (G-MCPTOAST) made thirteen synchronous arms push their toast AFTER
the handler and FROM its reply, because those handlers push none
themselves. This handler is different: it is the GUI's add path, and it
has already pushed exactly the toast F1.1 asks for — the refusal text, at
Warning, after the work. A `push_mcp_outcome` on top would put a second
Warning on the screen for one request, which is the very thing F1.1's
`a_refused_add_toolpath_shows_the_refusal_and_never_added` asserts against
("exactly one Warning toast"). Honouring F1.1's rule here means adding
nothing. The arm carries that reasoning as a comment, and it adds zero
`push_notification(` calls, so F1.1's
`only_the_progress_toasts_bypass_the_outcome_door` census (which counts
bare calls in `app/mcp.rs` and requires exactly the three progress
toasts) is unaffected.

The arm does still switch the workspace to Toolpaths, as the
`SetToolpathParam` arm does, so the operator is looking at the thing that
just changed — or at the place the toast is talking about.

`RsCamApp` needs an `eframe::CreationContext`, so the dispatch arm itself
cannot be constructed in a test — the limit F1.1 recorded and worked
around the same way. What is driven here is the controller the arm calls
into, through the same public entry point, so the untested gap is the
twenty lines of the arm, not the behaviour.

Note what `the_gui_binds_the_first_tool_even_when_a_compatible_one_is_second`
asserts: that the add is REFUSED. R0.3 §4.3 proposes changing exactly
this (bind the first tool that `accepts_tool`, create the op blocked). Its
message says so, so when F4.2 lands and the assertion trips, the next
reader knows it is the contract arriving rather than a regression, and
that F4.2's own test then owns the case.

## 8. What this task did NOT do

1. **It changes no behaviour.** `handle_add_toolpath` is untouched. The
   add-time refusals (A1, A3, A4) still refuse, the binding is still
   `tools().first()` / `models().first()`, and the toast texts are
   unchanged. This task makes that path observable; F4.2 changes it.
2. **The dispatch arm is not driven end-to-end**, for the `RsCamApp`
   reason above. A headless `RsCamApp` constructor would close this and
   would close F1.1's equivalent gap at the same time.
3. **No live call.** The MCP server was down. Nothing here was exercised
   over the wire, and the "live parity test" §5 asks for is satisfied at
   the controller layer, not through the server.
4. **`setup_index` moves the selection as a side effect** — deliberately,
   because that is how the GUI reaches a setup, but it means a caller who
   passes it has also changed what is selected. The description says the
   parameter selects the setup; it does not say the selection is restored
   afterwards, because it is not.
5. **No `blocked` list.** R0.3 §3.3 wants `add_toolpath` to return one;
   that is F4.2's, and this tool reports today's refusal instead.
