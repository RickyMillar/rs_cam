---

## 1. The race, and why only one arm of it was exposed

An operator presses G on a 3D operation, the generation runs for a while, and
they change a parameter while it runs. The result that lands was computed from
the parameter set they just left.

Before this, `drain_compute_results` wrote it into `session.results` — which
is exactly what `FreshnessState` reads for `Current`. So the edit was silently
answered by geometry that predates it: the card said `OK`, the inspector said
`Done`, Readiness counted it current, and F2.3's export gate would have let
the file through. The edit itself had correctly dropped the core result
(F2.1); the arriving result put one back.

**The auto-regen arm was already safe, by a route that has nothing to do with
freshness.** A second edit re-stales the toolpath, the 500 ms sweep resubmits,
the resubmit supersedes the running job, and G-REGEN-RACE drops the abandoned
result before it reaches the store —
`a_param_edit_mid_generate_regenerates_without_a_pending_flicker` pins that.
**Nothing supersedes on a manual-regen operation.** The operator is the only
thing that resubmits, and they have no reason to: they just watched it
generate. That is why the PLAN row names the 3D manual-regen arm specifically,
and it is the arm this closes.

## 2. What changed

| Symbol | Change |
|---|---|
| `state::runtime::ToolpathRuntime::submitted_revision` (new `Option<u64>`) | `ProjectSession::toolpath_revision` as it stood when the toolpath was last handed to the lane. Cleared by `clear_runtime` with the rest. |
| `controller::events::compute::submit_toolpath_compute` | Stamps it immediately before `compute.submit_toolpath`. |
| `controller::events::compute::drain_compute_results`, `Ok` arm | Compares the stamp against the revision now. On a mismatch it skips `insert_result` and stores the result on `rt.result` only. |

That is the whole change. **The mechanism was already there and F2.1 said
so**: `drop_result` bumps `toolpath_revision`, and `insert_result`
deliberately does not — a generation is not an input change. This task is the
first consumer of that counter.

The stamp lives on the GUI runtime rather than riding the `ComputeRequest`
round trip. The request crosses a thread boundary and is an input to
generation; which configuration the GUI *believed* it was submitting is
GUI-side bookkeeping and does not belong in it. The two are equivalent here
because at most one job per toolpath is in flight — a resubmit supersedes, and
the superseded result is dropped before the comparison — and the auto arm's
sentry pins that.

Absent stamps are treated as agreement (`None` on either side ⇒ accept). A
result for a toolpath this controller never submitted, or one that has since
been removed, is not a mismatch this guard can honestly claim.

## 3. Point 2 — stored, not discarded

The row says *stored but marked stale*, and I agree with it; I did not need to
argue the other way, but here is why it is right rather than merely
instructed.

A 3D finish on a real terrain is minutes of compute. Discarding its result on
arrival would cost the operator all of it and leave them with a card that says
`STALE` and a viewport that says nothing — and the reason it vanished would be
invisible, because nothing on any surface would distinguish "your edit
cancelled a generation you were watching" from "it never ran". Keeping it
costs one `Arc` the GUI was holding anyway and buys a drawable picture of the
parameter set they just left, which is frequently the thing they want to
compare against.

The three halves of the row are asserted separately in the sentry:

- **stored** — `rt.result.is_some()`;
- **marked stale** — `session.get_result(idx).is_none()`, so
  `freshness` derives `EditedSince`;
- **never shown as current** — `state_of(..) == EditedSince`, which is what
  every surface F2.2 wired reads and what F2.3's gate refuses on.

One consequence worth stating: `rt.status` is `Done`, because the generation
did finish. That is not a contradiction — `ComputeStatus` describes the lane,
`FreshnessState` describes whether the answer is current, and the whole point
of R0.1 was that those are different questions. `freshness` puts the lane's
status first, so **while the job is still running the state is `Regenerating`,
not `EditedSince`** — the operator is told work is in progress rather than
that their edit is unanswered. The sentry asserts that intermediate state too,
because it is easy to "fix" it into a wrong answer.

## 4. Point 3 — extending the existing sentry

`a_param_edit_mid_generate_regenerates_without_a_pending_flicker` is the auto
arm. The new tests sit directly beside it, share its fixture
(`freshly_loaded_controller`, `LaneModelBackend`) and name it in their doc:

- `a_param_edit_mid_generate_manual_arm_keeps_the_edit_g_lateresult` — the arm
  the row names. It flips `auto_regen = false`, presses G through the real
  `AppEvent::GenerateToolpath`, edits through the panel's own write-back
  (`panel_edit`, the same door every inspector edit uses), finishes the lane
  job and drains. It also asserts `!superseded_toolpaths.contains(&tp_id)`, so
  the test cannot silently become a second copy of the auto arm.
- `a_manual_generate_with_no_edit_is_accepted_g_lateresult` — the other side.
  A guard that rejected every result would pass the first test and break the
  application; this is what stops that.

No parallel test file was written. R0.1 §5 names this sentry
`a_late_result_for_an_edited_config_is_not_current_g_lateresult`; I kept the
`a_param_edit_mid_generate_*` prefix instead so it sorts and reads beside the
arm it extends, which is what the row asks for. Same subject, same fixture,
same file.

## 7. What this task did NOT do

- **It did not touch core.** `git status crates/rs_cam_core/` is empty.
  `toolpath_revision` was already public; F2.1 built it for this.
- **It did not add a notification.** A late result now lands as `STALE` with
  no toast. The operator edited the parameter, so the state is not a surprise;
  and a toast on every superseded generation would fire on the auto arm too,
  where it is routine. If the operator wants to be told, that is a
  notification-policy decision, not a state one.
- **It did not request an automatic regeneration on mismatch.** On a
  manual-regen operation that would defeat the `MAN` badge, which exists
  precisely so a 3D op does not resubmit itself.
- **It did not cover the simulation half.** R0.1 §5 lists a second F2.4
  sentry, `simulation_stamps_edit_counter_at_submit_g_latesim` — an edit
  during a running simulation must leave `is_stale` true after the drain. The
  PLAN row does not mention it and it is a different mechanism
  (`SimulationState::is_stale` over `edit_counter`, not the per-toolpath
  revision). **Ledger it** — see §8.
- **Nothing was verified live.** No GUI, no MCP.
