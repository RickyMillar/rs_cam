---

## 1. The ruling: I agree, and here is the reasoning in full

`no_freshness_text_promises_that_export_is_gated` was written under F2.2,
against a head where F2.3 had not landed. At that moment an operation whose
card read `STALE` could still export its old geometry, because
`emitted_result_toolpath` fell back to the GUI's retained result. The risk
was therefore that a freshness string would over-promise — that a display
notice would be read as a safety claim the programme had not earned — so the
test refused the word "export" anywhere near "stale" or "edited since".

F2.3 merged. The gate exists: an edited operation blocks the file, is named,
and the sentence comes from one builder shared by export, the pre-flight
modal and MCP `export_gcode` (`io::export::blocking_toolpath_message`).

The old guard still passed, because it scanned only two files. That is the
worst way for a test to be wrong — **silently**. Two things were now untrue
about it:

- **Its failure message asserted a falsehood.** "F2.3 has not landed the gate
  and a stale operation still exports" would have been printed to whoever
  tripped it, and they would have believed it.
- **It forbade a true sentence.** A future card chip or inspector line saying
  "this will not export until you regenerate" is now correct, useful, and
  exactly the kind of thing D1/D3 might add. The guard would have refused it
  and sent its author looking for a hole that had been filled.

**The lead's reading is right and I am not overturning it: the risk
inverted.** It is no longer over-promising. It is a second surface explaining
WHY an operation blocks, in its own words, and drifting from the one builder.
That is the shape of every defect this phase has closed — three freshness
stores in R0.1, four hand-written workspace lists in G-WSMENU, two chip
vocabularies in F2.2 — and a card that says "cannot export: regenerate first"
while the pre-flight says "…regenerate it, or accept the previous geometry to
cut it as it was" is the same class of thing, one wording short of a
contradiction.

## 2. What the guard protects now

Renamed to `no_freshness_surface_writes_its_own_export_blocking_sentence`.
The rule:

> A freshness surface may SAY an operation will not export. The sentence
> comes from `io::export::blocking_toolpath_message`, not from a literal the
> surface wrote itself.

Mechanically:

- Scans four surfaces, up from two: `toolpath_panel.rs`, `readiness_panel.rs`,
  `workspace_bar.rs`, `properties/mod.rs`.
- A file that calls `blocking_toolpath_message` is skipped — it is using the
  one text by construction, and the rule is about surfaces that do not.
- Within a file, a **string literal** mentioning "export" fails only if it
  also carries a blocking claim: `cannot`, `can't`, `won't`, `will not`,
  `unable`, `block`, `refus`, `prevent`, `not be export`.
- Comments are exempt. Several discuss the gate, and should be free to.

The word "export" alone is fine, and had to be: `readiness_panel.rs` carries
an "Export G-code…" button and `properties/mod.rs` a Getting-started step
that reads "7. Export G-code". Both survive, which is the test of whether the
rule is drawn in the right place.

A second test, `the_shared_blocking_text_is_available_to_a_freshness_surface`,
asserts `blocking_toolpath_message` stays public and stays keyed on
`FreshnessState`. A rule that says "call this instead" is only fair if a
surface can, and only useful while the builder can still say the thing an
edited operation needs said.

## 3. Shown to bite

The lead said an own sentry is not required for changing a test's subject.
A guard that has never failed is a guard nobody has checked, so I injected
the exact violation it exists to catch — a card chip writing its own
export-blocking sentence — and confirmed it fails, then reverted:

```
---- no_freshness_surface_writes_its_own_export_blocking_sentence stdout ----
toolpath_panel.rs:697: this surface writes its own export-blocking sentence
(matched "cannot"). That text has ONE home since F2.3 —
`io::export::blocking_toolpath_message` — which export, the pre-flight modal
and MCP `export_gcode` all share. Call it instead of writing a second wording
that can drift from it:
            "STALE — this operation cannot be exported until you regenerate it",

test result: FAILED. 5 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out
```

The injected line is not in the commit. Note what the message now does that
the old one did not: it names the builder to call, rather than asserting a
state of the world that can go stale.

## 4. What this task did NOT do

- **No production code changed.** `git diff --stat` is one test file and this
  report. The injected violation was reverted before staging.
- **It did not delete the test.** Deleting it would have left the four
  surfaces free to grow their own refusal wording, which is the live risk.
- **It did not duplicate F2.3's own sentry.**
  `export_refuses_stale_result_g_stalexport.rs::preflight_rows_and_the_export_refusal_share_one_text`
  already pins that export and the pre-flight agree. This guard covers the
  surfaces F2.3 does not touch — the card, the chips, the inspector, the
  Readiness row.
- **It did not add a freshness surface that says anything about export.**
  None of them does today. The guard is about what happens next, not about a
  change made here.
