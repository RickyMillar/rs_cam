## 1. What changed

`controller/io.rs::open_job_from_path` built every toolpath runtime as
`ToolpathRuntime::new(true)` with `stale_since = Some(loaded_at)`,
regardless of the operation's own `default_auto_regen()`. Five hundred
milliseconds after any load, `process_auto_regen` submitted **every**
operation — including the 3D families whose card says MAN and whose
generation is minutes, not milliseconds.

Both loader arms now follow the operation's own dial:

| Arm | Before | After |
|---|---|---|
| Session loader | `ToolpathRuntime::new(true)`, `stale_since` always set | `ToolpathRuntime::new(tc.operation.default_auto_regen())`; `stale_since` set only when that is true |
| Legacy fallback loader | `ToolpathRuntime::new(tp.auto_regen)`, `stale_since` always set | same runtime dial, and `stale_since` now follows it |

`OperationConfig::default_auto_regen()` is `true` for the 2.5D families
and `false` for the twelve 3D ones (`REG_DROP_CUTTER`, `REG_ADAPTIVE3D`,
`REG_WATERLINE`, `REG_PENCIL`, `REG_SCALLOP`, `REG_UNIFIED_FINISH`,
`REG_STEEP_SHALLOW`, `REG_RAMP_FINISH`, `REG_SPIRAL_FINISH`,
`REG_RADIAL_FINISH`, `REG_HORIZONTAL_FINISH`, `REG_PROJECT_CURVE` —
`crates/rs_cam_core/src/compute/catalog.rs`). Nothing in the registry was
touched; this reads a dial that was already there and was being ignored.

The legacy arm's change is the smaller half but the same defect: it
already carried a per-operation `auto_regen` from the file, and then set
the regeneration request on every operation anyway — which the sweep
ignored for the manual ones, so the request was simply a lie left in the
runtime.

## 2. Caution 1 — `NoResult` must not read as a failure

A freshly loaded 3D operation now reads `FreshnessState::NoResult`. That
is the same state a never-generated operation has always had, so no
surface needed a new arm; what I checked is that none of them *treats* it
as failure. All ten, read at HEAD:

| Surface | What it shows for `NoResult` | Alarm? |
|---|---|---|
| Card chip (`toolpath_panel::status_chip`) | `PEND`, `theme::TEXT_DIM`, no hover | no — dim grey, and `ERR` is a separate arm |
| Card row 3 / ▶ | no figures; Generate offered | no |
| Inspector header (`properties/mod.rs`) | `"Ready"` | no |
| Viewport | nothing drawn (there is no result) | no |
| Workspace Toolpaths chip | counted in `N pending` | amber, and true — work is outstanding |
| Workspace Readiness chip | counted in `N uncomputed` | amber, and true |
| Readiness Operations row | `0/2 current`, `CheckStatus::Warning` | Warning, not Fail |
| Pre-flight modal | `Fail` row, `'X' is not generated` | yes — but only inside the export pre-flight, where it genuinely blocks (F1.9's rule, unchanged) |
| Export gate | refuses, naming it | correct, unchanged |
| MCP `list_toolpaths` | `"freshness": "no_result"` | no |

The one red thing is the pre-flight row, and it is red for the right
reason: an ungenerated operation does block the export, exactly as it did
before F2.6 for an operation the operator had never generated. Nothing
says or implies that something went wrong with the load.

`Warning` rather than `Fail` on the Readiness row is the distinction that
matters here, and it is asserted:
`a_fresh_load_counts_as_pending_never_as_stale`. The other count that
carries meaning — `stale` — is **zero** on a fresh load, because nothing
has been generated to be wrong. An operator opening a saved job sees "0/2
current", not "2 stale".

## 3. Caution 2 — what G-REGEN-RACE actually is, and what this removes

I checked rather than assumed. G-REGEN-RACE is documented in three
places: `compute/mod.rs` on `ToolpathSubmitOutcome`, the section comment
in `controller/tests.rs`, and `planning/ui_review_2026-09-09/results/W03/support/r08_source_track.md`,
which is the document that names the load as its precondition:

> Because `auto_regen` is forced **true** for every op regardless of
> `default_auto_regen()`, `process_auto_regen` submits **all** of them
> 500 ms after load, including 3D ops that the card labels "MAN". This is
> the G-REGEN-RACE precondition described in `controller/tests.rs`.

The race itself is: an agent's `generate_all` arriving while one of those
load-time submits is still the lane's ACTIVE job resubmits that toolpath;
the lane's resubmit-cancels-and-requeues rule aborts the in-flight job,
and its `Cancelled` used to drain as the toolpath's *outcome*.

**What F2.6 removes is the precondition for 3D operations only.** Precise
statement, because the PLAN row's wording ("Removes the G-REGEN-RACE
precondition") is easy to over-read:

- 3D manual-regen operations are no longer submitted by the load-time
  sweep at all, so the collision window the live reproduction used —
  minutes-long 3D jobs still running when an agent calls `generate_all` —
  is gone.
- **2.5D operations still auto-regenerate on load**, by design: that is
  what the ruling asks for. A 2.5D job is still submitted 500 ms after a
  load and can still be the lane's active job when a `generate_all`
  arrives. The window is far shorter (milliseconds of compute, not
  minutes) but it is not zero.
- **The G-REGEN-RACE fix stays and is still needed.**
  `ToolpathSubmitOutcome::SupersededActive` is what makes a supersede
  distinguishable from an outcome, and nothing in this commit touches it.
  Its sentries still pass.

So: the precondition is removed where it mattered, not eliminated. Saying
otherwise would be the kind of claim this programme exists to stop.

## 6. One thing found on the way, not fixed

`ProjectSession::save` writes its atomic temp file as
`.rs_cam_save_<pid>.tmp` in the project's parent directory
(`crates/rs_cam_core/src/session/save.rs`). Two saves from the SAME
process into the same directory therefore race: both write that one
name, the first rename wins, the second fails with `NotFound`. It cost
three failing tests here before I saw it, and the tests now each use
their own directory.

It is a real defect for any caller that saves two projects concurrently
in one process — no shipped GUI path does, which is presumably why it has
survived — and the fix is a unique suffix on the temp name. **Out of
scope for a UI task and not attempted**; recorded here so it has been
written down once.

## 7. What this task did NOT do

- **The `auto_regen` dial is not persisted per operation.** The session
  project file has no per-operation `auto_regen`, so the session loader
  can only use the registry default. An operator who turns auto-regen off
  on a 2.5D operation gets it back on the next load. The legacy loader
  does carry the flag. Pre-existing; F2.6 changed neither.
- **No change to the 500 ms debounce**, to `process_auto_regen`'s rule,
  or to which operations `generate_all` submits.
- **No change to `ToolpathSubmitOutcome` or anything else in the
  G-REGEN-RACE fix** (§3).
- **No numeric threshold, gate bar, feeds constant or LUT row was
  touched.** No `Cargo.toml`, `.mcp.json` or permissions change.
