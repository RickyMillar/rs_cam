## 1. The mechanism

`AppController::rescale_model`
(`/home/ricky/personal_repos/rs_cam_wt_p1/crates/rs_cam_viz/src/controller/io.rs`)
re-imports the model at the new declared units and replaces its geometry
through `LoadedModel::adopt_geometry`, so every polygon moves by the unit
scale — 25.4× from millimetres to inches. It then did four things and none
of them was an invalidation:

| pre-fix step | |
|---|---|
| `model.adopt_geometry(new_model)` | the geometry moves |
| `model.units = Some(new_units)` | the declared units follow |
| `stock_mut().update_from_bbox` | mesh models only, under `auto_from_model` |
| `pending_upload = true` / `gui.mark_edited()` | the viewport redraws |

**No `invalidate_model`. No stale sweep.** So every dependent toolpath
result stayed cached, every card stayed green, and export emitted a path
generated against geometry that no longer existed.

The two sibling doors in the same file do it properly, and this fix copies
their shape exactly:

```rust
let affected = self.state.session.invalidate_model(model_id.0);
let now = Instant::now();
for index in affected {
    if let Some(tc) = self.state.session.get_toolpath_config(index) {
        let id = tc.id;
        self.state.gui.toolpath_rt_or_default(id).stale_since = Some(now);
    }
}
```

`ProjectSession::invalidate_model`
(`.../crates/rs_cam_core/src/session/mutation.rs:1105-1118`) filters on
`tc.model_id == model_id`, drops those results and clears the simulation. It
is NOT `drop_all_results` — a toolpath bound to a different model keeps its
result, and the sentry pins that.

`reports/F4.4.md` §6 recorded the priority: the rescale door turned out to be
the WORST of the three arms of G-RELOADTARGETS (25.4× out, not one version
stale), so the door whose targets F4.4 repaired was also the door that still
shipped stale results.

## 2. The `ModelKind::Step` early return — checked, and NOT given the sweep

The brief asked. The answer is **no sweep there, deliberately.**

`rescale_model` reads the record, and if `model.kind == Some(ModelKind::Step)`
it returns `Ok(None)` **before** it calls `import::import_model`. Nothing is
re-imported, nothing is assigned, no geometry moves and the declared units do
not change. A door that changed nothing must invalidate nothing — otherwise
the invalidation is no longer tied to the geometry being replaced, and an
operator would lose a project's worth of results by opening a combo and
picking the value that was already there.

The reason the STEP arm exists at all is that `io::load_model_file` reports
`units: Some(ModelUnits::Millimeters)` for a STEP file whatever the record
declares, having already applied the scale (`LoadedModel::adopt_geometry`'s
doc states this). A STEP model therefore has no unit dial to turn.

`a_step_rescale_changes_nothing_and_drops_nothing` pins the ruling as a
passing test, so a later lane cannot read the omission as an oversight.

### Generic over the door, not over the fixture

The rule is **a door that replaces a model's geometry drops the results of

identical assertion to three doors: rescale (RED), reload (the control), and
the STEP early return (the other side of the rule).

|---|---|---|

### The non-vacuity floor

Three checks, all in the first test:

1. **Both results start cached.** An empty cache would satisfy "the result is
   gone" for free. This is the floor the brief asks for.
2. **Nothing starts stale.** A runtime entry that was already stamped would
   satisfy the stale assertion for free.
3. **The rescale really moves the geometry** — the model's bbox width must
   grow by more than 10×. A door that changed nothing would pass "the result
   is gone" only by being wrong in a different way, and this catches a
   fixture whose import silently failed.

The second toolpath, bound to a DIFFERENT model, is the fourth guard: it
distinguishes `invalidate_model` from `drop_all_results`. A fix that dropped
every result in the project would fail on it.

### Two fixture decisions worth naming

- **The fixture is an SVG, not an STL.** `rescale_model`'s
  `auto_from_model` branch calls `stock_mut().update_from_bbox` when the
  model carries a MESH. An SVG carries none, so `stock_bbox_update` stays
  `None` and the only mechanism under test is the door's own invalidation. I
  also read `ProjectSession::stock_mut`
  (`.../session/mod.rs:1586-1592`): it is a raw accessor and drops no
  results by itself, so an STL fixture would not have gone green pre-fix —
  but the SVG removes the question rather than answering it.
- **`stale_since` is read through `and_then`.** Pre-fix the runtime entry for
  a toolpath may not exist at all, so "absent" must read as "not stale"
  rather than panicking on an unwrap.

## 6. What I did NOT do, and why

- **No regeneration is requested after the rescale.** The door marks stale
  and stops, which is what reload does. Auto-regeneration on a units change
  is a separate behaviour decision and would be a surprise on a large
  project.
- **`rt.result` is kept** (§3). Dropping it would replace a stale picture
  with no picture and would read as "never generated".
- **The picks are not rescaled.** A rescale moves every drill TARGET by the
  unit scale and leaves `selected_holes` where they were. After this lane's
  two fixes, rescaling a drawing that has picks drops the results and the
  regeneration REFUSES with the G-DRILLPICKSTALE sentence — which is the safe
  outcome, and better than the silent 25.4×-wrong hole that shipped before.
  Moving the picks by the same factor is recorded as F4.12 in
  `reports/F4.8.md` §8.
- **No stock refit on rescale beyond the existing one.** `rescale_model`
  keeps its own `auto_from_model` branch, unchanged.
- **`ProjectSession::replace_model_geometry` was not built.** `reports/F4.4.md`
  §6 rejected it and the reasoning still holds: `invalidate_model` is `pub`
  and all three doors now call it, so the core has its invalidation entry
  point.
- **Nothing was verified live.** The MCP server is down and I started no GUI.
  I read the code paths; I did not run them.
- **I ran no cargo command**, so I have not compiled this.
