# J8 — F1.18 / G-DEPTHSTOCKCORE: the depth-beyond-stock caution moves into core

Date: 2026-09-10. Branch: `core-consolidation`. **Core half only — the GUI
switchover is NOT done and must not be assumed.**

## What was missing

F1.6 shipped the rule GUI-side, in
`crates/rs_cam_viz/src/ui/properties/operations/mod.rs`. That reaches the
inspector ribbon and nothing else. MCP `get_toolpath_diagnostics` and the CLI
`project` report both route through
`diagnostics::diagnose_toolpath_inputs`, which never saw it.

Red first, verbatim, on the pre-change tree — a pocket 25 mm deep on an
18 mm board:

```
J8: pocket depth 25.0 on an 18.0 mm board
J8:   core diagnostics = []
J8:   geom.depth_beyond_stock present: false
```

The core list is **empty**. Not "missing one entry" — core had nothing at all
to say about a cut that goes 7 mm into whatever holds the board.

## The wiring, and why it needed no forbidden edit

The stock span was already in scope at the only session call site and was
being thrown away. `session/compute.rs` builds
`height_ctx = self.height_context_for_toolpath(tc)` and then
`ResolvedHeights::from_context(&height_ctx)`; `HeightContext` carries
`stock_top_z` and `stock_bottom_z`, and `from_context` dropped both.

So the change is entirely inside
`crates/rs_cam_core/src/diagnostics/adapters/from_static_checks.rs`:

- `ResolvedHeights` gains `stock_top_z: Option<f64>` and
  `stock_bottom_z: Option<f64>`. `None` means **NOT MEASURED**, never "the
  cut is inside the board".
- `from_context` fills them from the context it already receives.
- `heights_checks` gains the operation (it is a private function; its one
  caller already holds `op`).
- New: `DepthBeyondStock`, `depth_beyond_stock_applies`,
  `depth_beyond_stock`, `DEPTH_BEYOND_STOCK_EPS_MM`.
- `crates/rs_cam_core/src/diagnostics/ids.rs`: `GEOM_DEPTH_BEYOND_STOCK`,
  added to `ids::ALL`.

**No public signature changed**, so `diagnostics/diagnose.rs` and
`session/compute.rs` are untouched — and `session/**` is forbidden to me this
round. The caution reaches MCP and the CLI the moment this lands.

The id string is `geom.depth_beyond_stock`, deliberately the same string the
GUI rule uses, so the eventual switchover is a deletion there rather than a
rename for the operator. The sentence is byte-identical too:
`Depth exceeds stock thickness by 7.00 mm`.

## The one deliberate difference from the GUI rule — read J7 first

The GUI rule compares the DEEPER of two bottoms with the stock: the
operation's depth dial, and the Heights tab's resolved Bottom Z. **This one
reads the depth dial alone.**

J7 measured why. For every operation this rule applies to, a pinned Bottom Z
reaches no emitted motion — the pin moved 14 mm on a test pocket and the
emitted floor did not move at all. Folding the pin into a caution about the
cut would describe a cut the machine does not make, which is the defect class
the whole programme is closing.

The F1.6 worker recorded this caveat and asked that it not be lost. It is not
lost; it is resolved, and resolved by removing the ambiguity rather than
porting it:

- **"Your cut goes through the board"** is a statement about emitted motion.
  That is this predicate, and it reads the depth dial.
- **"This field does nothing on this operation"** is a statement about a
  dial. That is J7's `honors_pinned_bottom_z`, and it belongs beside the
  field, not beside the depth.

Two findings, two sentences. Merging them is what produced the false caution.

### Consequence for the GUI switchover

When the UI programme deletes its rule and consumes this one, **case (d) of
F1.6's sentry changes behaviour**: "Pocket 6 mm with Bottom Z pinned 3 mm
below the stock bottom → 3.00 mm" will stop cautioning, because 6 mm of cut
into an 18 mm board is not a cut through the board. That is the intended
correction, not a regression, but it is a visible change and the UI lane
should expect it. Case (d2) and every depth-driven case are unchanged.

## Who abstains, and why abstention is not exoneration

`depth_beyond_stock_applies` returns `false` — meaning **NOT MEASURED** — for
three groups:

| Group | Why |
|---|---|
| `Adaptive3d`, `UnifiedFinish`, `Waterline` | their floor CAN be a pinned Bottom Z, and this adapter's snapshot carries no pin flag — `from_context` sets `bottom_z` to the stock bottom whatever the operator pinned. Answering would mean guessing. |
| the surface-riding finish family | the mesh is the floor; `depth_semantics()` is `DepthSemantics::None` |
| `DropCutter` | `DepthSemantics::DerivedStockTop(min_z)` — its depth CLAMPS a surface-riding descent, it does not command a floor, so a `min_z` below the board does not mean the tool reaches it |
| `ProjectCurve`, `AlignmentPinDrill` | ProjectCurve's depth drops below the MESH surface, not the stock top; the pin drill's whole purpose is to reach into the spoilboard |

**My first draft of the applicability predicate got this wrong**, and the
sentry caught it: it asked for "anything that is not `DepthSemantics::None`",
which admitted `DropCutter`. The rule now requires `DepthSemantics::Explicit(_)`
and nothing else — which is exactly what the GUI rule requires, checked
against `ui/properties/operations/mod.rs:2019-2027`. **The two rules therefore
agree on WHICH operations they answer for, and differ only on the pinned
Bottom Z.** That makes the switchover a smaller change than it looked.

`Drill` IS included: it has a depth dial anchored at the top and no
spoilboard allowance of its own (`DrillConfig` carries none — the
"Spoilboard" dial belongs to `AlignmentPinDrill`).

Giving the first group a caution of their own needs a `bottom_pinned` flag on
the diagnostics snapshot. That is the follow-up and it is small.

## The sentry

`crates/rs_cam_core/tests/depth_beyond_stock_core_g_depthstockcore.rs`, seven
arms: the acceptance through the real `diagnostics_from_static_checks` list;
a cut inside the board silent (so a green acceptance is not a rule that
always fires); a through cut exactly at the stock bottom silent; a Bottom Z
far below the board silent on its own (J7's consequence); the three abstainers
proved to abstain; a missing stock span proved to abstain; and the id proved
to be in `ids::ALL`.

## NOT done — do not read this as covered

- **The GUI-side rule is still there and still ORs the pin.** I did not
  delete it. `crates/rs_cam_viz/src/ui/properties/**` is a live UI lane. Until
  the switchover, the inspector ribbon and the core list read DIFFERENT rules
  and can disagree on exactly one case, (d) above.
- The core predicate is therefore **unconsumed by the GUI**. It is consumed
  by MCP `get_toolpath_diagnostics` and the CLI `project` report the moment
  this branch lands.
- No threshold moved. `DEPTH_BEYOND_STOCK_EPS_MM` is an equality epsilon
  (1e-6 mm), the same value F1.6 used, so a through cut exactly at the stock
  bottom stays silent on both surfaces.
