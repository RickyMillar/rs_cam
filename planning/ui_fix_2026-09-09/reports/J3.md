# J3 — the `cusp_radius` Bull arm

Core-geometry account, 2026-09-10. Branch `core-consolidation`.

## 1. The prompt's claim, checked

Verified in the source, not taken on trust:

- `MillingCutter::cusp_radius` (`crates/rs_cam_core/src/tool/mod.rs:295`)
  matched `ToolGeometryHint::TaperedBall { tip_radius }` and fell through to
  `_ => self.radius()` for every other shape.
- `BullNoseEndmill` (`crates/rs_cam_core/src/tool/bullnose.rs`) overrides
  `corner_radius_mm` (`:65`) and `geometry_hint` (`:90`, returning
  `Bull { corner_radius }`) but NOT `cusp_radius`.
- `scallop.rs:2202` takes `let cusp_r = cutter.cusp_radius_mm();` and drives
  the stepover and cusp equations from it.

So a Ø10 bull nose with a 2 mm corner reported 5.0. **The claim holds.**

Two things the prompt did not say, both of which matter:

- `ToolDefinition` — the wrapper the production path actually holds —
  forwards `cusp_radius` and `cusp_radius_mm` to the inner cutter
  (`tool/mod.rs:699-704`), and `cusp_radius_mm` is a plain alias of
  `cusp_radius` (`:311`). So the default trait method is a **single**
  change site that covers both spellings and the wrapper.
- `ToolGeometryHint::Bull` is produced by exactly ONE type,
  `BullNoseEndmill::geometry_hint`. Nothing else can reach the new arm.

## 2. The change

`crates/rs_cam_core/src/tool/mod.rs`, `MillingCutter::cusp_radius`:

```rust
crate::feeds::ToolGeometryHint::Bull { corner_radius }
    if corner_radius > 0.0 =>
{
    corner_radius
}
```

**The `> 0.0` guard is load-bearing.** `BullNoseEndmill::new` asserts
`corner_radius >= 0.0`, so a zero-corner bull is constructible and is a flat
end mill wearing a bull's name. Returning 0.0 for it would divide by zero in
`equal_cusp_stepover_mm` and collapse every claim floor, close radius and
region area that scales from the cusp radius. A zero-corner bull keeps
`radius()`.

Note the arm is self-consistent at the other degenerate end too: a bull with
`corner_radius == radius` is a ball nose, and the arm returns the radius,
which is what the fall-through returned.

## 3. Per-consumer audit

Every consumer of `cusp_radius` / `cusp_radius_mm` outside the trait
definition, and whether the corner radius is the right answer there. Sites
are located by SYMBOL.

### 3a. Correct — a genuine cusp / feature-scale question

| Site | Use | Why the corner radius is right |
|---|---|---|
| `scallop.rs::…` (`cusp_r`) | stepover and cusp equations | This is the motivating case. A bull forms its scallops with the corner torus. |
| `session/multitool.rs::equal_cusp_stepover_mm` and its two callers | the cusp law itself | Same equation, same reason. |
| `tier_map.rs` (ladder ordering, `finest_cusp_mm`, the coarse→fine sort) | orders tools by the finest feature each can form | A bull's fine-feature scale IS its corner. Ordering by envelope put it in the wrong tier. |
| `finish_planner.rs::FinishPlannerParams::for_tool` | `close_radius`, `pencil_claim_floor`, `min_region_area` | Its own doc already says "MUST be the tool's cusp-forming (tip) radius — not `radius()`". The arm makes that doc true for a bull. |
| `tier_islands.rs::derived_close_radius_mm` / `derived_min_region_area_mm2` | morphological close radius, minimum region area | Same family as `for_tool`; the doc names `cusp_radius`, "never `radius()`". |
| `compute/operation_configs.rs::planner_params` | passes the value into `for_tool` | Pass-through. |
| `compute/execute.rs:2485` | `cfg.planner_params(ctx.tool_def.cusp_radius_mm())` | Pass-through; its comment already argues for the tip, not the envelope. |
| `ramp_finish.rs` (`swath_width = 2.0 * cusp_radius_mm()`) | swath the tip lays down | Correct in the same sense as the cusp law. |

### 3b. Correct, but it changes the COST of a run

| Site | Use | Consequence for a bull nose |
|---|---|---|
| `finish_setup.rs` (`CuspQuarter`, `GeometricMean`) | classification grid = `cusp_radius / 4` | Ø10 R2 bull: cell 1.25 mm → 0.5 mm. **6.25× the cells**, so the classification grid gets finer and slower. It is also more CORRECT — the old cell could not resolve features the tool can cut. |
| `measurement.rs` (`CuspRadius`, `GeometricMean`) | the same two resolution modes | Same. The reported label `"classification grid (cusp_radius/4)"` stays true. |
| `reach_map.rs` (`cell_mm = cusp_radius_mm() / 2.0`, clamped) | reach-map grid cell | Same direction, and clamped at both ends by `MIN_REACH_CELL_MM` / `MAX_REACH_CELL_MM`, so the blow-up is bounded. |
| `unified_finish.rs` (five `for_tool` sites) | planner params per band | Correct, and inherits the finer grid above. |

This is a real cost, it is not a defect, and it is stated rather than hidden.
An operator putting a bull nose on a finishing op will see slower planning
than before. **Not measured in this job** — no timing run was made.

### 3c. Cache keys — a one-time invalidation, bull-nose tools only

| Site | Effect |
|---|---|
| `tool_shape_key.rs:91` (`cusp_radius: tool.cusp_radius_mm().to_bits()`) | The key CHANGES for a bull nose, so stored work keyed on it is invalidated once. Note the same file already hashes the hint as `Bull(corner_radius.to_bits())` at `:59`, so the key carries no NEW information — only a changed value. Nothing is silently reused under a wrong key: the key moves, the entry misses, the work is redone. |
| `compute/sim_prefix.rs::hash_tool` | Same. It already hashes `corner_radius_mm()` alongside `cusp_radius()`, so again the information content is unchanged and only the value moves. Simulation prefix memos for bull-nose projects miss once. |

Neither is a correctness hazard. Both are worth knowing before someone
reports "my cached plan regenerated".

### 3d. Sites that want a DIFFERENT query — read carefully

The trait doc is explicit that the cusp radius is "**Not** an answer to
'does the tool fit / reach in there'". On a TAPERED BALL the tip radius
happens to answer both questions near the tip. **On a bull nose it does
not**: the corner radius forms the cusp, but what has to fit into a valley
is the cutter's full width. So a fit/reach site reading `cusp_radius` gets
an OPTIMISTIC answer for a bull after this change, where before it got a
conservative one.

| Site | Question it is really asking | Verdict |
|---|---|---|
| `reach.rs::working_half_width_mm` | `engagement_radius_mm(depth).max(cusp_radius_mm())` — how wide is this cutter here | **No-op for a bull, by arithmetic.** `BullNoseEndmill::width_at_height(0) == r1 == R − R2`, and `R − R2 > R2` for any corner under half the radius, so the floor never binds. On a bull with `R2 == R` (a ball) the cusp equals the radius anyway. No change, and no call-site fix needed. Verified against `bullnose.rs::width_at_height`. |
| `rest_field.rs` (`erode_cells`, `region_margin`) | its own doc says "the tip is what has to fit" — a FIT question | **Changes for a bull, and in the optimistic direction.** The erosion radius shrinks from 5.0 to 2.0 on a Ø10 R2 bull, so rest regions come out larger than the tool can actually enter. NOT fixed here; see §5. |
| `pencil.rs` (`pencil_cutting_diameter = cusp_radius_mm() * 2.0`, and the three `let r = tool.cusp_radius_mm()` sites) | pencil tip diameter — a FIT question | Changes for a bull. But see the next row: the pencil's own entry path already resolved this. |
| `pencil.rs::tip_contact_radius` | "the tool radius that actually nestles into a crease" | **Already correct and unaffected.** It reads `corner_radius_mm()` first and falls back to `cusp_radius_mm()` only where the corner is zero. This is strong precedent: the repo had already ruled, at its own site, that a bull's crease-nestling radius is its corner. The arm makes the shared query agree with it. |
| `session/reach.rs:43` | groups `Flat \| Bull \| VBit` and says `cusp_radius_mm()` cannot answer the reach question | **Already correct.** It does not call the query for these shapes. |

## 7. The one-line arm was NOT enough — H2 landed instead

The full core suite surfaced exactly one new failure, and it is the site §3d
had flagged as asking a FIT question through a CUSP query. The repo had a
sentry on it:

```
---- every_non_tapered_shape_keeps_the_radius_it_had stdout ----
panicked at crates/rs_cam_core/tests/rest_region_tip_radius_dilation_f1.rs:277
```

That arm's own doc calls itself "an identity transformation for every
non-tapered shape, by construction", and its assertion message says **"F1
would change this shape's dilation and moat, which it must not."** It is an
argued-for, executable claim, and it is RIGHT: a bull nose cannot enter a
valley its corner radius would suggest, because the full-diameter cylinder
sits only one corner radius above the tip, so the cutter binds on its FULL
radius the moment it descends past the corner. Dilating a rest mask by a
bull's corner radius would report territory the fine tool cannot reach — and
those polygons become `BoundarySource::DerivedRestRegions`, the territory a
fine-tool operation is ALLOWED to cut.

A second site rests on the same invariant. `pencil::resolve_reference_cutter`
compares `cusp_radius_mm() * 2` and its doc says in those words: "which is
`diameter()` for every non-tapered shape, **so nothing but the tapered path
moves**."

So `cusp_radius` was serving two questions that happen to coincide on a
tapered ball — the tip sphere both FORMS the cusp and is what ENTERS the
valley — and a bull nose separates them, in opposite directions.

### The resolution: land H2

The tool-scale taxonomy in `tool/mod.rs` already reserved a name for the
missing query:

```
| VALLEY | two-wall / profile fit in a valley | no API today (H2) |
```

This job lands it. `MillingCutter::valley_radius_mm()` is the tip radius for
a tapered ball and `radius()` for every other shape — **byte-identical to
what `cusp_radius` returned before the Bull arm** — so every call site moved
onto it keeps its current behaviour for every tool that exists. Moved:

| site | question | now reads |
|---|---|---|
| `rest_field::RestReference::erosion_radius` | fit | `valley_radius_mm` |
| `rest_field` mask→polygon dilation | fit | `valley_radius_mm` |
| `rest_field` trust-region moat (`erode_cells`) | fit | `valley_radius_mm` |
| `pencil::resolve_reference_cutter` | fit | `valley_radius_mm` |

`ToolDefinition` forwards it explicitly, for the reason PR-2 gives at that
block: a shape that overrode the query directly rather than through
`geometry_hint()` would otherwise see the wrapper silently revert to the
trait default.

The F1 sentry arm now asserts the identity on `valley_radius_mm` — the query
that actually feeds the dilation and the moat — so **the claim it protects is
preserved, not weakened**. Two assertions were ADDED to it, pinning that the
two queries genuinely part company on a bull nose (`cusp` 1.0, `valley` 3.0),
so the move is load-bearing rather than a rename and a later revert would
trip it.

### What this means for the audit in §3d

`rest_field` is no longer an open optimistic-reading risk — it was the thing
that forced the split and it is fixed. The same applies to
`resolve_reference_cutter`, which §3 had not separately flagged. The three
`let r = tool.cusp_radius_mm()` sites at the bottom of `pencil.rs` are inside
its TEST module, not production.
