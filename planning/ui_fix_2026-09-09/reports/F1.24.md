## 1. The three facts, with file and line

### 1.1 The collision is CONCURRENT. The sequential case is litter, not breakage.

`crates/rs_cam_core/src/session/save.rs:95` (parent `1106e893`):

```rust
let temp_path = parent.join(format!(".rs_cam_save_{}.tmp", std::process::id()));
```

The two statements after it were:

```rust
std::fs::write(&temp_path, &toml_string)?;
std::fs::rename(&temp_path, path)?;
```

**Concurrent.** Two saves in one process build the same name. One
interleaving is this:

1. Save A writes the temp file.
2. Save B writes the same temp file. `std::fs::write` opens with truncate,
   so B's bytes replace A's.
3. Save A renames. Path A now holds **B's project**, and save A returns
   `Ok(())`.
4. Save B renames a file that is no longer there. It returns
   `Err(SessionError::Io)` with `NotFound`.

So the defect is worse than "one loses the rename": the winner can publish
the loser's content and report success. A third shape is possible, because
each `std::fs::write` is a create-truncate followed by a write: two writes
can interleave inside the file and leave a mixture that is not valid TOML.

**Sequential.** A leftover temp file from an earlier failed save does NOT
break a later save. `std::fs::write` truncates, so the later save
overwrites it and proceeds. The cost is a hidden file that stays in the
project directory. That is litter.

### 1.2 Who calls `save`, and whether two calls can overlap

Both shipped doors reach one function:

- GUI menu and shortcut: `crates/rs_cam_viz/src/ui/menu_bar.rs:19,83` push
  `AppEvent::SaveJob`; `crates/rs_cam_viz/src/app/input.rs:357,365` handles
  it and calls `AppController::save_job_to_path`.
- GUI export wizard: `crates/rs_cam_viz/src/app/export.rs:474`, same call.
- MCP `save_project`: `crates/rs_cam_viz/src/mcp_server.rs:828-831` →
  `crates/rs_cam_viz/src/app/mcp.rs:452` → `mcp_save_project`
  (`app/mcp.rs:3127-3128`), same call.
- The single implementation:
  `crates/rs_cam_viz/src/controller/io.rs:283-294`.

**Two of these cannot overlap, and the compiler is what says so.**
`pub fn save_job_to_path(&mut self, path: &Path)` takes an exclusive borrow
of the controller (`controller/io.rs:283`), so two saves cannot hold the
controller at once. The frame-loop dispatch is the second leg: `app/input.rs`
and `app/mcp.rs` both run on the eframe update loop.

The CLI has one caller,
`crates/rs_cam_cli/examples/apply_suggest_save.rs:119`, which is
single-threaded.

So **no shipped path saves two projects at the same time today**. What
still makes this a real defect:

- **Test harnesses.** `cargo test` runs `#[test]` functions in parallel
  threads of ONE process. Any two tests that save into one directory hit
  the race. That is exactly what happened to the F2.6 worker.
- **The leftover temp file** (fact 1.3), which reaches any caller.
- **Any future caller.** The property "an atomic-write temp name is unique
  per write" belongs to the write, not to the current call graph.

### 1.3 Nothing cleaned the temp file up

Both statements used `?`. On a failed `write` a partial temp file could
remain. On a failed `rename` the whole temp file remained. Nothing in
`save` removed it, and no other code in the workspace removes it — I
searched for `rs_cam_save` across `*.rs` and `*.md` and found only the one
producer at `save.rs:95` plus documentation and two test helpers.

The next save from the same process then **overwrote** that file, as
fact 1.1 says, so the leftover caused no wrong result. It stayed on disk,
hidden, in the operator's project folder.

## 2. Honest severity

**Narrower than "two saves collide", and worth fixing anyway.**

No shipped GUI, MCP or CLI path saves two projects concurrently, and
`save_job_to_path`'s `&mut self` makes it impossible through the GUI door
without a code change. The measured exposure today is the test suites and
a hidden litter file. I did not find, and do not claim, any operator-facing
data loss.

It is still a defect worth repairing: an atomic-write temp path keyed on
the process id alone is wrong regardless of who calls it today, and the
failure path leaving its own temp file behind is wrong for every caller.
The repair costs one counter.

Footnote. `crates/rs_cam_viz/src/io/project.rs:486` — the legacy fallback
loader's own `save_project` — uses `path.with_extension("tmp")`. That name
is per DESTINATION, so it cannot collide across destinations, though two
saves of ONE destination would still race. It has no production caller and
I did not touch it.

## 3. What I changed

### 3.1 The fix — `crates/rs_cam_core/src/session/save.rs`

A process-wide counter gives every CALL its own name:

```rust
static SAVE_TEMP_SEQUENCE: AtomicU64 = AtomicU64::new(0);

fn save_temp_file_name() -> String {
    let pid = std::process::id();
    let seq = SAVE_TEMP_SEQUENCE.fetch_add(1, Ordering::Relaxed);
    format!(".rs_cam_save_{pid}_{seq}.tmp")
}
```

Why a counter and not a timestamp: `fetch_add` guarantees a distinct name
for every call in one process. The pid keeps two processes apart. A
timestamp adds nothing to that guarantee, and it would make a temp file
left by a killed process permanent, because no later save could ever
overwrite it.

**No dependency was added.** I read `crates/rs_cam_core/Cargo.toml`: it
carries no `uuid`, `rand` or `tempfile`. `AtomicU64` is `std`.

Two properties are preserved deliberately, and the doc comment on
`save_temp_file_name` says both:

- The name keeps its leading dot, so the file stays hidden.
- The file stays in the DESTINATION directory. **An atomic rename cannot
  cross a filesystem boundary**, which is the reason the temp file is not
  in `/tmp`.

The failure path now cleans up:

```rust
if let Err(e) = std::fs::write(&temp_path, &toml_string) {
    // A failed write can still leave a partial file behind.
    let _ = std::fs::remove_file(&temp_path);
    return Err(e.into());
}
if let Err(e) = std::fs::rename(&temp_path, path) {
    let _ = std::fs::remove_file(&temp_path);
    return Err(e.into());
}
```

The removal is best-effort (`let _`), because a failed write may leave no
file to remove. Neither original error is swallowed.

### 3.2 The doc comments that named the old scheme

- `save.rs`, the `save` doc comment: it now says the temp name is unique
  per call and that a failed save removes its own temp file.
- `save.rs`, the test helper `temp_path`: rewritten, see §4.
- `crates/rs_cam_viz/tests/load_requests_only_25d_regen_g_loadregen.rs`,
  the `temp_project_path` doc comment: rewritten, see §4.

`planning/` documents still describe the old name in their own historical

## 4. The F2.6 workaround — found, and reverted

The rule is that a test which changes its expectation is where a fix hides
its own weakening. I found **two** workaround sites and reverted both. **No
assertion in either file was weakened, removed or relaxed.** Only the file
layout of the temp projects changed.

### 4.1 F2.6's own — `crates/rs_cam_viz/tests/load_requests_only_25d_regen_g_loadregen.rs`

The file was created whole by F2.6 (`0b38e88f`), workaround included. Its
`temp_project_path` gave each test a nanosecond-named DIRECTORY, and its
doc comment named the race as the reason:

> Not just a unique FILE name: `ProjectSession::save` writes its atomic
> temp file as `.rs_cam_save_<pid>.tmp` in the project's parent directory,
> so two saves from the same process into the same directory race and one
> of them loses the rename.

**Reverted.** All five tests now share ONE directory,
`$TMPDIR/rs_cam_loadregen_{pid}`, and an `AtomicU64` counter keeps the FILE
names apart — a separate need that survives the fix. So the five parallel
saves now exercise the repaired path instead of avoiding it.

The five tests still assert exactly what they asserted: which toolpaths a
load submits, that the 3D operation still waits after the sweep, that it
reads `NoResult` and never `Error`, that a fresh load counts as pending and
not stale, and that it reaches the chip as pending.

### 4.2 The older one — `crates/rs_cam_core/src/session/save.rs`

The unit-test helper `temp_path` carries the same workaround and predates
F2.6: it came in with `a86a2b4c` ("Phase 2B/2C"), and its comment read

> Per-test temp directory so concurrent saves don't race on the shared
> `.rs_cam_save_{pid}.tmp` temp filename that `save()` uses.

**Reverted.** The nine unit tests in that module now share ONE directory,
`$TMPDIR/rs_cam_test_save_{pid}`, with one file per test. Every assertion
is unchanged.

### 4.3 One thing I deliberately did NOT keep

Both `cleanup` helpers used to remove the temp DIRECTORY as well as the
file. With a shared directory that would be a new race of its own: one
test's `remove_dir` can succeed while another test is between
`create_dir_all` and `save`, and that test's write then fails with
`NotFound`. Both `cleanup` helpers now remove only the file. One empty
pid-named directory is left in `$TMPDIR` per test run. I judged that a
better trade than a race I would be introducing myself.

## 5. The sentry

- Crate: **`rs_cam_core`**
- Test binary: **`save_temp_path_unique_f124`**
- Path:
  `/home/ricky/personal_repos/rs_cam_wt_alt/crates/rs_cam_core/tests/save_temp_path_unique_f124.rs`
- Runs in the cheap dev loop (`cargo test -p rs_cam_core -q`). No GUI, no
  `heavy-tests` feature, no printing.

Three tests, and they are not worth the same:

| Test | Pins | Pre-fix |
|---|---|---|
| `the_temp_name_is_not_the_pid_alone` | the name is not derivable from the pid | **deterministic RED** |
| `two_saves_into_one_directory_both_succeed` | the CONTRACT | probabilistic RED |
| `a_failed_save_removes_its_temp_file` | the cleanup half | **deterministic RED** |

**`the_temp_name_is_not_the_pid_alone`** builds the exact old name in the
project directory and puts a DIRECTORY there, then asserts the save
succeeds. The old code writes onto a directory and fails; the fixed code
picks a different name. Stated limitation, in the file header so nobody
over-reads it: the test knows the old name, so if the `.rs_cam_save` prefix
is ever renamed the obstruction stops obstructing and the test goes
vacuous.

**`two_saves_into_one_directory_both_succeed`** is the contract itself. Two
threads meet at a `Barrier` on each of 32 rounds and save two different
sessions into ONE directory. Each round asserts the save returned `Ok` and
that the file on disk still contains its own marker, which catches both the
`NotFound` shape and the cross-content shape. It is **PROBABILISTIC before
the fix** — the two saves must interleave for the defect to show — and
deterministic after it. A green run of this one test on unfixed code is
luck, not the absence of the race. Each session's name carries 128 000
characters of padding, so the serialized TOML is large and the write window
is wide.

**`a_failed_save_removes_its_temp_file`** makes the destination a
directory. `rename(file → existing directory)` is `EISDIR` on Linux, so the
save always fails, and the test asserts no `.rs_cam_save*` entry remains.

Non-vacuity floors, all explicit:

- the concurrent test asserts `path_a.parent() == path_b.parent()`, with
  the message "the two saves must target one directory, or this test proves
  nothing";
- the obstruction test asserts the obstruction really is a directory;
- the failure test asserts the destination really is a directory.

The concurrent test also asserts that no temp file is left behind after
the successful saves. **That assertion does not discriminate.** On the
unfixed code the colliding rename REMOVES the shared temp file — that is
why the second rename fails with `NotFound` — so the concurrent test leaves
no leftover before the fix either. `a_failed_save_removes_its_temp_file` is
the only cleanup pin that goes red.

## 7. What I could not establish without a compile

I ran no cargo command, so none of the following is verified:

1. **That the sentry compiles.** In particular
   `two_saves_into_one_directory_both_succeed` needs `ProjectSession: Send`
   so that a session can move into a scoped thread. I read
   `crates/rs_cam_core/src/session/mod.rs:69` onward and the
   `ProjectSession` field list: `String`, `Vec`, `HashMap` and plain config
   structs, with no `Rc`, `Cell` or `RefCell` stored in the session (I
   searched core for those three; the only hits are local `RefCell`
   parameters in `compute/execute.rs`, never a session field). I expect
   `Send`, but I did not compile it. If the compiler disagrees, moving the
   session by value does NOT help — by-value is what needs `Send`. The
   repair is to build each session INSIDE its own thread closure, so no
   session ever crosses a thread boundary.
2. **That the sentry is RED on the parent.** I reasoned it from the code. I
   did not run it.
3. **That the fix is GREEN.** Same.
4. **The reliability of the probabilistic arm.** I chose 32 rounds, a
   barrier and a 128 000-character payload to widen the window. I have no
   measurement of how often it trips pre-fix.
5. **`cargo fmt --check`.** I wrote to rustfmt's shape by hand: no line
   over 100 columns, `format!` argument lists kept well under 60, and the
   assert messages either comfortably under the 60-column call width or
   comfortably over it, so the layout should not sit on the boundary. Not
   verified.
6. **Clippy.** Every `format!` inlines its identifiers, which matters
   because `uninlined_format_args` is warn-by-default and `-D warnings`
   promotes it; the old line survived only because `std::process::id()` is
   a call. The sentry file carries
   `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic,
   clippy::indexing_slicing)]` and prints nothing, so it needs no
   `print_stderr` allow. Not verified.
7. **`cargo test -p rs_cam_viz`.** §4.1 changes a viz test helper. The five
   tests in that binary now share one directory. I expect them to pass; I
   did not run them.
