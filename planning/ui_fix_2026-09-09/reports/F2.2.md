## 1. The defect this closes

F2.1 built one `FreshnessState` and proved every mutation lands on the right
one. **Nothing read it.** Each surface still asked its own question, and on an
operation edited after generation every one of them answered "fine":

| Surface | What it asked | What it said on an edited operation |
|---|---|---|
| Card chip | `ComputeStatus::effective` | `OK`, green — the generation *did* finish |
| Card ▶ button | `ComputeStatus::needs_generation()` | hidden — `Done` does not "need generation" |
| Card stats row | `rt.result.stats` | three confident numbers, unmarked |
| Setup header n/m | `ComputeStatus::Done` | `2/2` |
| Inspector header | `ComputeStatus::effective` | green "Done", directly above the changed field |
| Toolpaths chip | `needs_generation() \|\| Computing` | nothing |
| Readiness chip | `gui.toolpath_rt[..].result.is_none()` | nothing |
| `readiness::operations_check` | same GUI store | `2/2 computed` (**F1.17**) |
| Rest `dep` badge | `needs_generation() \|\| stale_since` | green `dep` |
| Viewport | — | full-colour path |

Two root causes, and they are different:

- **`ComputeStatus::Done` is true.** The generation that produced the drawn
  geometry really did finish. `ComputeStatus` has no way to say "and then the
  inputs moved", which is exactly the gap `FreshnessState` was built to fill.
- **`gui.toolpath_rt[..].result` is deliberately retained.** An edit drops the
  core result and KEEPS the GUI's copy so the viewport can still draw
  something. Any surface counting that copy counts an operation the core
  cannot reproduce as computed. That is F1.17, and it is why Readiness could
  read `2/2 computed` beside a blocking export row.

## 3. Point 3 — why `EditedSince` reads the way it does

`EditedSince` means the geometry on screen was generated from inputs the
project no longer holds. The lead's caution is right: a chip that reads like a
mild advisory understates it. Three decisions, defended:

**The word is "STALE", not something stronger.** Not because the condition is
mild, but because this repo already spends "stale" on exactly this idea — the
simulation badge, `SimulationState::is_stale`, the MCP wire's `"stale"` key,
`FreshnessState::label()`'s `"edited_since"` beside them. Inventing a second
word for one idea is how three stores came to disagree in the first place;
R0.1 exists because of it. A new word would buy prominence at the cost of the
thing this whole phase is for.

**The colour is amber, not red.** Nothing is *wrong*: no gate tripped, no
collision, no failure. The answer on screen is the previous question's. This
panel spends red on `ERR` and on collisions, and spending it here would flatten
a distinction the operator needs — "this cut may hurt the machine" versus
"this picture is out of date". The sentry asserts the colour is neither the
success colour nor the error colour, so a later edit cannot quietly promote or
demote it.

**The prominence is not in the chip — it is in the numbers.** This is the
judgement that matters, and it is where R0.1's table earns its keep. Four amber
letters do not undo three confident figures two rows below them: `1,284 moves ·
14 min · 31.2 m` is the strongest thing on the card, and left unmarked it says
"this is a finished, measured operation" louder than the chip says otherwise.
So the stats row is prefixed `old:` and drops to the faint colour, and the ▶
button — hidden before, because `Done` does not "need generation" — reappears
on exactly the card whose whole message is "regenerate me". The chip names the
state; the row it sits above stops asserting the opposite; the button offers
the fix. Prominence here is three small consistent signals, not one loud one.

The hover carries what four letters cannot: *"Inputs changed after this was
generated. The path drawn in the viewport and the figures below are from the
PREVIOUS generation, not from the settings now in the project. Regenerate."*
It names the two things the operator is looking at, says whose they are, and
says what to do. The inspector header says both halves out loud, because it
sits directly above the field that was just changed: *"Done · edited since —
regenerate"*.

## 4. Point 2 — Q6, answered by assumption

**R0.1 §7 Q6 is unanswered by the operator: opacity 0.4 with the same palette,
or dashed grey? I implemented R0.1's own recommendation — §4.4's viewport row
reads "dimmed (opacity 0.4), same palette" — and I am recording that I
answered it by assumption, not by ruling.** Dashed grey was not tried.

Two things a reader should know about how it landed:

**The factor is the existing 0.45, not a new 0.4.** The line pipeline already
carries exactly one dim uniform and one dimmed bind group
(`MOVE_DIM_UNDER_REACH = 0.45`, built for P5.3's reach overlay). A stale path
takes that same bind group. Adding a second uniform, buffer and bind group to
express a 0.05 difference nobody has ruled on would be a new tunable rather
than a clearer picture, and this repo is strict about new numbers. If the
operator later rules for 0.4 specifically, it is a one-line constant.

**The complication R0.1 raises is real and I did not solve it.** Colour
overlays are exclusive per surface, so a stale path drawn with the engagement
or advance-per-tooth palette is a *stale palette* too — the colours are as old
as the geometry. Dimming cannot distinguish "old geometry" from "old colour
mapping". What I can say is that it is not misleading: both are old, together,
because they come from the same retained result — the dim marks the whole
drawing as last generation's, which is exactly what it is. What it does NOT do
is survive the reach overlay: while that is painting, every move is dimmed
already, so the stale dim adds no signal there at all. That is stated in the
code at the decision and it is why the card chip and the inspector header,
not the viewport, are the authoritative surfaces. A reader who wants the
stale/fresh distinction under a reach overlay does not have it.

## 8. The caution: this display does NOT mean the export is safe

F2.1 closed the defect where a GUI edit left the core result in place. It did
not close the export fallback: `io::export.rs::emitted_toolpaths` still falls
back to `gui.toolpath_rt[..].result` when the core slot is empty, which is
exactly the state an edited operation is in. **So an operation whose card
reads STALE can still export its old geometry today.** F2.3 owns that gate.

Nothing this task adds says or implies otherwise. The chip hover, the header
line and the Readiness row all speak about what is *drawn and counted*, never
about what would be *emitted*. `no_freshness_text_promises_that_export_is_gated`
enforces it mechanically: it scans every line in the two panels carrying
"stale" or "edited since" and fails if one mentions export. That test exists
so a later well-meaning edit cannot turn a freshness notice into a safety
promise this programme has not yet earned.
