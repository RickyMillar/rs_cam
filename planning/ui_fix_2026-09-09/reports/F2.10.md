## 1. The defect

`SimulationRunMeta::last_sim_edit_counter` is what
`SimulationState::is_stale` compares against. It was stamped in the DRAIN,
from the live `gui.edit_counter`, at the moment the result arrived:

```rust
last_sim_edit_counter: self.state.gui.edit_counter,   // pre-fix
```

So every edit the operator made *while the simulation ran* was folded into the
record of when the run was made. `is_stale` then answered `false`, and the run
was presented as current evidence on every surface that reads it — the
Simulation tab chip, `readiness::simulation_check`, and the Readiness panel's
`FreshnessGate`, which dims the whole readout when a run is stale and did not.

**This is the same defect shape F2.4 closed on the toolpath**, and it lands
somewhere worse. A toolpath result that answers a superseded config produces a
wrong program, which the export gate now refuses. A *simulation* that answers
a superseded config produces wrong **collision counts, engagement and
air-cut** — the numbers an operator reads to decide whether it is safe to cut
— with nothing anywhere saying they are old.

## 2. Point 3 — is stamping at submit the whole fix?

Yes, and here is why the obvious worry does not apply.

The worry: two simulations in flight, the first result arriving against the
second's stamp. It cannot happen. `ThreadedComputeBackend::submit_analysis`
clears the lane queue and raises the cancel flag on any in-flight job before
queuing the new one (`compute/worker.rs`), so a superseded run returns
`Err(Cancelled)` and never reaches the `Ok` arm that stamps. **At most one
result can arrive per stamp**, which is what makes a single `Option<u64>`
sound rather than a map keyed by run.

The stamp is `take()`n by the result it describes, so it cannot be re-used by
a later arrival that had no submit of its own; such an arrival falls back to
the live counter, which is the pre-F2.10 behaviour and not a claim this guard
can honestly make either way. `the_submit_stamp_belongs_to_one_run_g_latesim`
pins that.

## 3. Point 1 — the counter is project-wide, and it stays that way

`edit_counter` bumps on any `mark_edited`, so a simulation is staled by edits
that could not have changed it. F2.1 established that renaming an operation
marks the project edited without staling the toolpath — under this fix, a
rename during a run stales the simulation.

**Accepted, deliberately, and here is the argument.**

1. **It introduces no new coarseness.** This is already `is_stale`'s semantics
   for the window *after* a run: rename an operation once the simulation has
   landed and it goes stale today, on shipped code. All this change does is
   make the in-flight window behave like the windows either side of it.
   Narrowing it here would mean the simulation was *less* sensitive to edits
   made during the run than to the same edits made a second later, which is
   the wrong way round.
2. **Narrowing is a different task with a different shape.** A precise answer
   needs a per-simulation input signature — which toolpaths, at which
   revisions, plus stock, resolution, machine and post — i.e. F2.1's
   `generation_inputs_signature` idea lifted to the project. R0.1 §6 puts
   simulation policy explicitly out of scope, and doing it inside a
   late-arrival guard would be a policy change smuggled in under a race fix.
3. **The failure mode is a re-run, not a wrong cut.** Being conservative costs
   the operator a simulation; being wrong the other way tells them a cut is
   clear when the evidence for that belongs to a different configuration.

Not narrowed silently: this section is the disclosure, and the sentry's own
comment points at it.

## 4. Point 4 — stored, not discarded

Same answer as F2.4, same reasoning, and here it needs no extra machinery: the
result is stored exactly as before, and only the staleness stamp changes. So
the operator keeps a drawable simulated stock, the playback, the cut trace and
the metrics — every one of which is still useful for comparing against the
configuration they have moved to — and every surface marks them not-current.

Discarding would be worse than in F2.4's case, not better. A simulation is
minutes of work over the whole project, and a Simulation workspace that
silently emptied itself because an edit landed while it ran would be
indistinguishable from one that never ran.
