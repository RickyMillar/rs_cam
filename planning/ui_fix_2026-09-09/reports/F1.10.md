## (a) A cross-setup drag ignored the drop index — G-DROPINDEX

**Claim.** `mutation.rs::move_toolpath_to_setup` appends instead of inserting
at the drop index.

**Confirmed.** `ToolpathPanel::draw` computes the drop position from the
pointer (`compute_drop_index`, `ui/toolpath_panel.rs`), puts it on
`AppEvent::MoveToolpathToSetup`, and the handler took it as `_idx` and
discarded it (`controller/events/toolpath.rs::handle_move_toolpath_to_setup`).
Core then did `self.setups[target].toolpath_indices.push(tp_index)`. So every
cross-setup drag landed at the bottom of the target setup whatever the operator
pointed at, and putting it in the right place took a second gesture.

**Changed.**

- `crates/rs_cam_core/src/session/mutation.rs::ProjectSession::move_toolpath_to_setup`
  — new third parameter `target_position: Option<usize>`; the body inserts at
  `min(position, len)` and appends on `None`.
- `crates/rs_cam_viz/src/ui/mod.rs::AppEvent::MoveToolpathToSetup` — the
  position is now `Option<usize>`.
- `crates/rs_cam_viz/src/controller/events/toolpath.rs::handle_move_toolpath_to_setup`
  — takes `position: Option<usize>` and passes it through.
- `crates/rs_cam_viz/src/ui/toolpath_panel.rs` — the drop emits `Some(drop_idx)`.
- `crates/rs_cam_viz/src/app/mcp.rs::mcp_move_toolpath_to_setup` — emits
  `None`. **This is why the parameter is an `Option`.** The MCP tool has no
  position argument, and the literal `0` that used to sit there was inert
  because core threw it away; honouring it would have silently moved every
  MCP-moved op to the FRONT of the target setup. MCP behaviour is unchanged.

**Before / after.** Setup 1 holds `Target A, Target B, Target C`. Dragging
`Travelling` onto the gap above `Target A`:

| after | `Travelling, Target A, Target B, Target C` |

## (b) A same-setup re-order was a swap — G-DROPINDEX

**Claim.** The re-order is a swap where the operator expects an insert;
**confirm the intent against Move Up / Move Down before changing it**.

**Confirmed, and the ruling follows.** `reorder_toolpath` did
`setup.toolpath_indices.swap(pf, pt)`.

Three affordances reach that one method:

1. **Move Up / Move Down** (`handle_move_toolpath_up` / `_down`) always pass
   the ADJACENT op's global index. For adjacent positions an insert and a swap
   are **the same permutation**, so these two menu items are unaffected by the
   change either way.
2. **Drag and drop** passes `compute_drop_index`, which returns `0..=count` —
   an insertion GAP, not a card position (`count` means "below the last card",
   which is not a card at all). Only an insert can honour a gap. The old
   handler clamped that gap to `count - 1` and fed it to a swap.
3. **The card context menu** routes into the same two handlers.

So the review's framing — two gestures with two policies that must be
reconciled — does not hold. There is one meaning, "put this op here", and only
the drag could ever express the difference. Under the swap, dragging the last
of five ops to the top produced `E B C D A`: two ops moved when the operator
asked for one, and dragging A down to E's place produced the identical
permutation, so the two opposite gestures were indistinguishable in the result.

Corroborating, though not decisive: the older GUI-side job model,
`crates/rs_cam_viz/src/state/job.rs::Job::reorder_toolpath` and
`Job::move_toolpath_to_setup`, already implements BOTH as `remove` + `insert`
with a clamp. Neither has a caller today — the session is the live model — so
they are not evidence of current behaviour, but they are what this project
wrote when it last spelled these two gestures out.

**The ruling is therefore: change `reorder_toolpath` itself to an insert**,
rather than adding a second method beside it. Move Up / Down keep their exact
behaviour as a consequence of the adjacency identity, not as a special case,
and the sentry pins that identity so a future change cannot break one gesture
while fixing the other. The reasoning is recorded in the doc comment on
`reorder_toolpath` and in the sentry's module doc.

**Changed.** `crates/rs_cam_core/src/session/mutation.rs::ProjectSession::reorder_toolpath`
— `remove(pf)` then `insert(pt)`, both positions read off the original list:
downward the op lands just after the target, upward just before it, and the
ops between shift by one. `handle_reorder_toolpath`
(`controller/events/toolpath.rs`) now converts the drop GAP to the target card
before calling — `gap` when the gap is above the dragged card, `gap - 1` when
below — so the op lands exactly in the gap in both directions.

**Before / after** on `A B C D E`:

## (c) Generate All generated disabled operations — G-GENALLDISABLED

**Claim.** GUI Generate All without a rest chain should submit only enabled
ops.

**Confirmed.** `handle_generate_all` has two arms. The ladder arm submits
`generate_all_scope(..).enabled`. The arm beside it — taken whenever the
project holds no enabled `FromRemainingStock` op, which is most projects —
built its own id list from `toolpath_configs()` with no `enabled` filter and
submitted every one. Its own doc comment said so: "every config submitted
once, enabled or not". `submit_toolpath_compute` has no `enabled` check
either, so the ops really did reach the lane.

Why that is a defect and not a documented choice: the row-control hover
promises a disabled op is "excluded from generation, simulation and output"
(`ui/toolpath_row_controls.rs`); core's own `ProjectSession::generate_all`
skips disabled ops; `io::export::emitted_toolpaths` filters them out; and the
GUI simulation group builder includes enabled results only. This was the one
surface that generated them anyway — compute-lane time spent on work nothing
downstream reads, and a disabled card left reading `OK`.

**Changed.** `crates/rs_cam_viz/src/controller/events/toolpath.rs::handle_generate_all`
— the no-chain arm submits `scope.enabled`, and the "No enabled toolpaths to
generate" check moved ABOVE the branch so it covers both arms instead of only
the ladder.

**Before / after.** Three ops, the middle one disabled, no rest chain:

| | submitted to the lane |
|---|---|
| before | `[0, 1, 2]` |
| after | `[0, 2]` |

A project with nothing enabled: before, silence and no submissions; after, a
Warning notification "No enabled toolpaths to generate".

## (d) The fixpoint ladder rewrote the simulation resolution silently — G-RESNOTICE

**Claim.** The ladder that rewrites `state.simulation.resolution` /
`auto_resolution` must push a notification saying so. **Truthfulness only —
do not change when or whether it rewrites.**

**Confirmed.** `settle_generate_all_round`
(`controller/events/compute.rs`), arm `Next::Simulate(resolution)`, writes
`self.state.simulation.resolution = resolution` and
`self.state.simulation.auto_resolution = false` before every inter-round
simulation. The values STAY after the run, so every later simulation,
collision count and engagement figure is measured at whatever cell the ladder
chose. Nothing said so on any surface.

One thing the review's wording could mislead a reader about, so it is written
down here: **the GUI's own Generate All can never change the value.**
`pinned_simulation_resolution` returns `Some` only when `auto_resolution` is
already false, and then returns exactly `sim.resolution`, so the ladder writes
back what the operator pinned. The case that moves the dials is an **MCP**
`generate_all`, which carries its own `simulation_resolution_mm` argument and
can overrule both dials in a GUI the operator is watching.

**Changed.**

- `crates/rs_cam_viz/src/controller/generate_all.rs::resolution_override_notice`
  — new pure function returning `Option<String>`: `None` when the ladder's
  value equals a value that is already pinned, `Some(message)` otherwise. The
  message names the new cell size, the old one, whether the old one was `auto`
  or pinned, and the "Auto from tool size" checkbox it cleared.
- `crates/rs_cam_viz/src/controller/events/compute.rs::settle_generate_all_round`
  — pushes that message at Warning severity immediately before the two writes.

The two writes are byte-identical to before. No threshold, gate bar or feeds
constant was touched. `auto` at 0.150 counts as a change against a ladder at
0.150 because `auto` re-derives the cell per simulation, so clearing it moves
where later runs measure.

**Before / after** for an MCP `generate_all(simulation_resolution_mm: 0.15)`
against a GUI showing 0.300 mm auto:

| | operator sees |
|---|---|
| before | nothing; the Simulation panel silently reads 0.150 mm, unticked |
| after | "Generate All set the simulation resolution to 0.150 mm for the rest-stock ladder (was 0.300 mm, auto from tool size) and unticked "Auto from tool size". The new value stays after this run — collision counts and engagement both move with cell size, so set it back if you wanted the old one." |

**Sentry.** `crates/rs_cam_viz/src/controller/fixpoint_resolution_notice_g_resnotice.rs`,
five tests. It is a unit test beside the code, which PLAN.md §0 rule 3 allows,
because the two entry points it has to drive — `start_generate_all` and
`drain_compute_results` — are `pub(crate)`. The behavioural half drives a real
two-op chain: op 1 blocks on submit for want of prior stock, a result lands for
op 0, the round settles and takes the `Next::Simulate` arm.

## What this task did NOT do

- **It did not touch the `dep` badge's order-blindness** (r05 §6 item 3): a
  Rest op dragged above its predecessor still shows a green `dep` while the
  inspector blocks Generate. That is F1.8, already merged on this branch with
  its own predicate.
- **It did not fix the stale-snapshot regeneration or the export fallback**
  (r05 §6 items 1–2). `prior_stocks` still survives a re-order and a
  consumer regenerated afterwards still reads a pre-edit snapshot. Now that a
  drag can move an op several places at once, the window is wider, not
  narrower. That is P2's freshness model (F2.1–F2.4) and it needs R0.1 first.
- **It did not mark anything stale or dirty on re-order or move.** F1.11 as
  written is cancelled; the mutation matrix is P2's test list.
- **It did not add a position argument to MCP `move_toolpath_to_setup`.** The
  tool keeps appending. Adding one is a P3-shaped change and would want a
  schema pin.
- **It did not change when or whether the ladder rewrites the resolution**,
  nor which severity the GUI refusal uses, nor any numeric value anywhere.
- **It did not verify anything live.** The embedded MCP server is down and no
  GUI was started. Every claim here is from reading the code and from the
  sentries; none of it is a simulated or machined result.
- `compute_drop_index` is still a `round(fraction × count)` pointer heuristic
  over the whole drop zone rather than a per-card hit test, so which gap a
  drag reports is as coarse as it was. This task made the reported gap
  meaningful; it did not make it more precise.
