## What was wrong

The Feeds & Speeds card on the inspector printed the calculator's result under
labels that read as the configured operation. On the R03 fixture (fresh Pocket,
Ø6 two-flute end mill, feed 750, RPM 15000, depth per pass 1.2) the card read
`Commanded advance/tooth: 0.0435 mm/tooth` and `DOC: 4.20 mm`. The stored
operation gives 750 ÷ (15000 × 2) = 0.025 mm/tooth and cuts 1.2 mm per pass.
The `⚡ Apply cut geometry` button under the card writes 1.2, because the apply
funnel caps the depth to the machine rigidity (R0.5 §2.3 step 5). The button
was honest, the label was not.

Two further defects in the same rows (R0.5 §2.3 step 3):

- the advance row printed `FeedsResult::chip_load_mm`, the pre-derate TARGET
  chipload, while its hover said "feed ÷ (RPM × flutes) at the recommended
  feed". The printed number was not that quantity.
- the Feeds modal repeated both mislabels: a `DOC` row with the raw 4.2 in the
  Recommended column, and a `Commanded advance/tooth` row whose Recommended
  cell was the target chipload beside a Current cell that was feed ÷ (RPM ×
  flutes). One row, two quantities.

On this fixture the advance figures agree by coincidence of the fixture: the
recommended feed 1305 ÷ (15000 × 2) = 0.0435 equals the target because the
combined derate is 1.0 here. On a derated recipe the two differ and the hover
names both: "The calculator's target chipload before derates is N mm/tooth".

|---|---|---|

Left alone, on purpose: the S3 rubbing warning (`⚠ Commanded advance/tooth
below the vendor band minimum`) reads `current.chipload_mm()`, the configured
value, so "Commanded" is the right word there. The OPERATING POINT card keeps
`COMMANDED_ADVANCE_PER_TOOTH` (the gate's commanded figure). The
`FeedsWarning::ChiploadClampedToFloor` renderer text is core wording and is
out of scope. The scallop-derived `WOC ⓢ` row already explains its own
derivation on hover and is unchanged.

## Hover text

Advance row: "feed ÷ (RPM × flutes) at the recommended feed (1305 mm/min,
15000 RPM, 2 flutes). The calculator's target chipload before derates is
0.0435 mm/tooth. "configured" is the same quantity from the stored feed (750
mm/min) and the effective spindle speed (15000 RPM). The measured counterpart
is on the OPERATING POINT card below, after a simulation."

DOC row: "Raw calculator depth per pass. "Apply cut geometry" passes it through
the invariant funnel (machine rigidity cap, flute-length guard), so the written
value can be lower. "configured" is the stored depth per pass, which Generate
reads." WOC row: same shape, stepover-to-diameter clamp.

## The pure function

```rust
pub fn feeds_card_rows(inputs: &FeedsCardInputs) -> Vec<FeedsCardRow>
pub fn advance_per_tooth_mm(feed_mm_min: f64, rpm: f64, flutes: u32) -> Option<f64>
pub fn with_calculator_note(formatted: &str) -> String
```

`FeedsCardInputs` carries the calculator side (`FeedsResult` feed, rpm,
target chipload, axial depth, radial width) and the stored side (operation
feed, effective RPM = override else project default, tool flute count, depth
per pass, stepover). Rows follow the operation: DOC and WOC rows exist only
when the operation has those fields. No clamp logic is duplicated: the
as-applied DOC / WOC are not computed here, which is why those cells carry the
"(calculator)" note. F1.2's per-field preview helper is the route to an
as-applied figure; this task does not depend on it.

`advance_per_tooth_mm` returns `None` for zero flutes or a non-positive RPM
and the row prints `—` in both cells.
