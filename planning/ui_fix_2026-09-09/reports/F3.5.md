# F3.5 — G-TOASTREAD: `get_notifications`

Task F3.5, phase P3 (`planning/ui_fix_2026-09-09/PLAN.md` §5). Same tree,
head and conditions as `reports/F3.1.md`, with which this was written —
they are one task in two halves.

> Current toast stack with severity and age, so tests can assert what the
> operator saw (pairs with F1.1).

---

## 1. What it reads

`AppController` owns `notifications: Vec<Notification>` (private), where

```rust
pub struct Notification { pub message: String, pub severity: Severity, pub created_at: Instant }
impl Notification {
    pub fn ttl(&self) -> Duration;   // Info 4 s, Warning 6 s, Error 8 s
    pub fn is_expired(&self) -> bool // created_at.elapsed() >= ttl()
}
```

Before this task the only readers were `active_notifications()`
(non-expired, iterator) and `gc_notifications()` (drops expired). The
toast overlay in `app.rs` calls both once per frame. Nothing outside the
crate could see the stack, so F1.1's fix — a refusal now shows the refusal
text at Warning instead of a past-tense success — was assertable only by
reading the source or by driving an `AppController` directly.

This task adds `AppController::notifications(&self) -> &[Notification]`,
the whole stack, oldest first, including entries that have aged out but
not yet been collected. `get_notifications` publishes it.

## 2. The two decisions, and why they went that way

### Read-only, not read-and-clear

`get_notifications` takes `&self` and removes nothing. Two reads return
the same entries.

The alternative — draining on read — is tempting for a test harness
because it makes "what did THIS call push" trivial. It is wrong here for a
reason that is not about tests: **the next reader is usually the
operator**, still looking at the screen. A tool that consumed the stack
would clear toasts the operator had not read yet, from a call they did not
make. It would also make two agents (or an agent and a retry) see
different histories of the same run.

The "what did this call push" problem is solved without draining, in
F3.1: snapshot `notifications().len()` before the dispatch and read the
tail after. That works precisely because reads do not mutate, and because
the stack only ever grows until the collector runs —
`the_stack_only_grows_so_the_tail_belongs_to_the_latest_add` pins that.

`mcp_get_notifications` is declared `&self` so the compiler enforces this,
not a comment.

### Age is measured from the push, in this process

`age_seconds` is `created_at.elapsed()`, evaluated when the call is
served. Given the stack is not persisted, that is the only meaning
available, and the honest consequences are stated on the wire and in the
description rather than left for a reader to discover:

- ages are relative to the push, not to process start or to any wall
  clock;
- the stack is empty after a restart, so an age is never comparable across
  one;
- `ttl_seconds` is the severity's TTL and `visible` is `age < ttl`, both
  derived from `Notification`, so a reader does not have to know the
  table;
- expired entries are collected on the frame loop, so an expired one may
  already be gone. This is why `include_expired` defaults to **true**: a
  test asserting what the operator saw must not lose the evidence because
  the assertion ran a second late. Pass `false` for only what is on
  screen now.

The reply carries a `note` field saying all of that, so an agent reading
only the JSON is not misled.

## 3. Reply shape

```json
{
  "notifications": [ { "index": 2, "message": "…", "severity": "warning",
                       "age_seconds": 0.4, "ttl_seconds": 6.0, "visible": true } ],
  "total": 3, "returned": 3, "visible_count": 3,
  "include_expired": true,
  "note": "Read-only; nothing was removed. …"
}
```

`index` is the position in the stack (0 = oldest) and is preserved when
the list is reversed to newest-first, so two reads can be lined up against
each other and against F3.1's `notifications` array — which uses the same
`notification_json` builder, so the two surfaces cannot drift.

`limit` truncates after the reverse, so it returns the newest N. `total`
is the count after filtering and before truncation; `returned` is what you
got.

is now checkable from outside the module that made it.

The description test is deliberately strict about wording. "Read-only" is
not a nicety on this surface: an agent that believes a read drains the
stack will avoid calling twice and will report the operator's history
wrongly.

## 9. What this task did NOT do

1. **It does not clear, and there is no tool that does.** If a future task
   wants a "dismiss" it should be its own tool with its own name, so that
   consuming the operator's toasts is never something a read did.
2. **No persistence.** The stack still dies with the process; nothing here
   writes it anywhere.
3. **`Notification` gained no id.** Entries are identified by their stack
   index, which is stable only until the collector runs. An id would make
   two reads across a gc alignable; nothing needed that yet.
4. **The dispatch arm is not driven end-to-end** (the `RsCamApp`
   construction limit, as in F1.1 and F3.1). The accessor and the JSON
   builder are covered; the arm's own few lines are not.
5. **No live call.** The MCP server was down.
