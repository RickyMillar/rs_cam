# F1.6 — G-DEPTHSTOCK: a 2.5D depth beyond the stock thickness is a caution

Finding: UX-R03-007 (`planning/ui_review_2026-09-09/results/R03/REPORT.md`).
Branch: `ui-fix/F1.6` from `b0846bcd`. Date: 2026-09-10.

## What was wrong

A pocket 15 mm deep on a 12 mm board generated and simulated silently. The
Operations row read OK, the inspector header read Done, and no surface said
the cut goes through the board and into the bed. The static validator
(`validate_toolpath`) has only blocking rules. The header ribbon's cautions
come from the core static-check adapter, which receives
`ResolvedHeights::from_context` — a snapshot whose `bottom_z` IS the stock
bottom — so no depth comparison was possible on that path either.

## Which depth source is authoritative, and why

The rule reads the deeper of two bottoms and compares it with
`HeightContext::stock_bottom_z`:

1. **The operation's depth field, from the resolved Top Z.** This is what the
   generators cut. `OperationConfig::cutting_levels(top_z)`
   (`crates/rs_cam_core/src/compute/catalog.rs:2591`) steps from `top_z` to
   `top_z - cfg.depth` for Pocket, Profile, Adaptive, Zigzag, Rest, Trace and
   Face; `session/compute.rs:1199` computes it, and `execute.rs`'s
   `effective_levels` uses it whenever it is non-empty. VCarve
   (`max_depth`), Inlay (`pocket_depth`), Chamfer and Drill anchor their
   depth at the top the same way. None of these generators read a pinned
   Bottom Z. The field value comes from
   `OperationConfig::default_depth_for_heights()`, the same accessor the
   Heights tab uses.
2. **The resolved Bottom Z of the Heights tab.** `HeightsConfig::resolve`
   gives `top_z - op_depth` in `Auto`, so the two readings agree in the
   common case. A `Manual` or `FromReference` pin below the stock bottom is
   what the Heights tab shows the operator, so it cautions too (case d).

Caveat for the lead: for the depth-stepping family a pinned Bottom Z does
not reach the generator (`cutting_levels` reads `cfg.depth`). A pinned pin
below the stock therefore cautions on the Heights tab's own number, not on
the emitted motion. That is a pre-existing inconsistency between the Heights
tab and the 2.5D generators, not introduced here, and not fixed here.

Frame: `stock_top_z` / `stock_bottom_z` come from
`SetupEvalContext::heights_stock_bbox` — world for an identity setup,
zero-rooted local for a flip — so a flipped setup has the same thickness.
The sentry checks this.

Threshold: the caution fires only when the excess is above `1e-6` mm. A
through cut exactly at the stock thickness (UX-R03-006, F1.7) does not
trigger it.

## Operations covered

| Read by the rule | Depth field | Not read | Why |
|---|---|---|---|
| Face | Depth | 3D family | the mesh is the floor, `DepthSemantics::None` |
| Pocket | Depth | ProjectCurve | its depth is below the mesh surface, not the stock top |
| Profile | Depth | AlignmentPinDrill | spoilboard penetration is the point of the operation |
| Adaptive | Depth | | |
| VCarve | Max Depth | | |
| Rest | Depth | | |
| Inlay | Pocket Depth | | |
| Zigzag | Depth | | |
| Trace | Depth | | |
| Drill | Depth | | |
| Chamfer | Chamfer Width (proxy) | | |

Chamfer note: the real chamfer cut depth is `(width + tip_offset) / tan(half
angle)`, which needs the tool. The rule uses `chamfer_width`, the same proxy
the Heights tab uses for Bottom Z, so the two surfaces agree. For any V-bit
this proxy under-reads the depth; it never over-reads.

## Where it shows

- **Header**: the inspector ribbon under Generate prints
  `Safety: Depth exceeds stock thickness by 7.00 mm` in the actionable
  (amber) tier, with the `bottom_z` vs `stock_bottom_z` compare on hover. The
  Mods tab badge turns amber (it reads the same list).
- **Row**: an amber row directly under the depth field in the operation's
  parameter grid, same sentence, hover explains the bed cut and the dials.
- **Generate** stays enabled: `validate_toolpath` is untouched.
- **Not** on the Operations card row (`toolpath_panel.rs` prints compute
  status only) and **not** on MCP `get_toolpath_diagnostics`: that tool
  routes through the core `diagnose_toolpath_with_trace`, which does not
  receive the `HeightsConfig`. Moving the rule into the core
  `heights_checks` adapter would give both; that is a core change and was
  out of scope for this task.
