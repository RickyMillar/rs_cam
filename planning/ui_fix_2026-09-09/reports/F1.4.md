Finding: UX-R03-004 (`planning/ui_review_2026-09-09/results/R03/REPORT.md`),
census row "Drill" (`results/R03/census.md`), PLAN.md §3 row F1.4 (X3).
Branch: `ui-fix/F1.4` from `cbe20d06`. Worktree
`/home/ricky/personal_repos/rs_cam_wt_c`. Date: 2026-09-10.

## What was wrong

`drill_holes_for_config` (`crates/rs_cam_core/src/compute/execute.rs`)
resolved a `Drill` op with no explicit pick (`selected_holes == None`) to the
vertex centroid of every closed polygon in the model. On
`fixtures/demo_star.svg` (one closed polygon, no circles, no points) that
generated one hole through the middle of the star at (50, 51.1), simulated
clean, and read `Within` on all three drill gates. The inspector said
"Drill holes from SVG circle positions" and showed no target list, because
`draw_drill_target_selector` returned early when the model had no
`DrillTarget`. The static validator and the core precondition adapter were
silent: the adapter's `Drill` arm read `has_polygons`, so any drawing passed.

## The fallback decision: removed from the generator, circles classified at import

The PLAN row allowed either keeping the centroid fallback when targets exist
and none are picked, or removing it. The generator's fallback is removed. A
hole position comes from ONE of two sources: an explicit pick, or a
`DrillTarget` the model exposes. With no pick the op drills every target.
With no pick and no targets it refuses. Keeping the fallback when targets
exist would have kept the same defect in miniature (a DXF with an outline
and four circles drilled five holes).

Rework (lead review, 2026-09-10): the first version refused on EVERY SVG,
because usvg flattens a `<circle>` to a path before this crate sees it and
an SVG therefore exposed no `DrillTarget`. That regressed the documented
feature "SVG circles drill" (FEATURE_CATALOG line 28), which the centroid
path had been carrying. The finding was that a STAR got drilled, not that
circles should stop. So the 2D import doors now classify circle-like closed
rings as drill targets, and the generator keeps reading targets only:

- `svg_input::circle_like_ring(ring) -> Option<(centre, diameter)>`. Rule:
  at least 8 vertices, and with `c` the vertex centroid and `r̄` the mean
  vertex distance from `c`, every vertex satisfies
  `|r_i − r̄| ≤ max(0.02·r̄, 0.05 mm)`. A star fails on radius spread
  (~45 vs ~18), a rectangle on count and spread, an ellipse 10×6 on spread.
  A regular 8+-gon is accepted and drills at its centre. This is a geometry
  classifier, not a safety gate; no gate threshold moved.
- `svg_input::circle_like_drill_targets(polygons)` scans EXTERIORS AND
  HOLES, because `detect_containment` files a circle drawn inside an
  outline as that outline's hole (that is exactly `demo_pocket.svg`). Each
  hit is a `DrillTargetKind::CircleCenter { diameter }` on layer `circles`,
  so "select all in layer" works on an SVG.
- Both SVG doors call it AFTER the unit scale (`io::load_model_file`,
  `session::project_file::load_model_geometry`), so the two doors agree
  (the G-UNITSRELOAD sentry's invariant) and the mm floor is in mm. DXF is
  not scanned: a `CIRCLE` entity already yields its own target, and
  scanning its flattened polygon would double-count it.

Consequence: `demo_pocket.svg` drills its circle and nothing else;
`demo_star.svg` refuses; a DXF behaves as before minus the outline centroid.

## Sentry and pre-fix proof

`crates/rs_cam_core/tests/drill_no_targets_refuses_g_drillcentroid.rs`,
four cases through `ProjectSession::add_*` and `generate_toolpath`:

1. `fixtures/demo_star.svg` via `io::load_model_file`, `Drill` with default
   selection: `Err` containing "No drill targets", `get_result(0)` is `None`.
2. `fixtures/demo_pocket.svg` (rounded rect + `<circle>` at (40, 30) r=10),
   default selection: the model exposes exactly one target; ONE hole is
   drilled, within 0.1 mm of (40, 30); the rectangle is not a hole.
3. The star plus ONE synthetic `DrillTarget` (`CircleCenter` at (20, 30),
   what a DXF with an outline and one `CIRCLE` imports to), default
   selection: the emitted columns are exactly {(20, 30)}, never (50, 51.1).
4. Targets present, `selected_holes: Some(vec![])`: still refuses with
   "No drill targets selected".

Pre-fix run against `cbe20d06` (case 1 and 2 fail, case 3 passes):

```text

  (columns [(50.0, 51.1), (50.0, 51.1), (50.0, 51.1)]) — pre-fix this was one
  hole at the star's polygon centroid
a_drawing_with_one_circle_drills_the_circle_centre_and_nothing_else --- FAILED

  right: [(20000, 30000)]
```

Pre-fix the pocket SVG drilled TWO holes (the circle and the rounded
rectangle's vertex centroid), because the old fallback took every closed

The third case uses a synthetic target rather than a DXF fixture: the repo
has no DXF fixture with a `CIRCLE`, and `LoadedModel::drill_targets` is the
