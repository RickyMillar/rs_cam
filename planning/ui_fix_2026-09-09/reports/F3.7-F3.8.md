The one that passed in that run was the `set_toolpath_param` test — the
pre-fix description does not claim to rebind, correctly. Be precise
about that number: the run above was made before I added the pointer

**(b) The one key an agent would try is refused.** This is the pre-fix
dead-end evidence the task asked for, captured on the pre-fix tree with
a throwaway probe (`crates/rs_cam_core/tests/zz_prefix_probe.rs`, since
deleted) on a session with two tools and one Pocket toolpath bound to
tool id 0, **verbatim**:

```
--- PRE-FIX PROBE ---

set_toolpath_param(0, "model_id", 7) -> Err(InvalidParam("unknown parameter 'model_id' for Pocket operation. Valid parameters: stepover, depth, depth_per_pass, feed_rate, plunge_rate, climb, pattern, angle, finishing_passes, spindle_rpm"))

after all three: tc.tool_id = 0 (was 0), tc.model_id = 0
```

So the param route neither rebinds nor silently mis-writes: it refuses,
and it lists the params that ARE valid. Why it refuses is structural —
`ProjectSession::set_toolpath_param`'s `_ =>` arm merges the key into
the operation config's `params` object through a serde round-trip and
then verifies the key survived; a grep of
`crates/rs_cam_core/src/compute/operation_configs.rs` finds **no**
operation field named `tool_id` or `model_id`, so no operation type can
absorb either. Rest's `prev_tool_id` IS a real param on Rest (the
rest-analysis reference tool) — the near miss that could make an agent
believe the binding is reachable. It is a different field.

R0.3 §2.2's claim is therefore confirmed, not merely repeated.

## 2. The event each tool dispatches — and why there is none

The task asked me to name the `AppEvent` the inspector's Tool / Input
combos emit and dispatch the same one. **They emit no event.** This is a
finding, not an evasion, and I confirmed it by reading the whole path:

- `crates/rs_cam_viz/src/ui/properties/mod.rs`, inside the `Geometry`
  collapsing header: the Tool: combo is
  `ui.selectable_value(&mut entry.tool_id, *id, name)` and the Input:
  combo is `ui.selectable_value(&mut entry.model_id, *id, name)`. Both
  write a field of the panel's temporary `ToolpathEntry`. Neither pushes
  onto `events`.
- The panel's caller then calls `write_entry_config_to_session(&entry,
  &mut state.session)`, which copies `tc.tool_id = entry.tool_id.0;`
  and `tc.model_id = entry.model_id.0;` straight into the session's
  `ToolpathConfig`.
- Grep of the `AppEvent` enum (`crates/rs_cam_viz/src/ui/mod.rs`) finds
  no `SetToolpathTool` / `ToolpathToolChanged` / any variant carrying a
  tool or model binding.

So there was no widget event to share. The nearest true equivalence is
the LAYER: `mcp_set_toolpath_param` and `mcp_set_toolpath_heights` both
mutate through a `ProjectSession` setter, and that is the layer the GUI
write-back reaches too (one call lower, without a setter). The two new
MCP tools therefore route through **new core setters**, which is the
place `write_entry_config_to_session` should eventually call as well:

| MCP tool | `McpRequestKind` | viz handler | core setter |
|---|---|---|---|
| `set_toolpath_tool` | `SetToolpathTool { index, tool_id }` | `RsCamApp::mcp_set_toolpath_tool` | `ProjectSession::set_toolpath_tool` |
| `set_toolpath_model` | `SetToolpathModel { index, model_id }` | `RsCamApp::mcp_set_toolpath_model` | `ProjectSession::set_toolpath_model` |

Both dispatch arms follow F1.1: they select the toolpath and switch to
the Toolpaths workspace BEFORE the handler, then push exactly one toast
AFTER it, classified from the reply by
`McpOutcome::from_json_response`. The select + switch pair the
`SetToolpathParam` arm does inline is factored into
`RsCamApp::select_toolpath_for_mcp` and used by both new arms; the
`SetToolpathParam` arm is left as it was, because it also records an
`mcp_highlights` key for the changed param name and a rebind has no
param name to highlight.

## 3. Parameter structs

In `crates/rs_cam_mcp/src/server.rs`:

```rust
pub struct SetToolpathToolParam { pub index: usize, pub tool_id: usize }
pub struct SetToolpathModelParam { pub index: usize, pub model_id: usize }
```

Both fields of both structs are required integers; the schema sentry
pins that.

**The id-vs-index decision.** PLAN.md's F3.7 row writes
`set_toolpath_tool(index, tool_id)`; R0.3 §7 Q4 writes
`set_toolpath_tool(index, tool_index)`. I took `tool_id`, the
project-assigned id, because that is the number
`ToolpathConfig.tool_id` actually stores and the number `list_tools`
publishes as `id`. It **differs from `add_toolpath`, which takes a
positional `tool_index`** — and the two agree in any project that has
never had a tool removed, which makes a wrong guess silently obeyed
rather than refused. Three mitigations, all pinned by the sentry:

1. the tool description says "NOT its 0-based position (`add_toolpath`
   takes a `tool_index` — these differ once a tool has been removed)";
2. the success reply echoes the resolved `tool` object (id, name,
   tool_type, diameter), so a caller can see what it bound;
3. the refusal appends `Tool ids in this project: [...]`.

`model_id` needed no such decision: every model-taking tool on the
surface (`add_toolpath`, `ModelIdParam`) already uses the id.

## 4. Invalidation, and how it compares to the GUI route

Both core setters end in `invalidate_result_chain(index, enabled)` —
the same call `set_face_selection`, `set_heights_config`,
`set_boundary_config`, `set_stock_source` and `set_dressup_config` make.
It drops this toolpath's cached result AND, through
`invalidate_output_dependents`, every downstream `FromRemainingStock`
operation in the setup, because a different cutter (or a different
input) leaves different stock. `replace_toolpath_config` would have been
the lazy reuse and is **wrong here**: it does a bare `results.remove` +
`simulation = None` with no chain propagation.

On the viz side both handlers additionally do what
`mcp_set_toolpath_param` does: `gui.mark_edited()` and
`mcp_apply_stale(MutationKind::ToolpathParamChanged { toolpath_index })`,
which stamps `stale_since` on the GUI runtime rows so `list_toolpaths`
reports `stale: true`.

**Where this does NOT match the GUI, and why.** The GUI's Tool: / Input:
combos invalidate **nothing**. `write_entry_config_to_session` copies
both fields into the session directly, and the freshness block that
follows it only compares `op_before` / `heights_before` /
`boundary_before` — there is no `tool_before` or `model_before`, so a
GUI rebind sets no `stale_since`, calls no `mark_edited`, and leaves the
core result cached. `UndoAction::ToolpathParamChange` likewise carries
operation, dressups and face selection only, so a GUI rebind is not
undoable either. Taking the instruction "match what a GUI rebind
invalidates" literally would mean shipping an MCP tool that leaves a
stale result presented as current, which is the defect class this
programme exists to remove. I matched the **core mutation convention**
instead and made the MCP route the stricter of the two. The GUI gap is
recorded in §7 as a follow-up; I did not fix it, because R0.1 / F2.1
replace the whole GUI freshness flag scheme in P2 and night 1 already
deprioritised F1.11 for that reason.

Two more deliberate non-behaviours:

- **The tool SHAPE is not checked.** An operation whose registry entry
  rejects the bound cutter is a *blocked* operation the operator repairs
  by rebinding; refusing the rebind would delete the only repair, which
  is exactly the dead end F3.7 exists to close (R0.3 §3.1). The refusal
  stays at `ToolConstraintsDef::allows`, read by
  `execute.rs:generate_scallop` / `generate_unified_finish` BEFORE they
  ask for a mesh.
- **The geometry KIND is not checked** by `set_toolpath_model`. Same
  reason; that precondition belongs to F4.2's contract.

`set_toolpath_model` DOES refuse a `model_id` that resolves to nothing,
naming the ids that exist — unlike `add_toolpath`, which accepts one and
leaves a dangling reference (R0.3 §2.2's binding table). I did not change
`add_toolpath`; F4.2 owns it.

A rebind to the id already bound is a no-op and invalidates nothing.

## 5. The decision on `set_toolpath_param`

**The new tools are the only route. `set_toolpath_param` keeps its
current behaviour and keeps refusing `tool_id` / `model_id`.** Four
reasons:

1. `set_toolpath_param` writes the OPERATION's params. `tool_id` and
   `model_id` are sibling fields of `ToolpathConfig`, a different
   object. One function writing two objects under one name is how the
   next reader gets it wrong.
2. Today's refusal is precise and lists the valid params — it is the
   signal that sends an agent to the right tool. Turning it into a
   silent success removes the only feedback.
3. Rest's `prev_tool_id` is a genuine operation param. Making `tool_id`
   a magic key beside it invites the belief that `prev_tool_id` rebinds
   a binding too. Keeping the namespaces disjoint kills that class.
4. The invalidation and the future precondition contract hang off the
   BINDING, not off a param; one route, one meaning.

The one thing that DID change on `set_toolpath_param` is its
description, which now ends the sentence the dead end left unfinished:
"This writes the OPERATION's own params only: it cannot change which
cutter or which input model the toolpath is bound to, and refuses those
keys — use `set_toolpath_tool` / `set_toolpath_model`." An agent that
reads only this description is exactly the agent that hit the dead end.
No behaviour, schema field or reply payload of `set_toolpath_param`
changed.

`rebind_is_not_reachable_through_the_param_route` pins the refusal so
the two namespaces cannot merge later by accident, and
`set_toolpath_param_does_not_claim_to_rebind_and_names_the_route_that_does`
pins both halves of the description rule: the keys are never offered as
params, and both new tool names are present.

## 7. What these tasks did NOT do

1. **The GUI combos are untouched.** They still write `tool_id` /
   `model_id` into the session with no invalidation, no `stale_since`,
   no `mark_edited` and no undo entry (§4). The MCP route is now
   stricter than the GUI route for the same edit. This belongs to R0.1 /
   F2.1's freshness rewrite; adding a flag site here would be rework.
2. **No `AppEvent` was added**, because the widgets emit none. If P5
   gives the combos an event, both handlers should move onto it.
3. **`face_selection` is not cleared on a model rebind.** BREP face ids
   belong to the model that was bound when they were picked; after a
   rebind they point into a different mesh. The tool description and the
   core doc-comment say so, but nothing enforces it. Clearing them is a
   product decision, not a refactor.
4. **No precondition contract.** These tools deliberately allow an
   incompatible tool shape and an incompatible geometry kind; F4.2 owns
   the refusal contract and the `blocked` list.
5. **`add_toolpath` still does not validate `model_id`** (R0.3 §2.2).
   Only the rebind door validates. Out of scope here.
6. **Nothing was exercised live.** The embedded MCP server was down; the
   two tools were tested through the in-process router and the core
   session API only. No `rs_cam_gui` was started.
8. **No undo entry** for a rebind, on either surface. Adding one means a
   new `UndoAction` variant, which is F3.3's neighbourhood.
