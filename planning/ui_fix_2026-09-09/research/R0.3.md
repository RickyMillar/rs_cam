## 1. Question

An operation can need a tool shape (V-bit, ball tip), a geometry kind (2D
curves, 3D mesh, both), and for Rest a previous tool plus an earlier
operation. Today the repo checks these in four designs with four
vocabularies, at four moments, on four surfaces. Which single contract
should replace them, so that the GUI, MCP and CLI say the same sentence,
the operation always exists, and the fix is in the inspector?

## 2. What the code does today (re-verified at HEAD)

### 2.1 The one source that already exists

The registry carries a typed constraint per operation and a predicate on
it. Both exist and both are already wired to the two generators that
refuse at run time.

```rust
// crates/rs_cam_core/src/compute/catalog.rs — ToolConstraintsDef
pub struct ToolConstraintsDef {
    pub required_kinds: &'static [CutterKind],
    pub supports_v_bit: bool,
}
impl ToolConstraintsDef {
    pub const ANY_TOOL: Self = Self { required_kinds: &[], supports_v_bit: true };
    pub fn allows(&self, kind: CutterKind) -> bool {
        if !self.supports_v_bit && kind == CutterKind::VBit { return false; }
        self.required_kinds.is_empty() || self.required_kinds.contains(&kind)
    }
}
```

Membership at HEAD (`catalog.rs`, `REG_*` statics, pinned by the test
`tool_constraints_are_an_explicit_per_op_decision`):

| Operation | `required_kinds` | `supports_v_bit` |
|---|---|---|
| VCarve, Inlay, Chamfer | `[VBit]` | true |
| Scallop, UnifiedFinish | `[Ball, TaperedBall]` | false |
| the other 19 (incl. Pencil, SpiralFinish, DropCutter) | `[]` (`ANY_TOOL`) | true |

`CutterKind` has five values (`feeds/mod.rs:CutterKind`: Flat, Ball,
Bull, VBit, TaperedBall) and is a bijection with `ToolType`
(`compute/tool_config.rs:ToolType::cutter_kind`, `feeds/mod.rs:CutterKind::tool_type`).
`GeometryRequirement` has four values (`catalog.rs:GeometryRequirement`:
Stock, Polygons, Mesh, Both) read through `OperationType::geometry_requirement`.

The predicate is consumed by exactly three callers:

- `compute/execute.rs:generate_scallop` and `generate_unified_finish`
  (the generate-time refusal; the comment says "THE reconciliation point").
- `compute/catalog.rs` unit tests.

It is NOT consumed by the add-time Suggest gate, the GUI static
validator, the static-check diagnostic, the add menu, or the MCP add
handler. That is the whole problem in one sentence.

## 3. Options

### 3.1 Keep the add-time refusal, or always create?

| | Keep A1/A2 (refuse at add) | Always create, block in place |
|---|---|---|
| Operator sees the fix | No. The toast is gone in 6 s and names no tool | Yes. The blocked row and the Tool/Input combo are one screen |
| MCP agent | Gets an error and no index; must guess the fix | Gets an index and a `blocked` list; can act |
| Membership drift | Two predicates (feeds + registry) must agree; today they do not (Bull, Spiral) | One predicate |
| Loaded / duplicated / tool-swapped ops | Not covered — they bypass add | Covered — the check runs on the config, not on the click |
| Cost | none | Suggest must have a fallback recipe when it refuses |

Recommendation: always create. The plan already leans this way. The only
add-time refusals that stay are the two "nothing to bind" cases (A3 no
tools, A4 no models). They are not precondition mismatches; there is no
object to attach a blocked state to.

### 3.2 Where the single check lives

| | Core registry predicate + core precondition module | GUI validator (extend `validate_toolpath`) |
|---|---|---|
| CLI and MCP share it | Yes, by construction | No — CLI cannot see `rs_cam_viz`; MCP only through the GUI process |
| Generators read it | Already do (`allows`) | Cannot |
| Diagnostics adapters read it | Same crate | Would need a third copy |
| Two hand-copied validators (`validate_toolpath`, `validate_toolpath_config`) | Collapse to one thin wrapper | Stay as two |

Recommendation: core. The GUI keeps a wrapper that maps the typed list
into UI rows.

### 3.3 How MCP and CLI share it

- MCP `add_toolpath` returns `blocked: [{id, message, fix}]` in the
  mutation result; `list_toolpaths` / `get_toolpath_params` carry the
  same list; `generate_toolpath` on a blocked op returns the joined
  messages (as C2 does now, but from the same table).
- CLI `run` / `job` call the same core function before
  `generate_toolpath` and print each message on its own line; the
  `project` report prints the list per operation. Whether the CLI
  `project` report already prints static-check diagnostics is
  UNVERIFIED (not read).

## 4. Recommendation — the contract

### 4.1 The predicate and the list

In `rs_cam_core`, one new module `compute/preconditions.rs`. Two public
functions and one enum.

```rust
impl OperationType {
    /// THE tool-shape predicate. Delegates to the registry.
    pub fn accepts_tool(self, kind: CutterKind) -> bool {
        self.registry_entry().tool_constraints.allows(kind)
    }
    /// Human text for the menu hover, or None for ANY_TOOL.
    pub fn tool_requirement_text(self) -> Option<String>;
}

pub struct PreconditionInputs<'a> {
    pub tools: &'a [ToolConfig],
    pub models: &'a [ModelFacts],          // id, has_polygons, has_mesh, has_enriched_mesh
    pub setups: &'a [SetupFacts],          // ordered toolpath (id, tool_id, model_id, enabled)
}

pub fn check_toolpath_preconditions(
    tc: &ToolpathConfig,
    inputs: &PreconditionInputs<'_>,
) -> Vec<Precondition>;
```

`Precondition` carries the data; `id()` and `message()` are the only
text producers in the repo.

```rust
pub enum Precondition {
    NoTool,                                     // tool_id resolves to nothing
    ToolKindNotAllowed { op: OperationType, actual: ToolType },
    StepoverExceedsDiameter { stepover_mm: f64, diameter_mm: f64 },
    NoModel,                                    // model_id resolves to nothing
    GeometryMissing { op: OperationType, need: GeometryRequirement, model_name: String },
    RestPrevToolMissing,
    RestPrevToolNotLarger { prev_mm: f64, curr_mm: f64 },
    RestNoPriorSource,
}
impl Precondition {
    pub fn id(&self) -> &'static str;     // "precondition.tool_kind", … (extend diagnostics::ids::PRECOND_*)
    pub fn message(&self) -> String;      // the table below
    pub fn fix(&self) -> PreconditionFix; // Tool | Input | Parameter("stepover") | PreviousTool | Order
}
```

`ToolKindNotAllowed` covers `supports_v_bit == false` too: `allows`
already folds it in, and no op today has `supports_v_bit == false` with
an empty `required_kinds`, so one message id is enough.

### 4.2 The text table

One sentence per condition. Wood-router operator words. Tool names come
from `ToolType::label()` ("End Mill", "Ball Nose", "Bull Nose", "V-Bit",
"Tapered Ball Nose"), lower-cased in prose. Used verbatim by the GUI
rows, the MCP `blocked` list, the CLI lines, the diagnostic row, and the
generator's `InvalidTool` payload.

| id | Condition | Sentence |
|---|---|---|
| `precondition.no_tool` | `tool_id` resolves to no tool | `This operation has no tool; pick one in the Tool list.` |
| `precondition.tool_kind` | `!op.accepts_tool(kind)` | `{Op label} needs a {required}; the selected tool is a {actual}.` e.g. `Scallop Finish needs a ball nose or tapered ball nose; the selected tool is an end mill.` / `VCarve needs a V-bit; the selected tool is a ball nose.` |
| `precondition.stepover` | `stepover >= diameter` (Pocket, Adaptive) | `Stepover {s} mm must be smaller than the tool diameter {d} mm.` |
| `precondition.no_model` | `model_id` resolves to no model | `This operation has no input; pick one in the Input list.` |
| `precondition.geometry` | model lacks the `GeometryRequirement` | `{Op label} needs {need}; the input "{model}" has none.` with `need` ∈ `2D curves (SVG or DXF)` / `a 3D mesh (STL or STEP)` / `both 2D curves and a 3D mesh` |
| `precondition.rest_prev_tool_missing` | Rest `prev_tool_id` is `None` | `Rest Machining needs the previous tool; pick it in the Previous tool list.` |
| `precondition.rest_prev_tool_not_larger` | prev diameter ≤ current | `The previous tool ({p} mm) must be larger than this tool ({c} mm).` |
| `precondition.rest_no_prior` | no earlier enabled op in the setup with prev tool on the same model | `Rest Machining needs an earlier enabled operation in this setup that uses the previous tool on the same input.` |

Required-list rendering: join labels with "or" (`ball nose or tapered
ball nose`). Menu hover uses the fragment after "needs": `Needs a ball
nose or tapered ball nose` / `Needs a V-bit`.

### 4.3 Binding rule on add (GUI)

Tool, in order:

1. If `Selection::Tool(id)` is current and `op.accepts_tool(kind)`, that tool.
2. Else the first tool in project order with `accepts_tool == true`.
3. Else the first tool; the op is created with `precondition.tool_kind`.

Model, in order:

1. If the selection is a model and it satisfies `geometry_requirement`, that model.
2. Else the first model in project order that satisfies it (`Both` needs both; `Stock` needs nothing).
3. Else the first model; the op is created with `precondition.geometry`.

Step 1 goes beyond the plan text ("first compatible tool"); it is what
UX-R03-002's "Expected" line asks for ("picks a compatible tool (or the
selected one)"). See §7 Q1.

MCP keeps explicit `tool_index` and `model_id`; the handler validates
that `model_id` exists (today it does not) and returns the `blocked`
list. CLI keeps its own binding.

Suggest on add: call `suggest_params`; on `Err(FeedsError)` fall back to
`OperationConfig::new_default(op_type)` + `apply_stock_defaults`, with
`FeedsProvenance::default()`. The refusal is not a reason to withhold the
object; the Feeds tab will show the blocked row instead (F1 below).

### 4.4 Inspector blocked state

- `can_generate = preconditions.is_empty() && !tools.is_empty()` — same
  gate as now, one source.
- Under the Generate button: one row per `Precondition`, red
  (`Error` colour, not the current orange), text = `message()`.
- The control named by `fix()` gets a red frame stroke on the Tool:,
  Input:, Previous tool: combo or the stepover field, and the Geometry
  collapsing header opens when a fix lives inside it.
- Generate's disabled hover = the messages joined by newline.
- Queue card: a `BLOCKED` badge in the error colour with the same hover,
  derived from the list the way `draw_rest_badge` derives `dep`, so the
  card stops saying `PEND`/"Ready" for an op that cannot run.
  `ComputeStatus` is not changed (it is stored state; a derived badge is
  enough).
- Feeds tab: when the list is non-empty, show the `tool_kind` row in
  place of "Feeds unavailable: …"; keep the feeds error only for the
  cases the registry cannot express (DropCutter with a scallop height on
  a flat tool).

## 5. Acceptance — `tool_precondition_one_contract_g_refusal.rs`

Two files, because two surfaces live in `rs_cam_viz`.

### 5.1 Core: `crates/rs_cam_core/tests/tool_precondition_one_contract_g_refusal.rs`

Matrix: every `OperationType` in `ALL` (24) × every `ToolType` in `ALL`
(5) = 120 cells. For each cell, build a `ProjectSession` with one tool of
that type and a model that satisfies the op's geometry (a small STL and
SVG from `fixtures/`, or both for ProjectCurve; stock-only for Face and
AlignmentPinDrill), add the op, and assert:

1. `op.accepts_tool(kind) == registry_entry().tool_constraints.allows(kind)` (trivial today; pins the delegation).
2. `check_toolpath_preconditions` contains `precondition.tool_kind` iff `!accepts_tool`, and no other tool-kind row.
3. `diagnose_toolpath_inputs` contains exactly one `Blocking` row with that id iff `!accepts_tool`; message equals `Precondition::message()`. Pencil × EndMill: zero rows (today: one Critical).
4. `generate_toolpath` returns `OperationError::InvalidTool(msg)` with `msg == message()` iff `!accepts_tool`; otherwise it does not return `InvalidTool` (any other outcome is allowed — the matrix pins the refusal class, not success).
5. `suggest_params` on a refused feeds cell (Scallop/Unified/Spiral × Flat/VBit) is an `Err`, and the op is still created by the shared add path (a core `add_toolpath` never refused; the pin is that the CLI helper does not either).

Expected fixed rows the test names in its assertion messages:
(Scallop, BullNose), (UnifiedFinish, BullNose), (Scallop, VBit),
(Pencil, EndMill), (SpiralFinish, EndMill).

How it fails today: (2) has no producer; (3) fails on Pencil×EndMill and
passes Scallop×BullNose with zero rows; (4) fails on the message text for
all five V-bit and ball cells.

## 7. Open questions for the human

1. **Selected tool first?** §4.3 step 1 binds the selected tool when it
   is compatible. The plan text says "first compatible tool" only. Which?
2. **"Nothing to bind" refusals.** With no models in the project the menu
   greys every non-stock entry, so A4 is reachable only by another
   `AddToolpath` emitter (none found). Keep A3/A4 as the last two add-time
   refusals, or create the op with an unresolvable `model_id` and rely on
   `precondition.no_model`? The `unwrap_or(0)` sentinel collides with a
   real id once a model is imported, so "create" needs a real sentinel.
3. **Bull nose on Scallop.** The registry excludes it; the feeds formula
   accepts it (a corner radius defines the scallop). Keep the registry
   as the truth (recommended here — the generator was written for a ball
   tip) or widen `required_kinds`? Either way F4.2 must state the
   decision in `tool_constraints_are_an_explicit_per_op_decision`.
4. **MCP rebind tools.** The contract's fix path does not exist on MCP.
   F3 needs `set_toolpath_tool(index, tool_index)` and
   `set_toolpath_model(index, model_id)`; without them a blocked MCP add
   is a dead end. Add to F3 or to F4.2?
5. **Severity word.** The diagnostic row for a precondition is `Blocking`
   (matches Rest today), not `Critical` (matches D1 today). Confirm.
6. **Spiral Finish.** After the change it is created and generates with a
   flat tool (registry `ANY_TOOL`), and its Feeds tab shows the feeds
   refusal. Is that the intended product truth, or should Spiral Finish
   join the ball-tip list?
