## 1. Question

An operator opens a project and one model file is not where the project
says it is. What can they do today, and what is the smallest change that
gives them a "Locate file…" route that (a) loads the new file through the
same loader the project uses, (b) saves a path that survives a move of the
project folder, and (c) invalidates every toolpath and simulation built on
the old geometry?

## 2. What the code does today

### 2.1 The model path field and its serialisation

| Layer | Symbol | What it holds |
|---|---|---|
| In memory | `crates/rs_cam_core/src/session/mod.rs` `LoadedModel::path: std::path::PathBuf` — doc: "Original file path (for save round-trip)." | Whatever the constructor put there. Not normalised. |
| On disk | `crates/rs_cam_core/src/session/project_file.rs` `ProjectModelSection::path: String` (`#[serde(default)]`) | The string as written. |
| Save | `crates/rs_cam_core/src/session/save.rs` `ProjectSession::to_project_file` | `path: m.path.to_string_lossy().into_owned(),` — a verbatim copy. **No relativisation.** `to_project_file(&self)` does not receive the destination path; `save(&self, path)` has it and does not pass it down. |
| Load (project door) | `project_file.rs` `build_session_from_project` | `let model_path = std::path::PathBuf::from(&model_section.path);` … `path: model_path,` — the **raw string**. A relative string stays relative and unresolved in memory. |
| Resolution | `project_file.rs` `load_model_geometry` | `let full_path = if raw_path.is_absolute() { raw_path.to_path_buf() } else { base_dir.join(raw_path) };` — resolved **only for the read**, never stored. `base_dir` is `path.parent()` of the project file (`session/mod.rs` `ProjectSession::load`: `let base_dir = path.parent().unwrap_or(Path::new("."));`). |
| Load (interactive door) | `crates/rs_cam_core/src/io.rs` `load_model_file` | `path: path.to_path_buf(),` — the path the file dialog returned, which `rfd` gives as absolute. |

Consequence, and a correction to the PLAN's "paths are saved absolute":
the save is a pass-through. A path is absolute on disk because the
interactive import stored an absolute path; a path that was relative in a
hand-written TOML round-trips relative. Both are true at once, and the rule
is "whatever the constructor put there".

Two related defects follow from the raw string in memory:

1. **Reload from disk resolves against the process CWD, not the project
   dir.** `crates/rs_cam_viz/src/controller/io.rs` `reload_model`:
   `let path = model.path.clone();` … `import::import_model(&path, …)` →
   `load_model_file(path, …)` → `TriangleMesh::from_stl_scaled(path, …)`.
   No `base_dir` is applied. For `missing_model_project.toml`
   (`path = "missing_model.stl"`) Reload looks for `./missing_model.stl`
   relative to wherever `rs_cam_gui` was launched. `rescale_model` has the
   same shape. UNVERIFIED live; read from the code path only.
2. **The warning prints the unresolved string.** `controller/io.rs`
   `open_job_from_path`: `"Model '{}' could not be loaded because '{}' was
   not found.", m.name, m.path.display()` — for a relative path the
   operator reads `'missing_model.stl'`, not the directory that was
   searched.

There is a second, older loader in the GUI crate,
`crates/rs_cam_viz/src/io/project.rs`, with its own
`ProjectModelSection`, `persist_model_path` and `resolve_model_path`.
`persist_model_path` is exactly the rule this task needs:

```rust
fn persist_model_path(project_path: &Path, model_path: &Path) -> String {
    let Some(project_dir) = project_path.parent() else {
        return model_path.display().to_string();
    };
    if model_path.is_absolute() {
        if let Ok(relative) = model_path.strip_prefix(project_dir) {
            return relative.to_string_lossy().to_string();
        }
        return model_path.display().to_string();
    }
    model_path.to_string_lossy().to_string()
}
```

It has **no production caller**: `controller/io.rs` `save_job_to_path`
calls `self.state.session.save(path)` (the core saver), and `rg
"project::save_project|io::project::save_project"` over
`crates/rs_cam_viz/src` finds nothing outside `io/project.rs`. The viz
`load_project` runs only as the fallback arm of `open_job_from_path`
(`Err(session_err) => { … crate::io::project::load_project(path)? … }`).
Its `load_model_section` stores the **resolved** path on the placeholder
(`LoadedModel::placeholder(id.0, resolved_path, …)`), so the two loaders
already disagree on what `LoadedModel::path` means.

`AppEvent` that carries the `PathBuf`:

- `app/input.rs` `AppEvent::SaveJob`: `self.controller.state().gui.file_path.clone().or_else(|| rfd::FileDialog::new()….save_file())` — Save reuses `gui.file_path`; Save As always asks. The project directory at save time is therefore `path.parent()` of whatever `save_job_to_path` receives.

`AppEvent` lives in `crates/rs_cam_viz/src/ui/mod.rs`
(`ImportStl(PathBuf)`, `RescaleModel(ModelId, ModelUnits)`,

### 2.6 The two doors and the sentry

`crates/rs_cam_core/tests/model_units_survive_reload_g_unitsreload.rs`
pins that `io::load_model_file` (interactive) and
`session::project_file::load_model_geometry` (project) return the same
geometry for the same file at the same declared units. It says nothing
about paths or metadata. Two metadata differences remain between the doors
and are relevant to what a relink copies:

| Field | Interactive door `load_model_file` | Project door `build_session_from_project` |
|---|---|---|
| `winding_report` | `Some(winding.inconsistency_fraction * 100.0)` for STL | `None` always |
| `name` | file name of the path | `model_section.name` |
| `path` | absolute (from the dialog) | raw string |

Reload and Import both use the interactive door. A relink is an interactive
re-import of an operator-chosen file, so it belongs on the same door as
Reload; the project door consumes the saved path on the next open, and the
sentry guarantees the geometry agrees.

## 3. Options

### 3.1 Where the action lives

| Option | Cost | Note |
|---|---|---|
| A. Model inspector only | One button in `draw_model_properties`. | The operator must first find the model in the Setup panel. The inspector is the place that already prints `Path:`. |
| B. Load-warning window only | Needs the model id per warning line. `load_warnings` is `Vec<String>`; either the type becomes structured, or the window derives its buttons from `session.models()` where geometry is `None`. | The window is the moment the operator learns of the problem. |
| C. Both (A + B), plus a context-menu item beside "Reload from disk" | A + the derived-buttons form of B + one line in `setup_panel.rs`. | One event, three entry points. The derived form of B leaves `load_warnings: Vec<String>` and the MCP `load_project` reply unchanged. |

### 3.2 Relativisation rule on save

| Option | Rule | Cost | Note |
|---|---|---|---|
| R1. Relative when under the project directory, else absolute | `strip_prefix(project_dir)` succeeds → relative; else the absolute path verbatim. | Port `persist_model_path` (§2.1) into core `save.rs`; give `to_project_file` the project directory. | Already written and unit-tested in `io/project.rs` (tests at lines 1679, 1998 assert the resolved path after load). Cross-drive on Windows falls out as absolute. |
| R2. Always relative | Walk `..` up to a common ancestor. | New helper or a `pathdiff`-style dependency; undefined across Windows drives. | More portable projects, but a `../../../home/x/model.stl` string is fragile and unreadable. |
| R3. Configurable | A post/job setting. | UI, project-file key, docs. | Over scope for a P1-sized task. |

Whichever rule is chosen for disk, the in-memory rule must be fixed with
it, or Reload keeps resolving against the CWD (§2.1 defect 1). The pairing
that closes both:

- **In memory: always the resolved absolute path.** `build_session_from_project` stores `full_path` (the value `load_model_geometry` already computes) instead of the raw string. Import and the viz fallback loader already store absolute paths, so this removes a divergence rather than adding one.
- **On disk: R1**, computed against the directory of the file being written. A project loaded from `a/job.toml` with `path = "m.stl"` resolves to `a/m.stl`, and saves back as `m.stl`; "Save As" into `b/job.toml` writes `/abs/a/m.stl`, which is the truthful answer when the model did not move.

### 3.3 Relink mechanics

| Step | Where | Choice |
|---|---|---|
| Event | `ui/mod.rs` | `AppEvent::RelinkModel(ModelId, PathBuf)`; the UI calls `rfd` and pushes the event, as Import does. |
| Kind | controller | Infer from the new extension (the `match ext.as_str()` in `mcp_import_model` is the pattern; core `project_file::infer_model_kind` is `pub(crate)` and not reachable from viz). If the inferred kind differs from `model.kind`, **refuse** with a notification: a toolpath family bound to a mesh cannot run on polygons, and the Input combo is the tool for "use a different model". Same-family swaps (`.stp` for `.step`) pass. |
| Units | controller | **Keep `model.units`.** The declared units describe the operator's source, not the file on disk; a relink is "the file moved". Reload already keeps them (`model.units.unwrap_or(ModelUnits::Millimeters)`). |
| Load | controller | `import::import_model(&new_path, model_id.0, kind, units)` — the same door as Reload and Import. On `Err`: notification; model untouched. |
| Apply | core `mutation.rs`, new `replace_model_geometry(model_id, loaded: LoadedModel) -> Result<Vec<usize>, SessionError>` | Swap `mesh`, `polygons`, `drill_targets`, `layers`, `enriched_mesh`, `winding_report`, `path`, `kind`; set `load_error = None`; keep `id`, `name`, `units`. Then invalidate (next row) and return the dependent toolpath indices. Refit stock if `stock.auto_from_model` (what `rescale_model` and `add_model` already do). |
| Invalidate (core) | core `mutation.rs`, new `invalidate_model(model_id) -> Vec<usize>` | For every `tc.model_id == model_id`: `invalidate_result_chain(idx, true)`. Unlike `invalidate_tool`, this walks the chain, because a changed model changes what the op removes and therefore every `FromRemainingStock` op below it. `invalidate_output_dependents` already sets `simulation = None`. Return the dirtied indices. |
| Invalidate (GUI) | controller | For each returned index → `tc.id`: `rt.result = None; rt.stale_since = Some(now)` via `toolpath_rt_or_default`. Then `pending_upload = true; mark_edited()`. |
| Warning list | controller | `load_warnings.retain(\|w\| !w.starts_with(&format!("Model '{name}' could not be loaded")))`; `show_load_warnings = !load_warnings.is_empty()`. String matching is ugly but keeps the type unchanged; see §7. |
| Reload / Rescale | controller | Route both through the same apply-and-invalidate helper so they stop skipping `drill_targets`/`layers` and gain the invalidation for free. This is one refactor of two ~30-line functions, not new behaviour. |

Alternatives considered and not recommended: (i) delete-and-re-import
under a new id (breaks every `tc.model_id`, which is exactly what the Delete
guard refuses); (ii) `models_mut()` field swaps in the controller as Reload
does today (leaves the core with no invalidation entry point, so the MCP and
CLI cannot reach it later).

## 4. Recommendation

**Adopt C + R1-with-absolute-in-memory + the §3.3 mechanics.** One event,
one core mutation, one core invalidation, three small UI entry points. It
is P1-sized and can be folded into P1: no threshold moves, no new
dependency, no new project-file key, and every piece has a template in the
codebase already (`invalidate_tool`, `persist_model_path`, the pin-drill
stale mark, the menu-bar `rfd` pattern).
