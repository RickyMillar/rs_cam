## 1. Question

What does "current" mean for a toolpath, a simulation and an export? Where
is that state stored, who changes it, and which surface shows it?

Today three systems each hold a part of the answer and they do not agree.
This document names one state model, one owner for each transition, the
surfaces that render each state, the mutations that must move the state,
and the sentries P2 writes.

Two more stores matter:

- **The GUI result copy.** `ToolpathRuntime::result: Option<ToolpathResult>` is written together with the core insert in the drain's `Ok(computed)` arm and is what the card row 3, the viewport and the sim panels draw from. It is NOT dropped when S1 drops the core entry, by design (`io/export.rs` doc comment above `emitted_toolpaths`: "the viz store keeps its result so the UI can draw the stale toolpath").
- **`ComputeStatus`** (`crates/rs_cam_core/src/compute/config.rs`), stored on `ToolpathRuntime::status`: `Pending / Computing / Done / AwaitingPriorStock / Disabled / Error`. `Disabled` is derived by `ComputeStatus::effective(enabled, raw)` and never stored. `needs_generation()` is true for `Pending` and `AwaitingPriorStock` only. This enum has no arm for "has a result that no longer matches the config".

The core also owns `session::compute::compute_stale_set(session, MutationKind)` with `MutationKind::{ToolpathParamChanged, ToolParamChanged, SetupChanged, StockChanged, AllToolpaths}`. Only the MCP layer calls it (`mcp_apply_stale`). Its `ToolParamChanged` set (toolpaths whose `tool_id` matches) is SMALLER than `invalidate_tool`'s set (which also includes `PlannedTierRegions` ladders that name the tool), so the two "which toolpaths does a tool edit affect" answers already differ inside the core.

### 2.2 Where the three systems disagree

Quoted from the code as read:

1. **The GUI inspector never drops the core result.** `ui/properties/mod.rs::write_entry_config_to_session` writes every `ToolpathConfig` field through `session.find_toolpath_config_by_id_mut` (a plain `iter_mut().find`, `session/mod.rs`). No core setter runs. So after a GUI stepover edit: S1 still holds the OLD result, S2 says stale, the card says OK. Export reads S1 first and emits the old geometry with no fallback involved. The downstream `FromRemainingStock` chain is NOT invalidated either (only the core setters call `invalidate_result_chain`), so the 2026-07-09 "live-v2 staleness collision" class documented on `invalidate_result_chain` is reachable from the inspector today. (The R08 track read this row as "the core setter also drops results" — true for MCP and undo, not for the panel.)
2. **A GUI tool edit drops S1 and marks nothing in S2.** `properties/mod.rs::commit_tool_draft` calls `session.invalidate_tool` and `mark_edited`; it writes no `stale_since`. Cards stay OK, the viewport keeps drawing, and export takes the `gui.toolpath_rt` fallback in `emitted_toolpaths` — this is the one path the fallback was written for.
3. **The card cannot render staleness.** `toolpath_panel.rs::RuntimeSnapshot` has no stale field; the chip is a match on `ComputeStatus::effective` (`Done → "OK"`); row 3 prints `stats.move_count` whenever `rt.result` is `Some`. The inspector header (`properties/mod.rs`, the `match ComputeStatus::effective(entry.enabled, &entry.status)` under the Generate button) prints "Done" with no qualifier.
4. **The sim reads fresh for a trace of old inputs.** `last_sim_edit_counter` is stamped at drain time. An edit during a running simulation is invisible to `is_stale` afterwards. Conversely any `mark_edited` — including the unconditional no-op push on navigate-away from a toolpath / post / machine panel (`flush_toolpath_snapshot`, `flush_post_snapshot`, `flush_machine_snapshot`, no equality check) — marks the sim stale with nothing changed.
5. **No late-result guard on toolpaths.** `drain_compute_results`' `Ok(computed)` arm sets `Done`, inserts the core result and `rt.result` unconditionally. It neither reads nor clears `stale_since`. The only protection is the resubmit-cancels rule for auto-regen ops (`a_param_edit_mid_generate_regenerates_without_a_pending_flicker`); a MAN op, a locked op, or a job that finishes inside the 500 ms window lands a pre-edit result as current.
6. **The wire publishes a flag the operator cannot see.** `mcp_list_toolpaths` / `mcp_get_toolpath_params` publish `"stale": rt.stale_since.is_some()`; `mcp_set_toolpath_enabled` reports `stale_toolpaths: [index]` on the wire without setting `stale_since` on anything.

## 3. Options

### Option A — derive the display state from the core result cache

The GUI computes a `FreshnessState` per toolpath from `tc.enabled`, `rt.status`, `session.get_result(idx).is_some()` and `rt.result.is_some()`. `stale_since` stops being a truth and becomes only the auto-regen debounce clock. The core must be made to drop the result on EVERY input mutation (the S1 list above), which means the inspector write-back and the setup panel go through core setters.

- Pro: one truth (S1) that CLI, MCP and GUI already share; export and rest generation already read it; the invalidation closure (`invalidate_result_chain`) runs for every route, which closes the GUI-reachable collision class in §2.2 item 1 as a side effect.
- Pro: the card, header and wire read the same function; no new field to keep in sync.
- Con: the core alone cannot tell "never generated" from "had a result, then edited" — both are an absent entry. The GUI supplies that from its retained `rt.result`. Acceptable: the distinction is a display matter.
- Con: the late-result guard needs to know whether the config changed between submit and drain. An absent core entry cannot say that (the submit does not drop it, the drain inserts it). A per-toolpath revision counter in the core is required (see §4).
- Con: a stock-dimension edit today drops nothing in S1 on the GUI route and everything in S2 on the MCP route. Option A forces a decision (open question 1).

### Option B — the core publishes staleness

The core keeps stale results and marks them: `ToolpathComputeResult` gains the revision it was generated from, `get_result` returns only current results, a second accessor returns the retained stale one. The core exposes `ProjectSession::freshness(idx) -> {Current, EditedSince, NoResult}`.

- Pro: the CLI and the core export gate get the full state without a GUI; the GUI fallback in `emitted_toolpaths` disappears.
- Con: every core reader of `results` (rest generation via `prior_stocks`, `DerivedRestRegions` source lookup, load report, simulation assembly, CLI `project` report) must be audited for "current only". The R05 track lists these as separate owners; this is a core refactor, not a UI fix, and P2 is one serial night.
- Con: the core still cannot express `Regenerating` or `WaitingOnUpstream`; the GUI composes anyway.

### Option C — keep the GUI flag and fix the ~20 sites

Set `stale_since` at every gap in §2.3, put it in `RuntimeSnapshot`, render it.

- Pro: smallest diff; F1.11 already does half of it.
- Con: it leaves two truths. S1 stays intact after an inspector edit, so export and rest generation keep reading a result the card now calls STALE. A flag that is set at 30 sites and cleared at 2 will drift again; it has drifted once already (this document).
- Con: no late-result guard is possible from a timestamp alone.

## 4. Recommendation

**Option A, with one core addition: a per-toolpath `revision` counter bumped at the single drop site.** The GUI derives the display state; the core owns result validity; nothing new is persisted.

### 4.1 The state enum

Add to `crates/rs_cam_viz/src/state/runtime.rs` (or `state/toolpath/support.rs`, beside the `ComputeStatus` re-export):

```rust
/// Derived on every read. Never stored, never persisted.
pub enum FreshnessState {
    /// Core holds a result generated from the current inputs.
    Current,
    /// An input changed after the last generation. `rt.result` still holds
    /// the old geometry for drawing; the core holds nothing.
    EditedSince,
    /// The compute lane owns it right now.
    Regenerating,
    /// Blocked on upstream simulated stock (A/M11), not failed.
    WaitingOnUpstream(AwaitingPriorStock),
    /// Generation failed.
    Error(String),
    /// Never generated, or cancelled / forgotten.
    NoResult,
    /// `enabled == false`. Wins over everything.
    Disabled,
}

pub fn freshness(tc: &ToolpathConfig, rt: Option<&ToolpathRuntime>,
                 core_has_result: bool) -> FreshnessState {
    if !tc.enabled { return Disabled; }
    match rt.map(|r| &r.status) {
        Some(Computing) => Regenerating,
        Some(AwaitingPriorStock(b)) => WaitingOnUpstream(b.clone()),
        Some(Error(e)) => Error(e.clone()),
        _ if core_has_result => Current,
        _ if rt.is_some_and(|r| r.result.is_some()) => EditedSince,
        _ => NoResult,
    }
}
```

`core_has_result` is `session.get_result(idx).is_some()`. The seven names are the ones PLAN §2 asked for. `ComputeStatus` stays as the lane's own record; `FreshnessState` is what every surface reads.

### 4.2 The core addition

- `ProjectSession` gains `toolpath_revision: HashMap<usize, u64>` (or a `#[serde(skip)]` field on `ToolpathConfig`; the HashMap keeps the re-keying rules identical to `results`).
- One private function `fn drop_result(&mut self, index)` replaces every `self.results.remove(&index)` in `session/mutation.rs` and bumps the revision. `invalidate_result_chain`, `invalidate_output_dependents`, `invalidate_tool`, `move_toolpath_to_setup`, `replace_toolpath_config`, `apply_toolpath_param_snapshot`, `remove_result` all call it.
- `pub fn toolpath_revision(&self, index) -> u64`.
- Two new core setters so the GUI has no reason to write these directly: `set_setup_face(setup_index, FaceUp)` and `set_setup_rotation(setup_index, ZRotation)`, each dropping every result in that setup (the `MutationKind::SetupChanged` set) and the simulation. `compute_stale_set` and `invalidate_tool` should agree: add the `PlannedTierRegions` door to `compute_stale_set(ToolParamChanged)`, or have `mcp_apply_stale` read the result-set diff instead (see 4.3).

### 4.3 Transition owners

One owner per transition. Nothing else may move the state.

| Transition | Owner | Mechanism |
|---|---|---|
| any → EditedSince | **Core drop site** `ProjectSession::drop_result` | Called by the core setters. This replaces the 27 write sites with one. `open_job_from_path` sets it explicitly for every toolpath (keeps today's load-time regen; see open question 2). |

The MCP layer drops `mcp_apply_stale` and `compute_stale_set`: after a mutation it reports `stale_toolpaths` as the result-set diff the pump computed, so the wire and the GUI cannot disagree.

The `FreshnessGate` component keeps its role for the simulation. Its text changes from "params changed" to "edited since the last simulation" once 4.3's submit-time stamp lands, because "params changed" is then true.

`RuntimeSnapshot` gains one field, `freshness: FreshnessState`, computed in the snapshot loop where `has_result` is computed today. `has_result` can then go.

### 4.5 Export

Remove the `gui.toolpath_rt` fallback in `io/export.rs::emitted_toolpaths`. With 4.3 every route that invalidates also drops the core entry, so the fallback's stated reason (a GUI tool edit) becomes a refusal with a name, not a silent old file. The G-MODEXPORT invariant (the core slot holds the modulated program) is unaffected. `accept_stale` is an explicit flag on the export policy beside `ToolLoadOverrides`, off by default, surfaced in the wizard's checks step and as an MCP parameter.

## 7. Open questions for the human

1. **Stock dimensions.** Should a stock size or material edit make every toolpath `EditedSince`? Heights reference the stock top and `boundary_inherit` uses the stock outline, so geometry can move; the MCP route already marks all toolpaths, the GUI route marks none. Recommendation: yes for dimensions and pins (drop every result in the setup), no for material alone (feeds only; sim stale). Cost: every stock nudge regenerates every 2.5D op after 500 ms.
2. **Regenerate on load.** Today `open_job_from_path` forces `auto_regen = true` and requests regeneration of every op, including 3D MAN ops (the G-REGEN-RACE precondition). Under this model load reads `NoResult`. Keep the load-time request for 2.5D ops only (respect `default_auto_regen`), or keep it for all as today?
3. **Kinematics.** A machine kinematics edit changes timing and modulation, not geometry. Recommendation: sim stale only, toolpaths stay `Current`, and the MCP route gains the missing `invalidate_machine`. Confirm.
4. **Reorder of `Fresh` ops.** Two swapped `StockSource::Fresh` ops keep `Current` (their geometry does not depend on order); only downstream `FromRemainingStock` ops go `EditedSince`. Confirm that a green card after a reorder is acceptable when the exported program order changed.
5. **`accept_stale` wording and persistence.** Per-export flag (like `ToolLoadOverrides`, reset on load) or a project setting? Recommendation: per-export, never persisted.
6. **Dimmed viewport path.** Opacity 0.4 with the same palette, or a dashed grey? Colour overlays (engagement, advance per tooth) are exclusive per surface; a stale path with an engagement palette is a stale palette too.
