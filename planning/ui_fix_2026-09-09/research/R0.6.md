## 1. Question

Before the planner replaces operations, before a tool edit becomes the project
tool, and before a library save overwrites a catalog entry, can the operator
name what is replaced and what is kept? Today the answer is no on all three
surfaces. This document says what the code does, gives options for the five
D5 deliverables, recommends one option each, and scopes the tests and the
structural undo that P5 needs. The planner algorithm is out of scope.

**How ownership is recorded.** `crates/rs_cam_core/src/session/mod.rs:PlannerOrigin`
(l. 675): `plan_id: u64`, `tier: u8`, `tier_count: u8`. Doc: "`None` — the
default, and what every project written before this existed deserializes to —
means 'the operator built this'." It round-trips through both project IO doors
(`session/project_file.rs` l. 464, 710; `crates/rs_cam_viz/src/io/project.rs`
l. 283, 606, 1241) and is pinned by `tests/multitool_plan_roundtrip_o1b.rs`.

**Does a hand edit change ownership? No.** Every write path leaves
`planner_origin` untouched:

| Write path | Symbol | Touches `planner_origin`? |
|---|---|---|
| Inspector edit | `crates/rs_cam_viz/src/ui/properties/mod.rs:write_entry_config_to_session` (l. 3443) | No. Assigns name, enabled, tool_id, model_id, operation, dressups, heights, boundary, boundary_inherit, rest_analysis, coolant, pre/post gcode, stock_source, face_selection, debug_options, feeds_provenance. `state/toolpath/entry.rs` l. 158: "`write_entry_config_to_session` deliberately never writes it back". |
| MCP `set_toolpath_param` | `crates/rs_cam_core/src/session/compute.rs:set_toolpath_param` (l. 278) | No. Writes `tc.operation.*` and `tc.feeds_provenance`. |
| Undo / optimizer | `crates/rs_cam_core/src/session/mutation.rs:apply_toolpath_param_snapshot` (l. 1065) | No. Writes operation, dressups, face_selection. |
| Duplicate | `crates/rs_cam_viz/src/controller/events/toolpath.rs:handle_duplicate_toolpath` (l. 214) | Sets `planner_origin: None`. The copy escapes ownership. |

Consequence: a tier the operator re-dialled by hand is still deleted on the
next Apply, with no warning before and a 4 s count after.

**No GUI surface reads `planner_origin`.** In `crates/rs_cam_viz/src` the
only readers are project IO, the entry copy (`properties/mod.rs` l. 3434),
the duplicate handler (writes `None`), and MCP `list_toolpaths` /
`plan_multitool_finishing` (`"tier"`). The toolpath card
(`crates/rs_cam_viz/src/ui/toolpath_panel.rs` l. 396–470) draws a status chip,
`MAN`, a trace badge and, for Rest ops only, `draw_rest_badge` (l. 713). No
planner badge exists.

**Existing controller tests** (`crates/rs_cam_viz/src/controller/tests.rs`
l. 3348–3560): `planner_controller`, `tick_ball_tools`, `project_fingerprint`
(name, tool_id, enabled, `(plan_id, tier)`),
`opening_the_planner_emits_nothing_and_pre_ticks_nothing`,
`vetoing_the_planner_leaves_the_project_alone_and_drops_the_overlay`,
`applying_without_a_preview_plans_nothing`,
`a_one_tool_ladder_never_reaches_the_worker`. None applies a plan. A ready
preview lands only through the compute drain
(`controller/events/compute.rs` l. 1438); UNVERIFIED whether a test can build
a `MultitoolPreview` without a tier-map walk.

### 2.2 Boundary Source combo

`crates/rs_cam_viz/src/ui/properties/mod.rs` l. 4256–4335, inside the
Machining Boundary section of the operation inspector:

| Arm | Condition | Sets |
|---|---|---|
| `Stock` | always | `BoundarySource::Stock` |
| `Model Silhouette` | always | `BoundarySource::ModelSilhouette` |
| `Face Selection` | always | `BoundarySource::FaceSelection` |
| `Rest Regions` | enabled when `boundary_source_candidates` is non-empty | `DerivedRestRegions { source_toolpath_id: first candidate }` |
| `Imported Geometry` | **no arm** | — |
| `Planned Tier Regions` | **no arm** | — |

The combo's closed text is `entry.boundary.source.label()`, so a planner tier
reads `"Planned Tier Regions"` (`crates/rs_cam_core/src/compute/config.rs`
l. 1775) while it holds that variant. One click on any arm replaces it and the
variant is gone. It cannot be restored because the variant is a recipe with
seven fields (`config.rs` l. 1736): `tool_ids` (the full ladder), `tier`,
`cell_mm`, `tolerance_mm`, `margin_mm`, `treatment`, `islands`. `config.rs`
l. 1763 says why there is no arm: "`PlannedTierRegions` a whole ladder + tier,
so none of those four are listed here."

Where the recipe still exists after the click:

1. Any sibling tier of the same plan in the same setup. `multitool.rs:tier_boundary`
   (l. 946) builds every tier's variant from the same `spec` and `ordered_ids`;
   only `tier` differs. The op's own `planner_origin.tier` supplies that.
2. The dialog state, `crates/rs_cam_viz/src/state/multitool_planner.rs:MultitoolPlannerState::to_spec`
   (l. 318), in memory only, and only if the dialog was opened this session.
3. Nowhere, when neither exists.

Tier 0 carries the type default (boundary disabled) unless
`coarse_skips_fine_islands` is on (`tier_boundary` l. 947). A restore for
tier 0 must reproduce that rule, not copy a sibling's `enabled: true`.

### 2.3 Tool draft lifecycle

State: `crates/rs_cam_viz/src/state/history.rs:UndoHistory::tool_draft:
Option<(ToolId, ToolConfig)>` (l. 61). One draft at a time.

| Moment | Where | What happens |
|---|---|---|
| Enter a tool | `crates/rs_cam_viz/src/ui/properties/mod.rs` l. 303 | If the draft id differs from the selected tool, `tool_draft = Some((id, committed.clone()))`. |
| Every frame | `properties/mod.rs` l. 310–313 | `modified = draft != committed`; `tool::draw(ui, draft, modified)` edits the draft in place. |
| Affordance | `crates/rs_cam_viz/src/ui/properties/tool.rs:draw` (l. 22) | Modified: `"● modified"` + `Apply` (hover "Commit these edits to the project tool.") + `Revert` (hover "Discard these edits and restore the saved values."). Else `"✓ saved"`. Code comment l. 28: "Edits are pending until Apply (or until the user navigates away, which auto-commits)". |
| Apply | `properties/mod.rs:commit_tool_draft` (l. 106) | No-op if equal. Else push `UndoAction::ToolChange { tool_id, old, new }`, write the session tool, `session.invalidate_tool(id)`, `mark_edited()`. |
| Revert | `properties/mod.rs` l. 321 | `tool_draft = Some((id, committed))`. |
| Navigate away | `properties/mod.rs:flush_tool_draft` (l. 90), called first in `properties::draw` (l. 212) | If `selection` is not `Tool(id)`: `commit_tool_draft`. **Auto-commit.** Doc: "the spec's accepted fallback so a stray click elsewhere can't silently drop edits." |
| Tool deleted while selected | `properties/mod.rs` l. 328 | Draft dropped. |
| Project save | `crates/rs_cam_viz/src/controller/io.rs:save_job_to_path` (l. 152) | `session.save(path)`. The draft is not in the session, so a modified draft that has not been applied is **not in the saved file** while the panel shows the edited values. |
| Export | `crates/rs_cam_viz/src/io/export.rs:emitted_toolpaths` (l. 118) | Reads the session. An unapplied draft is not exported. |
| Undo of a commit | `crates/rs_cam_viz/src/controller/events/undo.rs` l. 21 | `*tool = old; self.invalidate_simulation();`. It does not call `session.invalidate_tool`, so cached results of dependent toolpaths are not dropped by Undo the way Apply drops them. Observed in code; consequence not measured. |

Summary: the affordance says "pending until Apply". The behaviour is "pending
until Apply or until you click anything else". `Revert` is only available
while the selection has not moved.

## 4. Recommendation

### 4.1 Before-Apply change summary — option C, with B as the shipped floor

Build a pure `PlanChangeSummary` in `state/multitool_planner.rs` from
`(&ProjectSession, setup_index, &MultitoolPreview, &[TierStrategy])`:

| Field | Source | Shown as |
|---|---|---|
| `add: Vec<String>` | preview `tool_ids` / `cusp_radii_mm` and the dialog's strategies, through a shared `tier_op_name(tier, strategy, cusp)` extracted from `multitool.rs` l. 385 so the summary and the emission cannot drift | `Add: Finish tier 0 (R2.0), Finish tier 1 iso (R1.0)` |
| `replace: Vec<ReplacedOp { id, name, plan_id, tier, tier_count, edited }>` | every op in `setups[setup_index]` with `planner_origin.is_some()` | `Replace: Finish tier 1 (R1.0) — plan #3, tier 2 of 2, edited since planned` |
| `manual_edits: Tracked(n) \| NotTracked` | `edited` needs the stamp below; without it the line reads `Manual edits affected: not tracked — every replaced operation is removed with its edits` | one line |
| `kept: usize` | ops in the setup with `planner_origin.is_none()` | `Hand-authored operations kept: 2 (setup "Top"); other setups untouched` |
| `dependents: Vec<String>` | ops anywhere whose `DerivedRestRegions.source_toolpath_id` is in `replace` (the same set `mark_derived_rest_dependents_stale` marks) | `Will need regeneration: …` |

Draw it under a `CHANGE SUMMARY` heading between `draw_status` and
`draw_actions`, only when a preview is ready, so it sits directly above the
Apply button it describes. Name the setup by its `name`, not its index; the
header's 0-based `#{setup_index}` and the overlay refusal's 1-based number
disagree today and D1 owns that header.

The stamp: add `emitted_fingerprint: Option<u64>` to `PlannerOrigin`
(`#[serde(default)]`, so old files read `None` = not tracked), computed in
`plan_multitool_finishing` over `(name, tool_id, operation, dressups, heights,
boundary, stock_source, enabled)` after `suggest_feeds_for` has run. The
summary recomputes the hash on the current config and compares. This is a
provenance field, not an algorithm change, but it is a core serialization
change, so it is the one part of D5 that needs the human's go-ahead (§7 Q1).
If refused, ship option B's `not tracked` line; the sentence is still true.

Also return the same names on the MCP reply: `mcp_plan_multitool_finishing`
should resolve `replaced` to names **before** `apply_multitool_plan` runs (the
configs are gone after), and the tool description should say the call replaces
without preview.

### 4.2 Badge — option A

Rule: `tc.planner_origin.is_some()`. Text `PLAN`, `RichText::small().strong()`,
colour `theme::TEXT_MUTED`, drawn in card row 2 immediately after the tool
summary and before `draw_rest_badge`, in a new `draw_planner_badge(ui, tc)`
that is a pure function of the config. Hover:

```
Planner-owned — plan #3, tier 2 of 2.
Applying the planner to this setup again replaces this operation,
including any edits you made here. Duplicate it to keep a hand-owned copy.
```

With the stamp, append `Edited since planned.` when the hash differs and use
`theme::WARNING` for the badge. The operation inspector gets the same sentence
as one small line under its heading. A duplicate shows no badge, which is
correct: `handle_duplicate_toolpath` sets `planner_origin: None`.

### 4.3 Tool draft commit boundary — option D, explicit Apply with parked drafts

Decision: **Apply is the only commit.** Navigating away parks the draft; it
neither commits nor discards.

| Consequence | Handling |
|---|---|
| `tool_draft` holds one tool | Becomes `tool_drafts: HashMap<ToolId, ToolConfig>`; `flush_tool_draft` is deleted; the re-init rule at `properties/mod.rs` l. 303 becomes `entry(id).or_insert(committed)`. |
| Operator forgets a parked draft | Drawer card (`toolpath_panel.rs` l. 174–210, the tool list) shows `● unapplied` in `theme::WARNING`; the inspector strip reads `● modified — not applied. Generate, export and save use the applied values.` |
| Committed tool changes underneath (undo, MCP `set_tool_param`) | The draft stays; `modified` is recomputed each frame against the new committed value, as today. |
| Tool deleted | Draft removed (today's l. 328 rule). |
| Project save / export / generate | Read the session; unchanged. The badge makes the divergence visible where today it is silent. |
| Project close or open with parked drafts | Route through the existing unsaved-changes prompt: `"{n} tool edit(s) not applied"`. |
| Wording | `Apply` hover: `"Make these values the project tool. Dependent toolpaths become stale."` `Revert` hover: `"Discard these edits."` Status when clean: `"✓ applied"` (today `✓ saved`, which reads as "saved to disk"). |

Fallback if P5 judges the map too large: option A, one string. The label
becomes `● modified — applies when you leave this tool or press Apply now`,
and `Revert` keeps its text. That makes the affordance true at zero cost, but
leaves the accidental-commit path.

### 4.4 Library save confirmation — option B

Rules:

1. `Save` reads the committed tool by id, never the draft. Disabled while
   `modified`, hover `"Apply your edits first — the library receives the
   project tool as committed."`
2. Add `pub fn find_signature_match_in(dir, name, &tool) -> Result<Option<(usize, ToolConfig)>>`
   beside `add_or_replace_to`, using `dedupe_key`. It reads only.
3. On click with `None`: write, status `"Saved '{name}' to {catalog}"`.
4. On click with `Some((_, existing))`: no write. The row shows

```
Replace 'Ball 6 mm long reach' in endmills?
Same geometry: BallNose Ø6.000, 2 flutes, cutting length 20.000.
Name differs ('Ball 6 mm long reach' → 'Ball 6'); holder and stickout will be overwritten.
[Replace]  [Keep both]  [Cancel]
```

   `Replace` calls `add_or_replace_tool`; `Keep both` calls `append_tool`
   (explicit, so TOO-004's silent pile-up does not return); `Cancel` clears
   the flag. Pattern: `confirm_delete_tool` in `tool_library_modal.rs` l. 384.
5. Status after: `"Replaced 'old' with 'new' in {catalog}"` or
   `"Saved '{name}' beside 'existing' in {catalog}"`.

"Holder and stickout will be overwritten" is the true list of non-key fields
that differ; compute it from the two configs, do not hard-code it.

### 4.5 Structural undo — option B, scope only (implementation is P5 / F3.3)

Minimal variants (box the config payloads; `large_enum_variant` is denied):

| Variant | Fields | Undo | Redo |
|---|---|---|---|
| `AddToolpath` | `setup_index, position, config: Box<ToolpathConfig>` | remove by id | restore at position with the same id |
| `RemoveToolpath` | `setup_index, position, config: Box<ToolpathConfig>` | restore at position with the same id | remove by id |
| `ReorderToolpath` | `setup_index, from, to` (positions in the setup) | reorder `to → from` | reorder `from → to` |
| `MoveToolpathToSetup` | `tp_id, from_setup, from_position, to_setup` | move back and reinsert at `from_position` | move again (append, as today) |
| `SetToolpathEnabled` | `tp_id, was_enabled` | set `was_enabled` | set `!was_enabled` |
| `PlannerApply` | `setup_index, removed: Vec<(position, Box<ToolpathConfig>)>, emitted: Vec<ToolpathId>` | remove `emitted`, restore `removed` in position order | remove the restored ids, re-add the emitted configs — which means `emitted` must also carry its configs: `emitted: Vec<(position, Box<ToolpathConfig>)>` |
| `ToolpathConfigChange` | `tp_id, old: Box<ToolpathConfig>, new: Box<ToolpathConfig>` | replaces `ToolpathParamChange` for the fields it misses (name, heights, boundary, stock_source, tool_id, …) | — |

What the core needs: one new mutation, `restore_toolpath(setup_index,
position, config) -> Result<usize>`, that keeps `config.id`, inserts at
`position` in `setup.toolpath_indices`, shifts higher indices, re-keys
`results`, runs `invalidate_output_dependents`, and never lowers
`next_toolpath_id`. Ids must survive because `DerivedRestRegions.source_toolpath_id`,
`toolpath_rt`, `Selection::Toolpath`, `isolate_toolpath` and the planner's
`replaced` list all key on them.

What the GUI needs on every structural undo or redo: the same teardown and
setup `apply_multitool_plan` performs today — remove or insert the
`ToolpathRuntime` row, `mark_derived_rest_dependents_stale`, clear selection
and isolation for a removed id, `pending_upload = true`, `mark_edited()`, and
`invalidate_simulation()` (r05 §6 shows `prior_stocks` survives every
structural edit today; an undo must not leave a consumer reading a snapshot
of a chain that no longer exists).

For F3.3, give `UndoAction` a `describe() -> UndoDescription { kind: &'static
str, subjects: Vec<String> }` so the MCP reply and an `Edit ▸ Undo delete
'Finish tier 1 (R1.0)'` menu label read the same text.
