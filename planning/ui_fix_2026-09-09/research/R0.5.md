## 1. Question

An operator reads a feeds value on the inspector card, on the Feeds &
Speeds modal, and after a simulation. Which of four things is that number?

| Role | Meaning |
|---|---|
| configured | the value stored on the operation, which Generate reads |
| proposed | the value an Apply would write now, given tool, material and machine |
| inherited default | a value the operation does not store and follows from elsewhere |
| emitted | the value the machine receives after modulation and kinematics |

Today the card prints a proposed value under a label that reads as
configured, and the proposed value it prints is not the value Apply writes.
This document fixes the four roles, lists what every Apply route writes,
says which provenance stamp each route records, and maps the D4 wireframe
onto the widgets that exist.

Notes on the table:

(a) **R8 writes plunge, not only feed and RPM.** `with_explored_speeds`
replaces `feed_rate_mm_min`, `rpm` and drops `chipload_bounds`
(`suggest.rs:1177-1189`). `apply_feeds_subset` then writes
`scratch.set_plunge_rate(round(result.plunge_rate_mm_min, 1.0))`
(`:872`) and copies `scratch.plunge_rate()` back under `Speeds`
(`:930-936`). So the stored plunge becomes the **calculator's** plunge,
clamped to the explored feed. The button hover says "plunge is pulled down
to the new feed if it would exceed it" (`feeds_modal.rs:2201-2206`). That
sentence describes a clamp on the stored plunge. The code overwrites it.
Not tested live.

(b) **The R04 track's R15 claim is wrong at HEAD for the five named
params.** `r04_source_track.md` §2.2 says `set_toolpath_param` writes no
provenance, based on a grep of `mcp.rs` alone. The stamp lives in the
core setter and has since commit `b255119c` (2026-06-08, "per-field
ValueProvenance data model (W2.1)"). PLAN §2 R0.5 repeats the wrong
claim ("MCP `set_toolpath_param` never restamps"). The gap that does
exist is the wildcard arm: an agent that sets `z_step` on a Waterline
changes the value `depth_per_pass()` reads while the `depth_per_pass`
stamp keeps its old label.

(c) **Two "Apply" sentries exist and neither reaches R3/R4.**
`crates/rs_cam_viz/tests/apply_contract_a3.rs` pins R7, R8, R9, R10, R14
(`no_apply_path_writes_the_raw_preview_value`,
`surviving_apply_paths_produce_the_funnelled_doc_exactly`,
`agent_apply_honours_its_declared_scope`, …) and asserts by source scan
that no `ApplyFeedsField` event, `FeedsField` enum or `small_button("Apply")`
in `compare.rs` grew back. It does not read `value_row.rs` or `dv_pill`.
F1.2 owns the pill sentry (`pill_writes_clamped_value_g_pillclamp.rs`).

(d) **Every GUI route folds into one undo entry per selection.** The
properties panel snapshots the selected toolpath once
(`properties/mod.rs:406-415`) and pushes it only when the selection moves
away (`flush_toolpath_snapshot`, `:180-199`). Controller routes R7–R15
push nothing. Not changed by D4; recorded because the D4 acceptance
("predict the changed fields") has no undo behind it.

### 2.2 How provenance is stored and where it is rendered

Storage. `ToolpathConfig::feeds_provenance: FeedsProvenance`
(`session/mod.rs:723`), six `Option<ValueProvenance>` slots: `feed_rate`,
`plunge_rate`, `spindle_rpm`, `stepover`, `depth_per_pass`,
`scallop_height` (`feeds/provenance.rs:113-126`). `None` means "never
explicitly derived or edited — the operation's struct default still
stands" (module doc). `ValueProvenance { source: ProvenanceSource,
reference: Option<String> }`; `reference` is the observation id for
`VendorLut` and `None` otherwise. Persisted in the project file with
`skip_serializing_if = "feeds_provenance_is_empty"`
(`session/project_file.rs:453-471`).

The kinds (`ProvenanceSource`, `provenance.rs:30-43`): `VendorLut`,
`Formula`, `EdgeRadiusFloor`, `Manual`, `Optimizer`, `AutoCorrect`. There
is no kind for "clamped", "explored", "planner" or "scaled by D^0.61".

Writers, in one place each:

| Writer | Where | Stamps |
|---|---|---|
| `FeedsProvenance::apply_suggested_subset` | `apply_feeds_subset:947` | V/F/E per written field |
| `FeedsProvenance::detect_manual_edits` | GUI flush, `properties/mod.rs:3451-3452` | `Manual` where value moved and stamp did not |
| `FeedsProvenance::stamped_optimizer` | `events/mod.rs:596, 733, 1224` | `Optimizer` where value differs |
| `FeedsProvenance::set(field, manual())` | core `set_toolpath_param`, five arms | `Manual` |
| `FeedsProvenance::set(field, auto_correct())` | `validate.rs:apply_stale_default_to_op` | `AutoCorrect` (two rules) |

Display vocabulary. `ui/components/provenance.rs:ProvKind` mirrors the six
kinds 1:1 plus display-only `Inherited`. One glyph and one colour per kind
(`ProvKind::glyph`, `ProvKind::color`): `▣ vendor LUT` green, `▲ formula
fallback` and `⌊ edge-radius floor` both amber, `✎ manual` muted, `◆
sim-optimized` blue, `⟲ auto-corrected` info, `〈〉 inherited` faint.
`ProvenanceBadge` is the single renderer; hover `Source: <label> (<ref>)`.

Where the stored stamp is rendered today:

| Optimize modal | any | No | — |

| CLI | any | Not checked in this pass (UNVERIFIED) | — |

The `⚡` pill beside a Feed row is coloured by the **live recommendation's**
chipload source (`prov_from_chipload(&result.chipload_source)`,
`properties/mod.rs:2003`), while the badge beside it is coloured by the
**stored** stamp. Two colours on one row describe two different values,
and the vocabulary does not say which is which.

Name collision to know about: `kinematic_utilization::FeedsProvenance`
(`Planned` / `Emitted`, the post-simulation qualifier, `app/mcp.rs:1478`)
and `feeds::FeedsProvenance` (the per-field stamps) share a name and are
unrelated types. The emitted role in §4 uses the first; the stamp column
uses the second.

### 2.3 What the card prints versus what is stored

Fixture: the R03 demo pocket (`R03/REPORT.md` UX-R03-005), fresh Pocket op
on a Ø6 two-flute end mill, `Generic Wood Router`.

| Row label on the card | Expression printed | Value | Stored value on the op | Where the stored value comes from |
|---|---|---|---|---|
| `Commanded advance/tooth:` | `result.chip_load_mm` (`properties/mod.rs:2047-2048`) | 0.0435 mm/tooth | 750 ÷ (15000 × 2) = 0.025 | feed written by the add-time funnel (R16/R16b) after the rubbing floor (`feeds/mod.rs:RUBBING_FLOOR_MM_TOOTH = 0.025`, `:858`) |
| `DOC:` | `result.axial_depth_mm` (`:2105-2106`) | 4.20 mm | 1.2 | `clamp_dpp_to_rigidity` inside the add-time funnel |
| `WOC:` | `result.radial_width_mm` (`:2110-2111`) | 2.10 mm | 2.1 | agree on this fixture |

Trace of the two disagreeing rows:

1. `result` is `entry.feeds_result`, filled by
   `feeds::suggest::feeds_result_for_operation` at `properties/mod.rs:1647`
   (Feeds tab) and `:4046` (Geometry tab). That function is
   `validate_tool_for_operation` then `feeds::calculate` (`suggest.rs:771-795`).
   It never calls `enforce_invariants` (`suggest.rs:1897`, private).
2. Pocket is in the explicit no-hint arm of `OperationConfig::feeds_hints`
   (`compute/catalog.rs:2503-2519`), so the calculator never sees the stored
   1.2 and takes the operation default profile: Pocket/Roughing
   `ap_factor 0.70`, `ae_factor 0.35` (`feeds/mod.rs:2035-2036`).
   4.2 = 0.70 × 6.0. 2.1 = 0.35 × 6.0.
3. `calculate` returns `chip_load_mm: chip_load` (`feeds/mod.rs:1989`), the
   same value as `derates.target_chip_load_mm` (`:1973`): the LUT midpoint
   or formula value **before** any derate. The advance per tooth at the
   recommended feed is `derates.effective_chip_load_mm()` =
   `target × combined_factor()` (`:625-626`). The card's hover text says
   "feed ÷ (RPM × flutes) at the recommended feed" (`properties/mod.rs:2049-2053`).
   The printed number is not that quantity. The label constant
   `COMMANDED_ADVANCE_PER_TOOTH` is defined as `feed / (rpm · flutes)`
   (`feeds/quantities.rs:33, 52-54`).
4. The rigidity cap is `clamp_dpp_to_rigidity` (`suggest.rs:2110-2136`):
   `cap = doc_roughing_factor × tool.diameter`, roughing role only. R04 §3
   reads the factor as 0.20 on the `Generic Wood Router` preset
   (`machine.rs:166`; not re-read in this pass). 0.20 × 6.0 = 1.2.
5. `apply_cut_geometry_to_op` writes 1.2, not 4.2: `apply_feeds_subset`
   puts 4.2 on the scratch (`:873`), `enforce_invariants` caps it, and
   only the scratch value copies back (`:938-940`). Pinned by
   `apply_contract_a3::panel_cut_geometry_apply_goes_through_the_invariant_funnel`
   on the Ø6.35 fixture (1.27 mm = 0.20 × 6.35).
6. The Geometry-tab `Depth/Pass:` pill (R4) writes 4.2: `dpp_sugg =
   feeds_result.map(|r| (r.axial_depth_mm, ..))` (`boundary_2d.rs:69`),
   `ValueRow::show` writes `round_suggestion_value(4.2, 0.001)`
   (`value_row.rs:127-135`). The pill hover reads "Suggest Depth/Pass =
   4.200 mm (source: …). Click to overwrite this field only."
   (`value_row.rs:112-118`). After the flush the row's stamp is `✎ manual`.
7. The pill's near-match test compares the **configured** value against
   the **raw** recommendation (`value_row.rs:104-105`, 1 % band). On this
   fixture 1.2 versus 4.2 keeps the pill enabled, although the funnel
   would write 1.2, a no-op. Any F1.2 fix must compare against the
   as-applied value or the pill stays lit on a no-op.

Ratio on this fixture: 3.5× between the printed and the applied DOC.

The modal repeats the two mislabels. Its Recommendation card prints
`explain.recommended.axial_depth_mm` in a `DOC` row and
`explain.recommended.chip_load_mm` in a `Commanded advance/tooth` row
(`feeds_modal.rs:565-580`), beside a **Current** column that is honest:
`current.depth_per_pass` and `CurrentValues::chipload_mm()` =
`feed / (rpm × flutes)` (`feeds_modal.rs:400-409`). The clamp is visible
only in the modal's "Why these values?" section (`feeds_modal.rs:1159`;
`SuggestRationale::from_warnings`, `:500`) and in
MCP `get_suggest_rationale`. The OPERATING POINT card on the inspector
prints the gate's real commanded figure,
`explain.commanded.feed_per_tooth_mm` (`draw_advance_per_tooth_card`,
`properties/mod.rs:1817-1860`), under the same
`COMMANDED_ADVANCE_PER_TOOTH` label. One tab, one label, two quantities.

## 4. Recommendation

### 4.1 Role definitions

| Role | Definition | Data source | Owner of the write |
|---|---|---|---|
| configured | The value Generate reads for this operation now | `tc.operation.{feed_rate,plunge_rate,spindle_rpm,stepover,depth_per_pass,scallop_height}()`; stamp `tc.feeds_provenance.<field>` | every route in §2.1 |
| proposed | The value the named Apply route would write now, after `enforce_invariants` | dry run of `apply_feeds_subset` on a clone, per route scope | none; read-only |
| inherited default | A value the operation does not own: RPM with `spindle_rpm == None` (project default from post config), or any field whose stamp is `None` and whose value equals the operation's struct default | `project_default_rpm`; `OperationConfig::new_default(op_type)` | the project, or nobody |
| emitted | What the machine receives after modulation and kinematics for the last simulation | `ToolpathLoadVerdict.feed_explanation` (`commanded`, `gate.value_mm`), `modulation_summary`; `kinematic_utilization::FeedsProvenance::{Planned,Emitted}` | the simulation |

The raw calculator value (`FeedsResult` before invariants) is **not a
role**. It is evidence for the proposal and lives in the rationale
("DPP 4.20 capped to rigidity factor 1.20") and in the vendor drawer.
