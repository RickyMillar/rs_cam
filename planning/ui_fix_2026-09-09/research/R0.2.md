# R0.2 — 2.5D ramp containment

Research worker R0.2, 2026-09-09. Document only. No source, test or config
file changed. No cargo command ran. Every code claim below names the file and
the symbol that was read on the `isoclip-rapid` checkout; `git diff` on
`dressup.rs` was empty at read time, so the working copy is HEAD for that
file. Line numbers are omitted on purpose; locate the symbol.

## 1. Question

How should a ramp entry behave when its straight leg does not fit inside the
operation's region?

The finding is UX-R03-001 (`planning/ui_review_2026-09-09/results/R03/REPORT.md`).
On `fixtures/demo_pocket.svg` with default dressups the first entry of the
pocket runs 19 mm along the ring tangent, leaves the pocket, and cuts a trench
in the stock outside the wall. Every operator surface reads OK. The ledger
entry is `planning/entry_moves_2026-09-03/FINDINGS.md` §Follow-ons: "2.5D ramp
containment: a 19 mm leg can leave a small pocket and side-cut a wall.
Different geometry class (2D containment), not measured here."

## 2. What the code does today

### 2.1 The emitter and its exact geometry

`crates/rs_cam_core/src/dressup.rs`:

| Symbol | What it does |
|---|---|
| `apply_entry_with_provenance` | Walks the toolpath. For each move `m` where `is_plunge(prev, m)` holds, it calls `find_next_xy_direction` and then `emit_ramp` (or `emit_helix`). The 1→K expansion is recorded as a `SpanKind::Entry` span. |
| `is_plunge` | `MoveType::Linear`, `dz < -0.1`, XY distance `< XY_STATIONARY_EPS_MM`. |
| `find_next_xy_direction` | The unit vector from the plunge target to the FIRST later move whose XY distance from the target exceeds 0.1 mm. Fallback `(1.0, 0.0)`. It reads raw move targets; it knows nothing about the region. |
| `ENTRY_CLEARANCE` | `2.0` mm. The ramp only covers the last 2 mm of the descent. |
| `emit_ramp` | Rapid to `stock_top + 2` (air), feed-plunge to `end.z + 2`, then two straight legs. |

The leg formula, quoted from `emit_ramp`:

```rust
let ramp_dz = (ramp_start_z - end.z).abs().max(0.1);   // = ENTRY_CLEARANCE = 2.0
let max_angle_rad = max_angle_deg.to_radians();
let ramp_xy_len = ramp_dz / max_angle_rad.tan();       // 38.16 mm at 3°
let half_len = ramp_xy_len / 2.0;                       // 19.08 mm
let planned = [
    P3::new(start.x, start.y, ramp_start_z),
    P3::new(start.x + dir.0 * half_len, start.y + dir.1 * half_len, mid_z),
    P3::new(start.x, start.y, end.z),
];
```

Two corrections to the wording in `PLAN.md` §2 and the R03 report:

- The leg length is `ENTRY_CLEARANCE ÷ tan(angle) ÷ 2`, not "depth-per-step ÷
  tan(angle)". At 3° it is 19.08 mm for every depth per pass. The R03 DPP of
  1.2 mm plays no part.
- The leg is not "unconstrained in XY" by accident. `emit_ramp` receives only
  `start`, `end`, `dir`, the angle, the feed and `EntrySafety`. It has no
  region, no polygon and no tool radius. It cannot constrain the leg.

The NC file confirms the arithmetic
(`planning/ui_review_2026-09-09/results/R03/scratch/REVIEW_ONLY_NOT_FOR_MACHINING_f1_pocket_profile.nc`,
lines 9–13):

```
G1 X22.485 Y18.030 Z1.000 F3000        ; feed-plunge to end.z + 2
G1 X3.622 Y20.909 Z0.000               ; leg 1: 19.08 mm along dir, drops 1 mm
G1 X22.485 Y18.030 Z-1.000 F1650       ; leg 2: back to the entry column, drops 1 mm
G2 X18.000 Y23.076 Z-1.000 I0.528 J4.985   ; first cut move: the ring's corner arc
```

`dir` here is (−0.989, 0.151): the tangent of the ring's first corner arc,
which heads toward the west wall. The wall is at X = 15 (report), the ring is
at X = 18 (wall + tool radius 3), the entry column is at X = 22.485. The leg
ends at X = 3.622, so the tool centre is 11.4 mm outside the wall and the tool
edge is 14.4 mm outside it. Leg 2 is the one that cuts: it descends from
Z 0 (stock top) to Z −1 while it returns. The third entry in the same file
does the same toward the south wall: `(28.623, 30.249) → (36.905, 13.058)`
with the wall at Y = 15.

### 2.3 What G-RAMPTERRAIN does and why prism ops were exempted

`EntrySurfaceProbe` (`dressup.rs`) carries mesh, spatial index, cutter,
`stock_to_leave`, `off_mesh`, `rest_stock`. `emit_ramp` samples the two legs
every `ENTRY_CLIP_SPACING_MM` (0.5 mm) in `clip_polyline_to_floor` and lifts
each sample to `max(planned z, drop-cutter CL + stock_to_leave)`. That is a
**Z** clip. It never moves a sample in XY.

The probe is issued only where `OperationConfig::entry_probe_leave` returns
`Some` (`catalog.rs`). Its doc states the exemption:

> `None` marks a prism operation: its passes legitimately descend BELOW the
> model surface (a pocket cut into a block), so a mesh-surface floor would
> silently destroy its ramp entries. These keep the audited 2D blind-leg
> behaviour (A0 finding 4).

`FINDINGS.md` §A0 finding 4 is the reason: "For a prismatic pocket the ramp
legs cut the material between passes — that is the purpose of a ramp." That
finding is about Z. It assumed the leg stays inside the pocket. Nothing
checked that assumption. The `else` branch in `emit_ramp` is labelled "Legacy
blind legs — honest only with no mesh surface to probe"; it is the branch every
prism op takes.

The G-ISOCLIPENTRY branch at the top of `emit_ramp` (lap ladder via
`pencil::plan_entry_ramp`) runs only when `probe.rest_stock` is `Some`. Prism
ops have no probe, so it never runs for them.

## 3. Options

Notation: `E` is the entry column (the plunge target). `L = 2.0 / tan(angle)`
is the total ramp XY length (38.16 mm at 3°). `r` is the tool radius. `C` is
the polyline of the cut moves that follow the plunge at the same Z level, up
to the next rapid or the next plunge.

### (a) Fold the leg along the first contour

Geometry. Walk forward along `C` from `E` for `L/2`, then walk back along the
same path to `E`. Interpolate Z linearly by cumulative arc length:
`z(s) = end.z + 2.0 − 2.0 · s / L`, `s ∈ [0, L]`. Emit a point at every vertex
of `C` crossed and at the turn-around point, all tagged `MoveIntent::EntryRamp`.
If `C` is a closed ring shorter than `L/2` (perimeter `P < L/2`), keep walking
laps. If `C` is open and shorter than `L/2`, reverse at its far end (bounce)
and continue. The slope along the path is exactly `tan(angle)` everywhere, so
the angle dial is honoured; a vertex chord is shorter than the arc it
replaces, so the slope on a chord is never steeper than the planned slope.

Containment argument. Every point of `C` is a tool-centre point of a cut move
the operation itself emits at that level. The generator already placed those
points inside the region offset by `r` (pocket ring: inset by `r`; profile
inside: inset; profile outside: outset, in the waste; zigzag: scan lines
inside the wall inset; face: passes over the stock face). So the fold is
contained wherever the operation's own cut is contained. No region polygon,
no offset call and no tool radius are needed at emit time. The mechanism
works for every prism op the same way.

Where it goes wrong. `C` shorter than a few millimetres and open (a stub scan
line, a two-point polyline): the bounce produces a sawtooth of 180° reversals,
each a full stop for the controller. Degrade rule needed (see §4). A ring
whose first moves are the far side of an island: still on `C`, still
contained; only the pre-cut location changes.

Cost. The walk is a forward scan over `C` bounded by `L/2` of path length
(19 mm), per entry. Zero plumbing: `apply_entry_with_provenance` already holds
`toolpath.moves`. Arc moves in `C` (none at entry time on the shipped
generators; arc fitting runs after entry) would be linearised with
`linearize_arc`. Goldens move: every fingerprint that carries a ramp entry on a
prism op re-baselines (`tests/transform_provenance_fingerprints.rs` and the
param-sweep fingerprints are the known carriers; G-RAMPTERRAIN forced the same
kind of re-baseline, `FINDINGS.md` §"The golden re-baseline the fix forced").

Per-op applicability: Pocket, Profile (both sides), Face, Zigzag, Rest, Inlay,
Chamfer: yes. VCarve: `C` is the centreline the V-bit follows at varying
depth; the fold stays on the centreline, so it is contained in XY, but the
depth interpolation must use `C`'s own Z profile as the floor
(`max(planned z, C's z at s)`) or the fold would dive under a shallow carve.
That is a small addition and it is what `clip_polyline_to_floor` already does
for a probe.

### (b) Zig-zag within an inscribed segment

Geometry. Cast the ray `E + t·dir` and `E − t·dir` against the region inset by
`r` (or against the raw region with a disc test). Get the free run `a+`
forward and `a−` backward. Pick the longer side. With `n` legs (even, so the
path ends at `E`), each of length `L/n`, choose the smallest even `n` with
`L/n ≤ a`. Emit `n` legs alternating out and back along `dir`.

Where it goes wrong. Small `a` gives a large `n` and a sawtooth with 180°
reversals at every leg (`a` = 4 mm → 10 legs of 3.8 mm). `dir` from
`find_next_xy_direction` is the first chord, which on a rounded corner points
partly into the wall, so `a` is often short even in a large pocket (the R03
entry has `a+ ≈ 7.5 − r = 4.5` mm along its own `dir`). Needs a per-op region
definition (Face: stock rectangle plus `stock_offset`; Profile outside: the
complement of the outset polygon) and plumbing of polygons plus tool radius
through `apply_dressups` on both call sites. A collapsed or failed inset
(`OffsetFailure`) needs its own fallback.

Cost. Moderate plumbing, one segment-vs-ring intersection per entry, a new
per-op region table that must be kept in step with the generators.

### (c) Degrade to helix when the inscribed width allows, else plunge

Geometry. A helix of radius `h` centred on `E` needs boundary clearance
`≥ h + r` at `E`. On every ring-based op the entry column `E` is ON the inset
ring, so its clearance is exactly `r`. A helix of any `h > 0` centred on `E`
cuts into the wall by `h`. The helix therefore needs a relocated centre at
least `h` inside the ring plus a lateral connecting move at full depth back to
`E`. That changes the entry XY, adds a full-width slot at full DOC (the same
cut adaptive makes), and needs the region's inward direction and clearance,
which is the same plumbing as (b).

Where it goes wrong. The relocated centre needs an inscribed-disc query, which
exists only for adaptive's grid (`find_entry_via_distance_transform`). On a
thin ring or scan line no centre qualifies and the ladder ends in a plunge
anyway.

Cost. Highest of the four. Two new geometry queries and an entry relocation.

### (d) Refuse with a finding

Geometry. Detect that `L/2 > a` and stop the generate with an
`OperationError` naming the entry.

Where it goes wrong. Pocket's shipped default is Ramp. Every pocket whose
free run at any ring start is under 19 mm refuses. That is most pockets on a
router. It contradicts the F4.1 acceptance "Keep the ramp option".

Cost. Low to build, high to the operator.

### Summary

| Option | Needs region plumbing | Contained by construction | Keeps a ramp in small pockets | Controller-friendly | Per-op table to maintain |
|---|---|---|---|---|---|
| (a) fold along `C` | no | yes | yes (laps / bounce) | yes on rings; sawtooth only on stub lines | no |
| (b) zig-zag in free run | yes | yes if the region table is right | yes, with many reversals | poor when the run is short | yes |
| (c) helix / plunge | yes | yes | no (plunge on every ring start unless relocated) | yes | yes |
| (d) refuse | yes | n/a | no | n/a | yes |

## 4. Recommendation

**Adopt (a): fold the ramp along the following cut polyline, with a plunge
degrade.** Implement it in `apply_entry_with_provenance` / `emit_ramp` on the
branch that today emits the legacy blind legs, that is, when
`safety.surface` is `None`. Leave the probe-clipped straight legs of the
surface-riding ops as they are (G-RAMPTERRAIN's contract, re-baselined once
already).

Degrade ladder, in order:

1. **Fold.** Collect `C` = the fed moves after the plunge up to the next
   rapid or plunge, linearised. If `C` is closed (its last point returns to
   `E` within `XY_STATIONARY_EPS_MM`), walk laps. If `C` is open, bounce at
   its far end. Walk `L/2` forward, then retrace to `E`. Emit `EntryRamp`
   points at each crossed vertex and at the turn. Z by arc length, floored at
   `C`'s own Z at that point (this floor is inert on a level pass and it makes
   VCarve safe).
2. **Plunge.** If the XY length of `C` is below `RAMP_FOLD_MIN_RUN_MM`
   (proposal: `max(1.0, tool_radius)`; `apply_dressups` already holds
   `tool_diameter`), or `C` is empty (`find_next_xy_direction`'s fallback
   case), emit the straight `EntryPlunge` to `E` at the feed the emitter
   already uses. A plunge at `E` is contained by construction: `E` is a cut
   point of the operation.
3. **Never refuse.** Refusal is for geometry the engine cannot produce. The
   plunge is always producible.

No helix step. Section 3(c) shows a helix cannot be centred on a ring start
without relocation. Relocation is a separate design (see §7).

Independent check, report-only. Add `entry_audit::fed_moves_outside_region`
(§5) and run it after dressups at both call sites, where the polygons are in
scope. Record the result on `GenerationFindings` the way
`record_boundary_clip_dropped` does (written after the adapter returned,
through `&mut GenerationFindings`), carry it on `ToolpathStats` as a new
three-valued field, and adapt it to a `Diagnostic` in
`diagnostics/adapters/from_generation.rs` with a new id beside
`GEOM_BOUNDARY_CLIP_DROPPED` in `diagnostics/ids.rs`. Suggested names:
`ToolpathStats::entry_outside_region: Option<EntryOutsideRegionFinding>`,
`ids::GEOM_ENTRY_OUTSIDE_REGION = "geom.entry_outside_region"`. Contract:
`None` = not measured (no polygons in scope, entry style `None`, or an op with
no defined region); `Some` with `chords == 0` = measured clean; `Some` with
`chords > 0` = the defect. The fold makes `chords > 0` impossible on the
shipped generators, so a nonzero reading means a generator regression, which
is exactly what the sentry is for.

Triage. `SimulationTriage::build_with_rest_context` (`sim_triage.rs`) fills
`safety` from two sources only: `inputs.rapid_collisions` and
`inputs.holder_collisions`. Every other diagnostic, `Category::Safety`
included, lands in `actions`. F4.1's "triage safety row when nonzero" needs a
third Class A arm (a promotion rule on the new id, or a new `TriageInputs`
field). Whether generation-stage diagnostics are present in
`inputs.diagnostics` at all is UNVERIFIED here: they enter the project list in
`diagnostics/diagnose.rs` via `diagnostics_from_generation`, and triage takes
`diagnostics_from_project(project_diagnostics)`; the join between the two was
not traced.

Region definition per op for the checker (the checker is independent of the
fix, so it needs a table; the fix does not):

| Operation | Region for the check | Test |
|---|---|---|
| Pocket, Zigzag, Rest, Adaptive, Inlay (female), Profile `Inside` | the model polygon(s), holes included | tool disc inside: sample inside polygon AND distance to every ring `≥ r − tol` |
| Profile `Outside` | the complement of the part | tool disc off the part: sample outside polygon AND distance to every ring `≥ r − tol` |
| Face | the stock rectangle grown by `stock_offset` | not measured (`None`); a leg past the stock cuts air |
| VCarve, Chamfer, Inlay (male) | radius varies with depth | not measured (`None`) in F4.1 |

The disc-distance test above equals "inside the region offset by the tool
radius" and needs no cavalier call, so it cannot collapse or fail on a thin
region. It needs one small public boundary-distance query on `Polygon2`
(`point_segment_distance_sq` and `ring_near_point` are private today).

Rule text for `CLAUDE.md`, to sit beside the G-RAMPTERRAIN pitfall paragraph:

> - **Ramp entries on prism ops fold along the operation's own first cut
>   moves (G-RAMPCONTAIN, 2026-09-xx).** `emit_ramp` used to draw two blind
>   straight legs of `ENTRY_CLEARANCE ÷ tan(angle) ÷ 2` mm (19.08 mm at 3°)
>   from the entry column along the first chord's direction, with no region
>   in scope; on `fixtures/demo_pocket.svg` the return leg cut a trench 11 mm
>   past the pocket wall under a clean verdict (UX-R03-001). The leg now
>   walks the following cut polyline out for half the ramp length and
>   retraces it (laps on a closed ring, bounce on an open one), so it is
>   contained wherever the op's own cut is. Below `RAMP_FOLD_MIN_RUN_MM` of
>   following cut the entry degrades to a plunge at the entry column; it
>   never refuses. G-RAMPTERRAIN's Z clip on surface-riding ops is
>   unchanged. Report-only check: `entry_audit::fed_moves_outside_region`
>   → `ToolpathStats::entry_outside_region` (`None` = not measured, never
>   zero). Sentry: `ramp_contained_in_region_g_rampcontain.rs`.

## 5. Acceptance

File: `crates/rs_cam_core/tests/ramp_contained_in_region_g_rampcontain.rs`.

Fixture. Reuse the `pocket_lift_bridge_b1.rs` construction: 100×100×12 stock
at origin (−10, −10, −12), Ø6 flat end mill (`common::make_endmill_6mm`),
one `Polygon2::with_holes` of the demo pocket shape (70×50 outer with the
Ø20 island), `PocketConfig` with `depth_per_pass = 1.2`, and dressups from
`DressupConfig::for_op(OperationType::Pocket)` (Ramp 3°, arc fitting, TSP),
wired through `common::session::single_op_session_with` and
`common::session::generate`. Build the polygon in code rather than load the
SVG: the R03 NC has the wall at X = 15 while the SVG rect starts at x = 5, and
the cause of that 10 mm frame shift was not traced here (UNVERIFIED — see §7).
A synthetic polygon in the toolpath's own frame removes the question. The B1
test comment already says its polygon "mirrors the `fixtures/demo_pocket.svg`
shape".

Checker, `entry_audit::fed_moves_outside_region`:

```rust
pub struct OutsideRegionChord {
    pub move_index: usize,
    pub intent: MoveIntent,
    /// How far the tool DISC reaches past the region at the worst sample, mm.
    pub max_outside_mm: f64,
    pub worst: P3,
}

pub fn fed_moves_outside_region(
    toolpath: &Toolpath,
    region: &[Polygon2],        // the op's region; holes included
    tool_radius_mm: f64,
    sample_spacing_mm: f64,     // 0.5, as buried_fed_chords
    tolerance_mm: f64,          // 0.05
    filter: impl Fn(MoveIntent) -> bool,   // is_entry_intent for the sentry
) -> Vec<OutsideRegionChord>
```

Same loop shape as `buried_fed_chords`: skip rapids, sample linear moves
along the chord and arcs along the arc, and at each sample compute
`outside = max(0, tool_radius − distance_to_nearest_ring)` when the sample is
inside the region, or `tool_radius + distance_to_nearest_ring` when it is
outside. Report a move whose worst sample exceeds `tolerance_mm`.

Assertions:

1. `fed_moves_outside_region(&tp, &[polygon], 3.0, 0.5, 0.05, is_entry_intent)`
   is empty. Print the worst chord on failure (`move_index`, `intent`,
   `worst`, `max_outside_mm`).
2. `count_intent(&tp, MoveIntent::EntryRamp) > 0`: the fix folds, it does not
   degrade every entry to a plunge (the same guard
   `entry_moves_stock_aware_g_rampterrain.rs` uses).
3. Every `EntryRamp` sample lies within 0.05 mm of the polyline of the cut
   moves that follow the same entry span (the fold rides `C`). This pins the
   mechanism and not only the outcome.
4. Simulation half (F4.1 acceptance): simulate at 0.5 mm and assert no
   column outside the outer polygon has a top below the stock top. The
   dexel query names here are UNVERIFIED; `TriDexelStock::
   max_conservative_top_z_in_disc` exists (used in `dressup.rs`) and is a
   candidate. `pocket_lift_bridge_b1.rs` shows the simulate call shape and
   reads `sim.rapid_collisions`.

How the sentry fails on today's code. From the NC: the first entry span is
`(22.485, 18.030, 1.0) → (3.622, 20.909, 0.0) → (22.485, 18.030, −1.0)`. With
the wall at X = 15 and `r = 3`, the worst sample of the second leg has the
tool centre 11.4 mm outside and the disc 14.4 mm outside; assertion 1 reports
